# TaruBot threat model

TaruBot is a Discord bot, not a high-security facility. Protect users, data and operation against realistic abuse, mistakes and failures. **Minimal complexity, minimal bespoke design; prefer standard components.** Operational authorization remains subject to [AGENTS](../AGENTS.md).

## Assets and realistic threats

Protect Discord permissions/messages, private member and character associations, PostgreSQL's ledger/configuration/audit/pending work, credentials, encrypted backups, SSH trust and release identity.

| Threat or failure | Protection |
| --- | --- |
| Unauthorized commands, forged claims or cross-guild effects | Reauthorize actors; fresh character ownership proofs; guild-scoped persistence and least-privilege Discord permissions. No routine Administrator access. |
| Privilege escalation inside TaruBot (2.44.0 permissions) | One decision point: every gated function checks one named permission (`src/domain/rbac.ts`) against the actor resolved for that interaction or request, never a cached grant. Permissions come only from roles TaruBot manages, and a managed role counts only while held and, for Officer, backed by TaruBot's own evidence; Manage Server alone grants nothing (owner decision Q2 A, 2026-10-12). Whatever changes who holds authority (the FC link, the four managed roles, the officer rank, officer grants, links that count for rank, `/setup`) is fixed to server managers and can't sit on any role, so no holder of a delegable permission can raise their own access. Staff permissions never sit on Member or Guest, which delegated officers can hand out (`/assign`, `/guest grant`). Rank counts only through links that can confer it: a delegated officer's `/assign` gives membership, never Officer or FC Leader, removing a rank-bearing link from someone else needs a server manager, and a link not yet checked against a roster grants no authority. Server managers hold every permission implicitly, so no stored state can lock a server out. An actor that skipped resolution holds only the baseline. |
| Malicious text, upstream responses or excessive requests | Escape and bound input, parameterize queries, restrict upstream destinations and bound requests/workers. Incomplete rosters never justify access removal. |
| Private data or credentials leak | Host-only runtime settings, restricted files, redacted logs/reports (without a failed query's bound values), cleaned suggestions and encrypted offsite backups. Public Actions output contains fixed status tokens and fixed-shape failure reasons (the failed check, exit statuses, container facts, readiness booleans, code-shaped error codes and cleaned developer-fixed log messages), enforced on the host and again on the runner; settings, error messages, URLs, IDs and stacks stay in private host logs. |
| Unreviewed code, vulnerable dependency or substituted release | Protected reviewed `main`, required CI/security checks, pinned Actions/tools, AMD64/ARM64 scans and standard GitHub provenance for the exact digest, source SHA/ref and publisher identity. Untrusted PRs receive no deployment credentials. |
| Wrong SSH target or changed host key | Independently verified Ed25519 host identity published as DNSSEC-authenticated SSHFP. Runner-local Unbound validates from the maintained root anchor; strict native OpenSSH refuses missing, unsigned, bogus or mismatching records without pin/prompt/TOFU fallback. |
| Unsafe deployment, duplicate writers or interrupted migration | Exactly one production approval, validated forced-command requests, workflow concurrency and host flock, immutable transactional migrations and the database writer lease. Durable pending state is written before stopping the writer. |
| Unhealthy release, lost acknowledgement or failed recovery | Exact-image readiness/schema/writer observations, encrypted pre-migration backup, private operation logs and owner reconciliation of pending/uncertain outcomes. No automatic rollback or blind mutation retry. |
| Host/database loss or unsafe provisioning | Owner-operated provisioning and cutover, managed PostgreSQL access controls/verified TLS, scheduled encrypted offsite backups and owner-run restore drills. |
| Browser sessions, forged requests, injected text and exploited web code | Opaque server-side sessions in `__Host-` cookies; Fetch Metadata/Origin on every POST, plus a per-session form token (an HMAC keyed with the session token, compared in constant time; 403 on a mismatch); escaped templates under a script-free CSP; OAuth `state` + PKCE, with `state` checked before any Discord call; time-limited Discord calls; same-origin return paths. Pages reach only the services they declare. A POST is refused once shutdown starts, when the actor memo already holds an answer that page doesn't admit, and over its page's budget per Discord user, each before it costs a Discord request; the memo check only refuses, so a member or guest can make TaruBot resolve them fully for a page they can't use at most once a minute. Writes reauthorize against fresh Discord state; officer writes commit with their audit in one transaction, and a member's role save commits only its job (no audit row, owner decision Q4 A); web handlers never write to Discord. Members and guests sign in: admission needs the bound Member or Guest role held now and no Administrator for TaruBot in that server, where an uncached TaruBot member counts as holding it (owner decisions A2 and Q6), and someone no page admits gets no session. A member in a Discord time-out may view but not save. Sign-in is limited per Discord user (10 in 10 minutes), sessions to 10 per user, and Discord token exchanges to 30 a minute and 4 at once across everyone, refused locally after a Discord 429 until its Retry-After passes. Two controls are deferred to recorded triggers (owner decision Q7, 2026-10-09): there is no recent-sign-in gate yet, and one is added before the first destructive or irreversible web action, such as ledger or guest decisions; per-address limits wait for observed callback floods or the D16 work, after a staging check that Caddy and Docker preserve IPv6 client addresses. The pages run inside the bot process: a web code-execution bug exposes the bot token and database login. The owner accepted this (#43 W1, 2026-10-04); it's revisited on a confirmed web vulnerability, anonymous pages, a client application, serving more than one FC's Discord server, or the owner's request. The first anonymous page was revisited and accepted on 2026-10-09: the public status page, `/status` (see the next row). Any further anonymous page reopens the question. Every member and guest can reach authenticated page code, guests being the least-known people TaruBot admits; guests from other FCs in this FC's own server don't count as serving another FC (owner decision Q6, 2026-10-09). What answers that wider reach: the anonymous routes are unchanged apart from the exchange gates and the status page, the two writing pages take bounded urlencoded forms parsed with zod, the `raw()` allow-list is empty, pages reach only their declared services, and members and guests are refused while TaruBot holds Administrator. |
| Anonymous status page and the offline page | The owner accepted anonymous pages for `/status` on 2026-10-09 (the W1 revisit trigger). It keeps W1's reasoning because a visit reaches almost no code: it answers from a snapshot in memory that a timer refreshes every minute, rendered once per snapshot, so no visit queries the database, calls Discord or renders much; it reads no session (the cookie isn't read), takes no input (the query string is ignored), has no form and sets no cookie; one global budget of 600 a minute, keyed by nothing personal, refuses a flood with a 429 and Retry-After before anything else and logs one line per run of refusals, not one per request (a flood can crowd real visitors out of the status page for the rest of that minute, and of nothing else); it carries the same header set, the script-free CSP and `noindex`. It shows process-wide state only (never a server, member or count of either), and its samples hold the same, kept 90 days (the very first one longer, to mark where the history starts). If the whole host is down, the page is down too, which the owner accepted; the heartbeat covers that. When Caddy gets no complete answer from the bot (stopped, restarting, crashed, or the connection dropped, as for a request body over 64 KiB), bundled Caddy answers a static page from a read-only mount, only for its own 502, 503 and 504: no script, a CSP admitting only its own styles and fonts, `no-store`, no upstream detail, and always the whole page (conditional and range headers are dropped first). Caddy serves whatever that mount holds and follows symlinks, so it holds regular files only (a test checks every entry and its Git mode) and dotfiles are hidden; the managed deploy entry makes it readable only when it's a real directory, so a symlinked folder can't widen the permissions of what it points at. |
| Self-service roles as privilege escalation | Any officer may change the role menu, with no Discord permission check of the officer (owner decision, 2026-10-09), so one rule set is the boundary. A menu role is an ordinary role below TaruBot that TaruBot can assign, and never a bound or retired access role; the menu editor, `/config roles` and `/setup onboarding` enforce that under the guild row lock. It sits below the Officer and FC Leader roles and below every role under TaruBot with Kick Members, Ban Members, Time Out Members, Manage Nicknames or Administrator, a moderation bot's managed role included (owner decision, 2026-10-09): Discord lets those powers reach only members whose highest role is lower, so a menu role placed above one would put everyone who picks it out of that role's reach. TaruBot's own managed role is the one exception, since TaruBot alone holds it. It holds no server permission @everyone lacks, and never Administrator, Manage Server, Manage Roles or Manage Channels. It changes nothing in a channel that everyone, Member holders or Guest holders already see. Its own allow in any channel carries no more than @everyone's server-wide permissions, View Channel aside, and lifts no deny another role sets there, View Channel included, nor @everyone's deny outside a channel it opens, so it can't undo a mute role, show a channel a jail or quarantine role hides, or let people post in a read-only channel they see through another role; in a channel it opens, lifting @everyone's deny and the View Channel bit of the Member and Guest roles' deny is what opening means. A menu role can't take anything away from its holders, so a mute, jail or quarantine role can't be listed and then removed by the people it restricts; such a role can't be removed through the menu either. It may open other channels only within what their audience holds server-wide, and never one TaruBot recognizes as officer-facing. **That recognition is a heuristic**: it misses a private channel only Administrators see, and one opened to officers through per-member entries rather than a role, so the editor lists every channel each role opens. Channels TaruBot can't read are outside every channel check, so officers confirm the roles don't open or give permissions in them. Roles are checked when added (against fresh Discord state), on every view of the editor and of My roles, per role against fresh Discord state just before a member's change is written, and by the "Role menu" health check; reconciliation's access-loss removals judge TaruBot's cached view and only remove. A role that later fails a check for what it gives, for example one moved above a moderation role, can't be given but can still be removed by whoever holds it. A save names only roles the menu allows in categories the person was shown; anything else is refused, and the job derives its targets again from the current menu. Discord adds up role grants, so an opt-in channel would stay open to someone who lost Member and Guest: reconciliation removes listed channel-opening menu roles from anyone left with none of Member, Guest, Officer and FC Leader, and the job doesn't add one to them (owner decision Q3 B, 2026-10-09). |
| Sensitive role choices (pronouns, gender identity) in storage | Discord holds members' picks. A waiting change holds role IDs until its job ends, at most 7 days after the last save, and migration 012's trigger clears them from the live record on every path that ends the job; backups and the provider's point-in-time recovery keep what they captured for their own retention. Finished role-choice jobs (who and when, never which roles) are deleted after 30 days. Results, diagnostics and logs carry counts only, choices aren't audited, officer views don't name the member, a failed query's bound values are stripped from issue reports, saves are refused while Discord changes are paused, and a restore closes the changes its backup caught waiting. |
| Mod mail: members' private messages to officers (2.43.0, issue #60) | The most sensitive text TaruBot holds. **Encryption scope:** each case's topic and every message are AES-256-GCM ciphertext under `MODMAIL_KEY`, padded first (every topic to one length, bodies in 256-byte blocks) so lengths say little, with a fresh nonce per field and an AAD binding a topic to its server, case and opener, and a body to those plus its message ID, author, side, signing and kind. A row copied to another case, or re-inserted under another opener or author, fails to decrypt. Who opened a case, who wrote each row, signing choices, states, times and the read log are not encrypted: they are what access control and retention work on. **What the encryption protects against:** read-only exposure of the database alone: a leaked dump, the provider's point-in-time recovery or storage, someone with read access. It does not stop a database **writer**: one can delete cases, or grant itself officer authority through the configuration tables (`guilds.officer_role_id`, `officer_overrides`) and then read every case through the dashboard like any officer. **Backups:** the offsite backup encrypts the database dump and the host's whole `.env`, which now holds `MODMAIL_KEY`, to the same age recipients (`ops/backup.sh`), so **whoever holds the backups' age identity can read every mod mail case they hold**: the `.env` copy carries the key next to the dump. That is the owner's deliberate trade-off (2026-10-11): a lost host restores fully, cases included, and that copy is how a lost key is recovered. **Key on the host:** the key lives in host settings (the private `.env` and its encrypted copies), never in the database, logs, reports, readiness (a boolean only) or Discord; main.ts reads it once, deletes it from the process environment and keeps it out of the configuration it passes around. Losing every copy loses every case (owner decision 1); changing it makes existing cases unreadable (no rotation in 2.43.0; the stored key ID leaves room for keeping previous keys). **Access:** a case is opened by a Member or Guest holder (without Administrator for TaruBot) through `/modmail` or the Mod mail page's form, both one application path with the same checks and limits, the page's form also during a Discord time-out, when Discord takes slash commands away (owner decision of 2026-10-11). It is open to its server's officers and to its opener while they hold Member or Guest without Administrator for TaruBot; anyone else gets the same 404 as a number never used. Mod mail's pages resolve the viewer afresh on every request, so an officer removed or demoted loses them at once. Every view of a case page, and every list that shows a case's decrypted topic, is recorded in its read log (case views once a minute per reader, list views once an hour). Officers always see the real author of every reply (owner decisions 3 and 4). Writes reauthorize on fresh Discord state, check text, limits and a revision for close and reopen, and commit in one transaction. **No text in Discord:** `/modmail`'s form text arrives with the interaction, so no message intent is needed or held, and its replies stay private even under DevBot's public-response override; pings and DMs carry a case number and a link, never the text or the member's name; the ping may mention only the Officer role, never @everyone (its allowed mentions name that role alone, and the gateway drops a role equal to the server's ID). For the mention to notify officers while their role stays non-mentionable, officers allow the TaruBot role Mention Everyone in the officer notifications channel's own permissions by hand (owner decision of 2026-10-11; TaruBot never grants itself a permission); `/config validate` warns about it anywhere else, or there while mod mail is off. A stolen bot token could then mention @everyone in that one channel, which the owner accepted along with the token's other powers; pings are coalesced to one per case, and reply pings to one per member across their cases, per 10 minutes, DMs to one per case. Job payloads hold the case ID only, with no user; only ciphertext is ever bound as a query value, so a failed query's bound values carry no text either; a field that won't decrypt shows a fixed sentence and files one issue report without its content, tampering and a changed key under separate reports. **Retention:** a closed case, its messages, read log and history are deleted 90 days after closing (owner decision 2), by a timer of its own under the writer lease; reopening cancels that. Only the officers' on/off switch reaches the long-lived audit log, so nothing there keeps who opened cases. Backups and point-in-time recovery keep what they captured for their own retention, and a restore can bring back expired cases until the next retention pass deletes them. **Host compromise:** host root or a web code-execution bug in the bot process (W1) reaches the key and the database together, so it reads every case still held. |
| Role churn and Discord request exhaustion | 10 saves per member in 10 minutes, equal-state saves that write nothing, one coalesced job per member, a 50-role menu cap, the queue's concurrency, discord.js rate-limit handling, light actor resolution for GETs and sign-in (one request instead of three), and POSTs to a page someone can't use refused from the actor memo, so they cost at most one full resolution a minute. |
| Sign-in floods costing the bot's egress address | Any client can start a sign-in, and each callback costs a token request from the bot's address; enough refused requests would get that address banned from Discord, bot included. `state` is checked before any Discord call, exchanges are capped at 30 a minute and 4 at once, and every callback is refused locally while Discord's Retry-After from a 429 runs. |

One Discord application must never run in two places. A database restore must account for Discord effects already delivered. A green build or skipped deployment does not prove a healthy live bot.

## Trust and authority

Discord input, Lodestone responses, member suggestions, unreviewed PRs and unverified artifacts are untrusted. Network connections require appropriate TLS or DNSSEC-authenticated SSH host verification.

We trust the owner account, protected `main` and code-owner review, GitHub-hosted Actions and correctly configured production protections, reviewed release/host scripts, selected pinned tools, maintained DNSSEC root anchors, the owner's DNS authority/delegation and the provider control plane. Scope credentials narrowly. The deployment key reaches only the reviewed forced command; the runner receives no database URL or Discord token. Runtime and backup credentials stay on the host.

The owner maintains branch/environment protections, DNSSEC delegation/SSHFP, credentials and infrastructure. The repository pipeline automates delivery, not provisioning. A reviewed protected workflow plus the owner's production approval authorizes delivery; no additional bespoke command broker, enrollment service or repeated proof chain is needed.

Trusting deployment code never grants Discord users privileges or makes their text executable.

## Accepted limits

- **Trusted-component compromise is not contained by these controls.** Compromised owner/runner/deploy credentials, DNS authority or reviewed host code can affect production. Docker access is effectively host-root access. Standard account protection and review remain essential.
- **Host root defeats host-local controls.** A read-only unprivileged container reduces exposure but cannot make a compromised host trustworthy.
- **Serialization needs cooperation.** Manual work must fence automation and other writers; flock and workflow concurrency cannot stop an unrestricted operator.
- **Cancellation is not undo.** A remote command may finish after the runner loses its connection. Inspect the durable host state before another mutation.
- **A leaked bot token acts as TaruBot.** It can grant every role below TaruBot's highest, including Officer, FC Leader and every role on the self-service menu. Keep moderation and admin powers on roles above TaruBot.
- **Officer-facing channel detection can't know a channel's purpose.** A private channel that only Administrators see, with no explicit allow, isn't recognized, nor is one opened to officers through per-member entries rather than a role (an officer room built from each officer's own entry, or a ticket-style channel), so officers must read each menu role's "Opens:" list.
- **Discord shows roles.** Role holders are visible to everyone in the server, and role changes to staff with View Audit Log; TaruBot can't hide what Discord shows.
- **A hand-added Member or Guest role admits its holder** to My roles until reconciliation removes it, because admission follows the role held now (owner decision Q6 A); its reach is picking menu roles.
- **Officers see channel names their roles don't open.** On Server configuration and Role menu, any officer, Officer-role holders included, can see the name of any channel TaruBot can see when a check names it or a menu role opens it, including channels their own Discord roles don't open, because the "Opens:" list is how they check the officer-channel heuristic.
- **Mod mail's encryption protects against read-only exposure only.** It keeps a leaked dump, the provider's point-in-time recovery or storage, and read access to the database from showing the text. The key sits beside the bot (owner decision 8), so host root or a web code-execution bug (W1) reads every case still held; the offsite backup encrypts the `.env` with the key to the same recipients as the dump, so whoever holds the backups' age identity can read the cases in them (the owner's deliberate trade-off, so a lost host restores fully); and a database writer can delete cases, or make itself an officer through the configuration tables and read them on the dashboard.
- **Recovery is bounded.** Restores can lose recent decisions or repeat external effects. Backups in the same provider account are not independent disaster recovery; keep independent copies. No zero-loss or continuous-availability guarantee is assumed.

A confirmed compromise requires owner response: fence writers, revoke/rotate credentials, assess damage and recover from verified evidence. These limits do not excuse leaks or known vulnerabilities.

## Engineering policy

Prefer GitHub controls, strict OpenSSH, Docker Compose, PostgreSQL transactions/advisory locks and established encrypted backup tools. Custom code must address a concrete requirement these facilities do not meet. Test practical failure behavior with invented data and disposable resources; record owner-run live acceptance separately. Introduce a stronger threat model only for a concrete requirement agreed with the owner.
