# TaruBot threat model

TaruBot is a Discord bot, not a high-security facility. Protect users, data and operation against realistic abuse, mistakes and failures. **Minimal complexity, minimal bespoke design; prefer standard components.** Operational authorization remains subject to [AGENTS](../AGENTS.md).

## Assets and realistic threats

Protect Discord permissions/messages, private member and character associations, PostgreSQL's ledger/configuration/audit/pending work, credentials, encrypted backups and their age identity, and release identity: the signed images and the channel tags that select them.

| Threat or failure | Protection |
| --- | --- |
| Unauthorized commands, forged claims or cross-guild effects | Reauthorize actors; fresh character ownership proofs; guild-scoped persistence and least-privilege Discord permissions. No routine Administrator access. |
| Privilege escalation inside TaruBot (2.44.0 permissions, 2.45.0 pauses) | One decision point: every gated function checks one named permission (`src/domain/rbac.ts`) against the actor resolved for that interaction or request. Commands, buttons and every web POST resolve the actor afresh; a page GET may reuse a resolution for up to 60 seconds (`ACTOR_MEMO_MS`), except pages that declare `freshActor` (mod mail, Moderation), and access is never cached apart from the actor it belongs to. Permissions come only from roles TaruBot manages, and a managed role counts only while held and, for Officer, backed by TaruBot's own evidence; Manage Server alone grants nothing (owner decision Q2 A, 2026-10-12). Whatever changes who holds authority (the FC link, the four managed roles, the officer rank, officer grants, links that count for rank, `/setup`) is fixed to server managers and can't sit on any role, so no holder of a delegable permission can raise their own access. Staff permissions never sit on Member or Guest, which delegated officers can hand out (`/assign`, `/guest grant`). Rank counts only through links that can confer it: a delegated officer's `/assign` gives membership, never Officer or FC Leader, removing a rank-bearing link from someone else needs a server manager, and a link not yet checked against a roster grants no authority. Server managers hold every permission implicitly, so no stored state can lock a server out. An actor that skipped resolution holds only the baseline. **Pauses (2.45.0)** are deny-only, so a pause can never raise anyone's access, and a stored pause is read afresh on every resolution of anyone but a server manager. Who may pause whom is the privilege rule (`src/application/moderation.ts`): nobody pauses or lifts a pause on themselves; server managers and bots can't be paused, and no stored pause counts against a manager; an officer with `moderation.block`, who isn't a server manager, may pause only people holding no staff permission and only member and baseline features, never mod mail opening (server managers only, owner decision Q6 B, 2026-10-12, since mod mail is how members reach officers about officers), and may change or lift only pauses an officer set; a server manager may pause anyone else. The Officer role carries `moderation.view` and `moderation.block`, so every delegated officer can use pauses within those limits until server managers can choose which permissions a role carries. |
| Malicious text, upstream responses or excessive requests | Escape and bound input, parameterize queries, restrict upstream destinations and bound requests/workers. Incomplete rosters never justify access removal. |
| Private data or credentials leak | Runtime settings only in the runtime (the owner's private settings copy and the containers' environment), restricted files, redacted logs/reports (without a failed query's bound values, and without the backup storage keys or the backup ping URL), cleaned suggestions and encrypted offsite backups. The runner never sees a runtime setting, and nothing on the runtime reports back to GitHub: Deploy's public output holds fixed sentences, the version, the source commit and the image digests. Backup logs and pings carry object keys, sizes and the failed stage, never a value. |
| Unreviewed code, vulnerable dependency or substituted release | Protected reviewed `main`, required CI/security checks, pinned Actions, tools and base images, AMD64/ARM64 scans of the bot image, and standard GitHub provenance for both release images' exact digests, source SHA/ref and publisher identity, which Deploy verifies again before it moves a tag. The runtimes follow only `ghcr.io/deconfined/tarubot-release`, written only by an approved Deploy with its environment's `RELEASE_REGISTRY_TOKEN` (owner decision, 2026-10-28): every workflow of the repository, on any branch, can ask for a token that writes `ghcr.io/deconfined/tarubot`, so a channel tag there would let any of them deploy without the approval or the provenance checks. Deploy's own token only reads, and it copies exactly the digests it verified. A publication never moves a channel back to an older release; only a dispatched Deploy rolls back. Untrusted PRs receive no token that can write a package. The web image, the stock Caddy image pinned by digest plus static files, isn't scanned. |
| A pipeline reaching into the runtime | No host access exists to misuse (owner decision, 2026-10-28): GitHub never connects to the runtime, and the runner holds no runtime credential. During an approved Deploy it holds the release registry token and nothing else, and uses it only to copy two verified digests to two channel tags; the runtime pulls. Runtime, database and backup credentials exist only in the runtime's settings. |
| Unsafe deployment, duplicate writers or interrupted migration | The owner's environment approval, given in the same attempt (owner rule, 2026-10-08), per-target workflow concurrency, an updater that stops the old container before it starts the new one, immutable migrations applied in one transaction under the writer lease's lock, and the database writer lease. One-off tools run as separate containers, which the updater never follows: it touches only the two named containers that carry its scope label, and a one-off run has another name. |
| Unhealthy release or failed migration | An encrypted pre-migration backup under the writer lease's lock, whose failure applies nothing; migrations in one transaction; the exact schema check, so an older image refuses a newer schema; a failed startup migration that waits 10 minutes before the container exits, holding nothing, so a restart loop can't store a full backup every minute; command registration that is reported, never fatal. GitHub can't watch or undo a deployment, which the owner accepted (2026-10-28): `/version`, the heartbeat and the container's health show the result, and rolling back is deploying the earlier version, which across a migration means fixing forward or restoring. |
| Host/database loss or unsafe provisioning | Owner-operated provisioning and cutover, managed PostgreSQL access controls/verified TLS, daily encrypted offsite backups taken by the bot itself, an owner-held age identity with an offline copy, and owner-run restore drills. Because the bot takes them, its process holds the bucket's key pair, which can read and delete backups: whatever reaches the process (a web code-execution bug, W1) reaches that too, so keep independent copies. The `rehearsal` profile never backs up, so a disposable database's dump never becomes the newest backup a restore takes as `latest`. |
| The updater's Docker socket | Watchtower mounts the Docker socket, which is root on that Docker host: it comes with the pull model the owner chose (2026-10-28). It is one image pinned by digest, read-only, with no capabilities and no new privileges, following only the containers named `tarubot` and `tarubot-web` that carry its scope label, and its scope keeps it from stopping another Watchtower on the host. A compromised updater image is a compromised Docker host. |
| Browser sessions, forged requests, injected text and exploited web code | Opaque server-side sessions in `__Host-` cookies; Fetch Metadata/Origin on every POST, plus a per-session form token (an HMAC keyed with the session token, compared in constant time; 403 on a mismatch); escaped templates under a script-free CSP; OAuth `state` + PKCE, with `state` checked before any Discord call; time-limited Discord calls; same-origin return paths. Pages reach only the services they declare. A POST is refused once shutdown starts, when the actor memo already holds an answer that page doesn't admit, and over its page's budget per Discord user, each before it costs a Discord request; the memo check only refuses, so a member or guest can make TaruBot resolve them fully for a page they can't use at most once a minute. Writes reauthorize against fresh Discord state; officer menu writes commit with their audit in one transaction, a member's role save commits only its job (no audit row, owner decision Q4 A), and mod mail audits only its on/off switch (see the mod mail row); web handlers never write to Discord. Members and guests sign in: admission needs the bound Member or Guest role held now and no Administrator for TaruBot in that server, where an uncached TaruBot member counts as holding it (owner decisions A2 and Q6), and someone no page admits gets no session. A member in a Discord time-out may view but not save. Sign-in is limited per Discord user (10 in 10 minutes), sessions to 10 per user, and Discord token exchanges to 30 a minute and 4 at once across everyone, refused locally after a Discord 429 until its Retry-After passes. One control is still deferred to a recorded trigger (owner decision Q7, 2026-10-09): per-address limits wait for observed callback floods or the D16 work, after a staging check that Caddy and Docker preserve IPv6 client addresses. The other, a recent-sign-in gate, exists since 2.45.0, when the first web action that restricts people arrived: a page that declares `recentSignIn` refuses every POST unless the session's Discord sign-in is within the last 15 minutes (`RECENT_SIGN_IN_MS`, judged on the database clock), answering 303 to the page itself, after the same-origin, session, server, form-token and shutdown checks and the actor memo's refusal (someone the memo already shows is not admitted gets the plain refusal, not an invitation to sign in) and before the budget and the fresh actor, and keeping none of the form. The page's GET then offers "Sign in again to make changes" as a plain link to `/login`, which returns to the page with a fresh session. The POST is not redirected to `/login`, because a form submission redirected on to discord.com is blocked by the page's CSP `form-action 'self'` in Chromium, so a click would silently do nothing; a link is a navigation, which that directive doesn't govern. Only the Moderation page declares it so far. What it gives, precisely: `/login` sends Discord `prompt=none`, so for a browser still signed in to Discord the re-sign-in is silent. The gate therefore stops a copied or replayed TaruBot session cookie, whose holder's browser has no Discord session as that person, from pausing people or lifting pauses once 15 minutes have passed since its owner last signed in; a cookie copied inside that window works until it closes. It does not defend an unlocked browser that is still signed in to Discord, where the redirect completes without a prompt. It covers changes only: a copied cookie can still read pauses with their reasons and look up suggestion senders. The other writing pages (Role menu, My roles, Mod mail) don't; a page opts in with one option, and whether more should is the owner's call. The pages run inside the bot process: a web code-execution bug exposes the bot token and database login. The owner accepted this (#43 W1, 2026-10-04); it's revisited on a confirmed web vulnerability, anonymous pages, a client application, serving more than one FC's Discord server, or the owner's request. The first anonymous page was revisited and accepted on 2026-10-09: the public status page, `/status` (see the next row). Any further anonymous page reopens the question. Every member and guest can reach authenticated page code, guests being the least-known people TaruBot admits; guests from other FCs in this FC's own server don't count as serving another FC (owner decision Q6, 2026-10-09). What answers that wider reach: the anonymous routes are unchanged apart from the exchange gates and the status page, the writing pages (Role menu, My roles, Moderation, and Mod mail's inbox and case pages) take bounded urlencoded forms parsed with zod, the `raw()` allow-list is empty, pages reach only their declared services, and members and guests are refused while TaruBot holds Administrator. |
| Anonymous status page and the offline page | The owner accepted anonymous pages for `/status` on 2026-10-09 (the W1 revisit trigger). It keeps W1's reasoning because a visit reaches almost no code: it answers from a snapshot in memory that a timer refreshes every minute, rendered once per snapshot, so no visit queries the database, calls Discord or renders much; it reads no session (the cookie isn't read), takes no input (the query string is ignored), has no form and sets no cookie; one global budget of 600 a minute, keyed by nothing personal, refuses a flood with a 429 and Retry-After before anything else and logs one line per run of refusals, not one per request (a flood can crowd real visitors out of the status page for the rest of that minute, and of nothing else); it carries the same header set, the script-free CSP and `noindex`. It shows process-wide state only (never a server, member or count of either), and its samples hold the same, kept 90 days (the very first one longer, to mark where the history starts). If the whole host is down, the page is down too, which the owner accepted; the heartbeat covers that. When Caddy gets no complete answer from the bot (stopped, restarting, crashed, or the connection dropped, as for a request body over 64 KiB), bundled Caddy answers a static page built into the release's web image, only for its own 502, 503 and 504: no script, a CSP admitting only its own styles and fonts, `no-store`, no upstream detail, and always the whole page (conditional and range headers are dropped first). Caddy serves whatever that folder holds and follows symlinks, so it holds regular files only (a test checks every entry and its Git mode) and dotfiles are hidden; the web image copies them with fixed modes (files 0644, directories 0755) and nothing else. |
| Self-service roles as privilege escalation | Any officer may change the role menu, with no Discord permission check of the officer (owner decision, 2026-10-09), so one rule set is the boundary. A menu role is an ordinary role below TaruBot that TaruBot can assign, and never a bound or retired access role; the menu editor, `/config roles` and `/setup onboarding` enforce that under the guild row lock. It sits below the Officer and FC Leader roles and below every role under TaruBot with Kick Members, Ban Members, Time Out Members, Manage Nicknames or Administrator, a moderation bot's managed role included (owner decision, 2026-10-09): Discord lets those powers reach only members whose highest role is lower, so a menu role placed above one would put everyone who picks it out of that role's reach. TaruBot's own managed role is the one exception, since TaruBot alone holds it. It holds no server permission @everyone lacks, and never Administrator, Manage Server, Manage Roles or Manage Channels. It changes nothing in a channel that everyone, Member holders or Guest holders already see. Its own allow in any channel carries no more than @everyone's server-wide permissions, View Channel aside, and lifts no deny another role sets there, View Channel included, nor @everyone's deny outside a channel it opens, so it can't undo a mute role, show a channel a jail or quarantine role hides, or let people post in a read-only channel they see through another role; in a channel it opens, lifting @everyone's deny and the View Channel bit of the Member and Guest roles' deny is what opening means. A menu role can't take anything away from its holders, so a mute, jail or quarantine role can't be listed and then removed by the people it restricts; such a role can't be removed through the menu either. It may open other channels only within what their audience holds server-wide, and never one TaruBot recognizes as officer-facing. **That recognition is a heuristic**: it misses a private channel only Administrators see, and one opened to officers through per-member entries rather than a role, so the editor lists every channel each role opens. Channels TaruBot can't read are outside every channel check, so officers confirm the roles don't open or give permissions in them. Roles are checked when added (against fresh Discord state), on every view of the editor and of My roles, per role against fresh Discord state just before a member's change is written, and by the "Role menu" health check; reconciliation's access-loss removals judge TaruBot's cached view and only remove. A role that later fails a check for what it gives, for example one moved above a moderation role, can't be given but can still be removed by whoever holds it. A save names only roles the menu allows in categories the person was shown; anything else is refused, and the job derives its targets again from the current menu. Discord adds up role grants, so an opt-in channel would stay open to someone who lost Member and Guest: reconciliation removes listed channel-opening menu roles from anyone left with none of Member, Guest, Officer and FC Leader, and the job doesn't add one to them (owner decision Q3 B, 2026-10-09). |
| Sensitive role choices (pronouns, gender identity) in storage | Discord holds members' picks. A waiting change holds role IDs until its job ends, at most 7 days after the last save, and migration 012's trigger clears them from the live record on every path that ends the job; backups and the provider's point-in-time recovery keep what they captured for their own retention. Finished role-choice jobs (who and when, never which roles) are deleted after 30 days. Results, diagnostics and logs carry counts only, choices aren't audited, officer views don't name the member, a failed query's bound values are stripped from issue reports, saves are refused while Discord changes are paused, and a restore closes the changes its backup caught waiting. |
| Mod mail: members' private messages to officers (2.43.0, issue #60) | The most sensitive text TaruBot holds. **Encryption scope:** each case's topic and every message are AES-256-GCM ciphertext under `MODMAIL_KEY`, padded first (every topic to one length, bodies in 256-byte blocks) so lengths say little, with a fresh nonce per field and an AAD binding a topic to its server, case and opener, and a body to those plus its message ID, author, side, signing and kind. A row copied to another case, or re-inserted under another opener or author, fails to decrypt. Who opened a case, who wrote each row, signing choices, states, times and the read log are not encrypted: they are what access control and retention work on. **What the encryption protects against:** read-only exposure of the database alone: a leaked dump, the provider's point-in-time recovery or storage, someone with read access. It does not stop a database **writer**: one can delete cases, or grant itself officer authority through the configuration tables (`guilds.officer_role_id`, `officer_overrides`) and then read every case through the dashboard like any officer, or end a pause on itself (`member_blocks`, whose trigger lets a lift be written once). **Backups:** the bot's offsite backup encrypts the database dump and a copy of the bot's own settings, `MODMAIL_KEY` included, to the same age recipients (`src/application/backups.ts`), so **whoever holds the backups' age identity can read every mod mail case they hold**: the settings copy carries the key next to the dump. That is the owner's deliberate trade-off (2026-10-11): a lost host restores fully, cases included, and that copy is how a lost key is recovered. **Key in the runtime's settings:** the key lives in the runtime's settings (the owner's private settings copy, the container's environment and the backups' encrypted settings copies), never in the database, logs, reports, readiness (a boolean only) or Discord; main.ts reads it once, deletes it from the process environment and keeps it out of the configuration it passes around, and only the cipher and the backup service's settings snapshot keep it. Losing every copy loses every case (owner decision 1); changing it makes existing cases unreadable (no rotation in 2.43.0; the stored key ID leaves room for keeping previous keys). **Access:** a case is opened by a Member or Guest holder (without Administrator for TaruBot) through `/modmail` or the Mod mail page's form, both one application path with the same checks and limits, the page's form also during a Discord time-out, when Discord takes slash commands away (owner decision of 2026-10-11). It is open to its server's officers and to its opener while they hold Member or Guest without Administrator for TaruBot; anyone else gets the same 404 as a number never used. Mod mail's pages resolve the viewer afresh on every request, so an officer removed or demoted loses them at once. Every view of a case page, and every list that shows a case's decrypted topic, is recorded in its read log (case views once a minute per reader, list views once an hour). Officers always see the real author of every reply (owner decisions 3 and 4). Writes reauthorize on fresh Discord state, check text, limits and a revision for close and reopen, and commit in one transaction. **No text in Discord:** `/modmail`'s form text arrives with the interaction, so no message intent is needed or held, and its replies stay private even under DevBot's public-response override; pings and DMs carry a case number and a link, never the text or the member's name; the ping may mention only the Officer role, never @everyone (its allowed mentions name that role alone, and the gateway drops a role equal to the server's ID). For the mention to notify officers while their role stays non-mentionable, officers allow the TaruBot role Mention Everyone in the officer notifications channel's own permissions by hand (owner decision of 2026-10-11; TaruBot never grants itself a permission); `/config validate` warns about it anywhere else, or there while mod mail is off. A stolen bot token could then mention @everyone in that one channel, which the owner accepted along with the token's other powers; pings are coalesced to one per case, and reply pings to one per member across their cases, per 10 minutes, DMs to one per case. Job payloads hold the case ID only, with no user; only ciphertext is ever bound as a query value, so a failed query's bound values carry no text either; a field that won't decrypt shows a fixed sentence and files one issue report without its content, tampering and a changed key under separate reports. **Retention:** a closed case, its messages, read log and history are deleted 90 days after closing (owner decision 2), by a timer of its own under the writer lease; reopening cancels that. Only the officers' on/off switch reaches the long-lived audit log, so nothing there keeps who opened cases. Backups and point-in-time recovery keep what they captured for their own retention, and a restore can bring back expired cases until the next retention pass deletes them. **Host compromise:** Docker host root, Docker access (which reads every container setting), the updater's socket or a web code-execution bug in the bot process (W1) reaches the key and the database together, so it reads every case still held. |
| Pauses: private reasons and the suggestion-sender lookup (2.45.0) | A pause's reason is private text, kept like a guest revocation: shown to the paused person (owner decision Q5 A, 2026-10-12: the feature, the end and the reason, never who set it) and to officers who hold `moderation.view`, who also see who set each pause of someone else and how earlier ones ended (an officer who is themselves paused, which only a server manager can do, sees their own pauses on the Moderation page as the paused person does, without who set them, and their own ended pauses are left out, as in `/moderate status`); held in `member_blocks` until a server's data is removed; never written to the audit log, logs, issue reports, Discord messages or DMs, and no pause posts or sends anything. The history can't be edited or deleted by an ordinary statement (a trigger). Pausing is deny-only, so the worst a wrongly set pause does is refuse one feature until it ends or an officer lifts it. **New visibility, deliberately** (owner decision Q7 A, 2026-10-12): officers who hold `moderation.view` can look up the sender of a public suggestion by its issue number, from the private audit record `/suggest` has always kept. Until 2.45.0 only the deployment's operator, reading the database, could. It exists so an officer can pause the sender; nothing public changes, and the issue and everything else public still carry no name. The lookup is scoped to the officer's own server, reads only that audit row, and finds nothing for an attempt GitHub didn't confirm or a row a restore lost. Setting or lifting a pause needs `moderation.block`, and the Moderation page's changes also need a sign-in within the last 15 minutes, which limits a replayed session cookie but not an unlocked browser still signed in to Discord (see the browser-sessions row). |
| Role churn and Discord request exhaustion | 10 saves per member in 10 minutes, equal-state saves that write nothing, one coalesced job per member, a 50-role menu cap, the queue's concurrency, discord.js rate-limit handling, light actor resolution for GETs and sign-in (one request instead of three), and POSTs to a page someone can't use refused from the actor memo, so they cost at most one full resolution a minute. |
| Sign-in floods costing the bot's egress address | Any client can start a sign-in, and each callback costs a token request from the bot's address; enough refused requests would get that address banned from Discord, bot included. `state` is checked before any Discord call, exchanges are capped at 30 a minute and 4 at once, and every callback is refused locally while Discord's Retry-After from a 429 runs. |

One Discord application must never run in two places. A database restore must account for Discord effects already delivered. A green build, a skipped deployment or a successful Deploy, which only moves tags, does not prove a healthy live bot.

## Trust and authority

Discord input, Lodestone responses, member suggestions, unreviewed PRs and unverified artifacts are untrusted. Network connections require appropriate TLS: the database with its verified CA, backups over HTTPS.

We trust the owner account, protected `main` and code-owner review, GitHub-hosted Actions and correctly configured production protections, GHCR, the pinned images (Alpine, Caddy and Watchtower) and tools, the Docker host and the provider control plane. Scope credentials narrowly. The runner holds no runtime credential. During an approved Deploy it holds the release registry token, the `production` or `staging` environment's secret `RELEASE_REGISTRY_TOKEN`, and nothing else; the workflow's own token only reads the release. Runtime and backup credentials exist only in the runtime's settings.

The owner maintains branch/environment protections, credentials, the Docker hosts and their settings, the backup buckets and the age identity. The repository pipeline automates delivery, not provisioning. A reviewed protected workflow plus the owner's production approval authorizes delivery; no additional bespoke command broker, enrollment service or repeated proof chain is needed.

Trusting deployment code never grants Discord users privileges or makes their text executable.

## Accepted limits

- **Trusted-component compromise is not contained by these controls.** Compromised owner credentials, the release registry token, the registry or a pinned image (TaruBot's, Caddy's or Watchtower's) can affect production. Docker access, the updater's socket included, is root on the Docker host. Standard account protection and review remain essential.
- **Tags, not digests, select what runs.** The updater follows the channel tag and verifies nothing itself: Deploy verifies provenance before it moves a tag, but whoever can write the release package's tags (the owner's account, or the release registry token) can change what runs. Deploy's summary records the digests it set, and `docker inspect` shows the one running.
- **The release registry token is a classic personal access token.** Its `write:packages` covers every package of the owner's account, `ghcr.io/deconfined/tarubot` included, not only the release package. It is held only as an environment secret of `production` and `staging`, which GitHub hands only to their approved job on `main`, with an expiry the owner tracks and renews.
- **Self-hosters following `latest` follow tags any repository workflow with `packages: write` can move.** `latest` and `web-latest` stay in `ghcr.io/deconfined/tarubot`, where publication moves them only after attestation, but nothing stops another workflow of the repository from moving them, or a version tag, too. The stock file's `updates` profile follows whatever `latest` names. Only a digest, pinned with `TARUBOT_IMAGE` after the [provenance check](DEPLOYMENT.md#signed-build-provenance), can't be changed by a tag, and that pins the bot only: the proxy follows a `web-` tag.
- **The web image isn't scanned.** It is the stock Caddy image pinned by digest plus TaruBot's static files; the bot image is scanned. A Caddy fix arrives by updating the pin in a release.
- **Host root defeats host-local controls.** A read-only unprivileged container reduces exposure but cannot make a compromised host trustworthy.
- **Serialization needs cooperation.** Manual work must fence other writers; the writer lease and workflow concurrency cannot stop an unrestricted operator, and a one-off `run` of the bot's service without a tool command starts a second bot.
- **Deploy can't watch or undo.** It ends once the tags moved; the runtime follows within its poll interval, and whether the release came up is read from `/version`, the heartbeat and the container. A rollback is a dispatched Deploy, and after a migration it means fixing forward or restoring (owner decision, 2026-10-28).
- **A leaked bot token acts as TaruBot.** It can grant every role below TaruBot's highest, including Officer, FC Leader and every role on the self-service menu. Keep moderation and admin powers on roles above TaruBot.
- **Officer-facing channel detection can't know a channel's purpose.** A private channel that only Administrators see, with no explicit allow, isn't recognized, nor is one opened to officers through per-member entries rather than a role (an officer room built from each officer's own entry, or a ticket-style channel), so officers must read each menu role's "Opens:" list.
- **Discord shows roles.** Role holders are visible to everyone in the server, and role changes to staff with View Audit Log; TaruBot can't hide what Discord shows.
- **A hand-added Member or Guest role admits its holder** to My roles until reconciliation removes it, because admission follows the role held now (owner decision Q6 A); its reach is picking menu roles.
- **Officers see channel names their roles don't open.** On Server configuration and Role menu, any officer, Officer-role holders included, can see the name of any channel TaruBot can see when a check names it or a menu role opens it, including channels their own Discord roles don't open, because the "Opens:" list is how they check the officer-channel heuristic.
- **Mod mail's encryption protects against read-only exposure only.** It keeps a leaked dump, the provider's point-in-time recovery or storage, and read access to the database from showing the text. The key sits beside the bot (owner decision 8), so host root or a web code-execution bug (W1) reads every case still held; each backup's settings copy carries the key, encrypted to the same recipients as the dump, so whoever holds the backups' age identity can read the cases in them (the owner's deliberate trade-off, so a lost host restores fully); and a database writer can delete cases, or make itself an officer through the configuration tables and read them on the dashboard; the same writer can end a pause on itself in `member_blocks`, whose trigger refuses edits and deletes by ordinary statements but not by someone who can alter the table.
- **Recovery is bounded.** Restores can lose recent decisions or repeat external effects. Backups in the same provider account are not independent disaster recovery, and the bot's bucket credentials can delete them; keep independent copies. No zero-loss or continuous-availability guarantee is assumed.

A confirmed compromise requires owner response: fence writers, revoke/rotate credentials, assess damage and recover from verified evidence. These limits do not excuse leaks or known vulnerabilities.

## Engineering policy

Prefer GitHub controls, Docker Compose with a standard tag-following updater, PostgreSQL transactions/advisory locks, `pg_dump`/`pg_restore` and age encryption. Custom code must address a concrete requirement these facilities do not meet. Test practical failure behavior with invented data and disposable resources; record owner-run live acceptance separately. Introduce a stronger threat model only for a concrete requirement agreed with the owner.
