# Extending the bot

Commands, gateway events and interaction components are discovered from their own files. Keep routing in `src/bot/`, business operations in `src/application/`, Discord formatting in `src/discord/presenters/`, and I/O adapters in `src/infrastructure/`. `src/main.ts` constructs dependencies and starts the application.

Use the [contributor workflow](../CONTRIBUTING.md), [persistence guide](PERSISTENCE.md) and [threat model](THREAT_MODEL.md) for checks, transactions and security boundaries.

## Discovery and deployment

Default-export `defineCommand`, `defineEvent` or `defineComponent` from a `*.command.ts`, `*.event.ts` or `*.component.ts` file in the corresponding `src/` directory. Discovery is recursive and deterministic; production loads the compiled `.js` files. Duplicate identities, invalid exports and missing services fail startup. `bun run build` removes stale compiled routes.

Command registration and runtime use the same definitions. Managed deliveries register them automatically: globally for production, in DevBot's guild for staging. In a local installation, after a definition changes, use `bun run commands:register --guild ID`, then rebuild/restart execution code. `scripts/commands.ts` also provides command inventory and guild-scope cleanup; see [maintenance-tool profiles](CONFIGURATION.md#maintenance-tool-profiles).

## Maintenance tooling boundaries

Keep tool I/O at the edges and reusable logic in exported functions or `src/`. Discord/database tools use the deployment-identity guard in `src/config/deployment.ts` before I/O. Share existing permission, visibility and inspection helpers instead of duplicating SDK interpretation; `src/domain/permissions.ts` supports checks that deliberately ignore Administrator.

## Permissions

TaruBot's own permissions (2.44.0) are a static catalog in `src/domain/rbac.ts`; `src/domain/permissions.ts` is Discord's permission arithmetic and unrelated. Every gated function checks one permission id at its application operation, through `requirePermission(actor, guildId, id, message?)` or `can(actor, id)` in `src/domain/policy.ts`, against the actor resolved for that interaction or request (`Actor.access`, computed by `Service.enrichActor`). Nothing else decides access: presenters and views only choose wording and detail from it.

- **Tiers.** `fixed` permissions (`admin.*`) change who holds authority: server managers only, never on a role. `staff` permissions are officer work and never sit on Member or Guest, because delegated officers can hand those roles out. `member` permissions are self-service features. `baseline` ones belong to everyone in the server, lobby newcomers included. `accessFor` applies the tier rule again whatever a template says.
- **Who holds them.** A server manager (Manage Server and Manage Roles) holds every permission except the `memberSide` ones, which follow their own Member or Guest role. Otherwise each managed role that counts carries its `TEMPLATES_V1` set: Member, Guest, and the Officer role while TaruBot's rank evidence or a grant backs it. Manage Server alone grants nothing.
- **Refusals.** A fixed permission refuses with scope `manager` (the "Server managers only" card), a staff one with scope `officer` ("Officers only", naming the command, or the throw site's own approved sentence), and a member or baseline one with scope `membership`. The detail names the permission. A pause refuses with scope `blocked` ([Pauses](#pauses)); the rules for who may pause whom refuse with `protected` (a server manager, a bot or, for an officer, someone with staff permissions or a pause a server manager set) and `self` (pausing or lifting your own).
- **Adding one.** Add the id to `PERMISSIONS` with its area, kind, tier and plain-words label, give it to the templates that should carry it, check it at the operation, and update `tests/unit/rbac.test.ts`, which pins the catalog and templates, and `tests/unit/access-parity.test.ts`. Ids are never renamed or reused. A new `member` or `baseline` permission becomes pausable by itself, because `BLOCKABLE` follows the tiers: see [Pauses](#pauses) for what that needs.

### Pauses

A pause (2.45.0) stops one person using one feature, set by `Moderation` (`src/application/moderation.ts`, `moderationKey`, which holds the rules for who may pause whom) and stored in `member_blocks` ([persistence](PERSISTENCE.md#pauses)). It is deny-only: it removes a held permission and adds none.

- **`can` and `holds`.** `Access.permissions` is what the person holds. `Access.blocked` maps the permissions paused now to a `Pause` (`until`, `reason`); `Service.enrichActor` reads it for everyone but server managers (`src/application/blocks.ts`), and `accessFor` keeps only pauses on permissions the person holds and none for a manager. `can(actor, id)` is held and not paused, the question every write asks. `holds(actor, id)` is held, a pause aside: use it where a pause must leave something open, namely admission to a page (`selfServiceAccess`, so a person whose My roles is paused still opens it) and the records a person already has (`mayUse` in `src/domain/modmail.ts`, so someone who can't open cases still reads, answers and closes theirs). `pauseOn` gives a page the pause to show.
- **Refusing.** `requireNotPaused(actor, id)` throws the `blocked` refusal (`pausedFailure`: the permission, the end and the reason, never who set it). `requirePermission` calls it before everything else, so a gated operation reports a pause before any missing-role card. Where a site decides with `can()` itself (`Suggestions.submit`, the ledger's read and deposit, `ModMail.open`, `SelfRoles.choose`), it calls `requireNotPaused` ahead of its own refusal and before its limits and any GitHub, Lodestone or other outside request, so a paused person's try costs nothing and counts against nothing. What comes first is only what has to: each command's own option parsing (`/verify`'s character ID, `/ledger`'s amount), the guild lookup (`Service.guild`, a database read), `Service.ledgerRead`'s stale-control check, the text checks of `IssueReports.user` (the description's length) and `Service.ledger` (the note), `Suggestions.submit`'s allowlist and off switch, `ModMail.open`'s case-ID shape check and `Service.apply`'s input parse. `/claim` checks twice: its command calls `requireNotPaused` after `Service.guild` and before `resolveClaimCharacter`, which may search the Lodestone, and `Service.claim` checks again through `requirePermission`; `Service.verify` and `Synchronization.refresh` check at their top through `requirePermission`, before the Lodestone or the roster. A pause holds for everyone who has the permission, officers included: `Service.ledgerRead` checks `ledger.view` for every reader after the guild lookup and the stale-control check, so a pause on reading the ledger stops an officer whose `ledger.audit` would otherwise open it (only a server manager can pause an officer, and nobody can pause a server manager), and `Service.ledger` checks `ledger.deposit` for a deposit before the setup, Discord and membership checks. Withdrawals, corrections and opening balances are staff permissions, which can't be paused.
- **Before a form opens.** `/modmail` and `/apply` also check in `beforeModal`, which has no resolved actor, so they read the person's active pause with `activeBlocks` and answer with `pausedFormReply` (`src/discord/presenters/failure.ts`) instead of the form, so nobody types into a form that can't be sent. `pausedFormReply` is the card the submission gives, built by the same code, minus the Code and Ref footer: an expected state, not reported. `ModMail.openGate` reads the pause after the refusals that need no pause (no key, no web, a server that isn't set up, not holding Member or Guest, TaruBot holding Administrator) and before the on/off switch and the case limits, and returns `{ paused }` for it; `/apply` reads it after the check that applications are open. Both skip the read for server managers (Manage Server and Manage Roles in the interaction's permissions), who can't be paused. Like every pre-form check it fails open: an error, an invalid result or a read over the budget opens the form, because opening one grants nothing and the submission (`ModMail.open`, `Service.apply`) repeats the check authoritatively.
- **What can be paused.** `BLOCKABLE` in `src/domain/rbac.ts` is every `member` and `baseline` permission, nine today; staff permissions can't be paused yet. `MANAGER_ONLY_BLOCKS` (mod mail opening, owner decision Q6 B) is the part only a server manager sets or lifts. `PAUSE_FEATURES` in `src/domain/moderation.ts` names each in plain words for the cards and chips, and `featuresMatchCatalog` (`tests/unit/moderation.test.ts`) keeps the two equal.
- **Lengths.** `PAUSE_DURATIONS` (`src/domain/moderation.ts`) lists the five lengths. Only `/moderate block` turns an omitted length into the default week; `Moderation.block` itself refuses any value outside the list as an input failure naming `duration`, and never picks a length for its caller.
- **Adding an enforcement site.** For a new function people use: give it a `member` or `baseline` permission; check it with `requirePermission`, or with `can` after `requireNotPaused`, in the application operation and before its limits and any outside request (and in `beforeModal` too, for a command that opens a form); admit pages and a person's own records with `holds` when they must stay open during a pause; add its `PAUSE_FEATURES` entry (a test fails without one, since `BLOCKABLE` follows the tiers); show the paused state on its page, as My roles and Mod mail do; and add a case to the pause tests. Nothing else needs changing: the commands, the Moderation page and the cards read the list.

## Add a command

Use an existing command in the same feature group as the starting point. The module owns its Discord builder, `execute`, optional `autocomplete` and `requires` services. Keep related subcommands under their root command.

The router acknowledges interactions, checks guild/human scope, resolves the actor and viewer, and controls reply visibility and mentions. Commands parse options, call an application operation and return its presenter. Application services independently authorize the operation with `requirePermission` ([permissions](#permissions)). A gated root declares `permissions`, an any-of list the router checks before the handler and for autocomplete; a root with subcommands of different permissions lists each one, and each operation checks its own. A root only server managers may use (`/setup`, `/officer`) also sets the builder's default member permissions, so Discord hides it from everyone else.

Autocomplete cannot defer and may reveal private records, so authorize each focused-option branch. Use `focusedOption()`, the shared `completeMember()` for member inputs, and `choice()` for bounded labels. Member completion values are user IDs, parsed by `userId()` in `src/discord/selectors.ts`; use `selfOnly` where appropriate.

### Present results

Return one `Presented` reply and throw catalog `Failure` values for errors. Put pure presenters in `src/discord/presenters/`, using typed application results and the viewer. Follow [REPLIES.md](REPLIES.md) for formatting, examples, attachments and presenter tests. Handlers do not set `flags` or `allowedMentions`.

### Open a modal

A command may provide a synchronous `modal(interaction)` instead of `execute`; `/apply` and `/modmail` are the current examples. Modal openers are user-access only. Opening a form must be the initial acknowledgement and does no database/network work. An optional fast `beforeModal` availability check is only a courtesy: errors or timeouts still open the form.

Handle submissions in a separate component namespace. Recheck actor/guild bindings, input limits and persisted context in the application operation. Forms can survive restarts; opening one does not create a record or authorize submission.

## Add an event

Use `defineEvent` with a unique handler `id` and a Discord `Events` value. Handler arguments follow `ClientEvents`; several handlers may subscribe to the same event. Filter guild scope and bots before feature work. Use `once` for a one-time listener; shutdown listeners may declare `duringShutdown`.

Delegate stateful decisions and critical deliveries to application services and the durable outbox. The binding layer handles errors and listener cleanup. Additional gateway intents must be configured in `DiscordGateway` and, when privileged, in the developer portal.

## Inject a new service

Reuse tokens from `src/application/keys.ts` where possible. A new capability defines one `ServiceKey` with a provider predicate, is registered through `services.provide()` in the composition root, and is declared in the module's `requires` list. Consumers retrieve it with `services.get()`. Import the same token in provider and consumer; startup validates required services.

## Add a component

Use `defineComponent` with a unique custom-ID `prefix`. Narrow the interaction type before reading fields. Build and parse IDs through `src/discord/custom-ids.ts`: they carry selectors, never authority. Every click resolves a fresh actor and the application operation reauthorizes it.

Replies are the default acknowledgement. Use `acknowledge: "update"` only for a component's own view; the router updates a source only when ephemeral or created for the presser. Ordinary failures leave that view intact and normally become private follow-ups; DevBot's public-response override is an exception. See the existing guest review, ledger pager and verification components for their durable context checks.

Messages outlive deployments. Add grammar/builder/parser tests together; retired actions keep parsing and answering “out of date” for at least one minor release.

## Test a presenter

Add cases to `tests/fixtures/replies/` and pin wording in the group's unit tests. [REPLIES.md](REPLIES.md#add-or-change-a-reply) lists the relevant checks. An intentionally added public command also needs the command inventory expectation updated.

## Web pages

The web pages (#43) run in the bot process: `src/main.ts` starts a second listener once the writer lease and Discord are ready, and the shutdown drain stops it. They stay off until `WEB_PUBLIC_ORIGIN` is set. `src/web/settings.ts` parses the web settings when the web starts, so a bad value turns the web off with a report naming the setting and never stops the bot. `src/main.ts` runs the same parse once before Discord connects, for the dashboard's address: `/dashboard` reads it through `dashboardKey` (commands never import web code), and the gateway's client option `presence` carries it as the custom status (`dashboardPresence`), which discord.js sends with every IDENTIFY. Off or invalid settings give neither. `src/web/http.ts` holds the header set and the POST checks; `src/web/server.ts` owns the fixed routes (`/`, sign-in, sign-out, `/health/ready`, the public `/status` and the assets) and wires the request pipeline.

### Add a page

Default-export `definePage` from a `*.page.ts` file under `src/web/pages/`. The path is `/g/:guild/` followed by lowercase segments, optionally ending in one `/:number` (2.43.0, mod mail's case pages): server.ts answers 404 for anything but a positive whole number before the page runs, hands it over as `context.number`, and such a page can't be in the navigation; `Page.href(guild, number)` fills both. `access` is required, with no default, so no page is public by omission. It's an any-of list of [permission](#permissions) ids (`admits` in `src/web/access.ts`). A member-tier permission (`selfroles.use`, `modmail.open`) also needs `botAdministrator === false` unless the actor is staff (`isStaff`): members and guests are refused while TaruBot holds Administrator in the server, and an uncached TaruBot member counts as holding it (owner decision A2). `selfServiceAccess` in `src/domain/policy.ts` is the same rule for application operations. Nothing in admission reads `timedOut`: a member in a Discord time-out may view, and the operation refuses the write. `requires` lists service keys, checked when the web starts; a missing one keeps the web off. A page reaches only those: `context.services.get()` throws "Page used an undeclared service" for any other key, which shows as a reported 500, so a bug in one page can't reach a service it never declared. A page with a `post` handler must also declare `postLimit`, its budget of POSTs per user and server in each ten-minute window, and `definePage` refuses one without it (or a `postLimit` without `post`). `nav` lists the page in the server navigation for viewers it admits, and the optional `icon` names its decorative navigation icon from `src/web/icons.ts`. An optional `navWhen(actor, services)` can hide that link from some of them (Mod mail's from members and guests while it is off): it gets the page's own scoped services, only ever hides a link (a failure, thrown or rejected, hides it too), and never closes the page, which still opens for anyone `access` admits. `freshActor: true` makes every GET resolve the actor afresh (light), never from the memo, for pages whose content a removed or demoted officer must lose at once. `recentSignIn: true` (with `post` only, 2.45.0) makes every POST need a Discord sign-in within `RECENT_SIGN_IN_MS` (15 minutes, `src/web/sessions.ts`), for pages that restrict other people, such as Moderation. `Session.recentSignIn` is judged on the database clock in the session read, like every session expiry; `servePage` answers a stale POST with a 303 to the page itself (after the memo refusal, before the budget and actor costs), and nothing of the form is kept; a redirect from the form through `/login` to Discord would be one form-submission navigation, which the page's `form-action 'self'` blocks in Chromium. So the page's GET reads `context.recentSignIn` and, when it is false, shows "Sign in again to make changes" as a plain link in place of its change controls. `bodyLimit` (with `post` only, above 64 KiB and at most 256 KiB) raises that page's own POST body cap, sized for the worst case of its fields' `maxlength` (9 bytes per UTF-16 unit urlencoded), so text a browser lets through reaches `post()` for a 422 that keeps it; mod mail's pages take 96 KiB, and Bun's listener cap is the largest page's. A numbered page marks the page it sits under as current.

The server refuses before the page runs: a malformed or unserved server, or someone who isn't a current member, gets 404, a signed-out visitor goes to sign-in, and a missing flag gets 403. `servePage` in `src/web/server.ts` has the exact order.

The actor is resolved as for a slash command, in one of two modes (`ActorResolution`, `gateway.actor()`). A GET reuses it for up to 60 seconds, and on a miss resolves it **light**: the server and its roles from the gateway cache, which the Guilds intent keeps current, and only the member fetched, one Discord request instead of three; a server that isn't cached and available falls back to full. Sign-in admission resolves light and fresh for each candidate server. Every POST resolves **full** and fresh, as commands do. Application operations authorize it again.

`get` loads a typed view model through `context.services`, and a pure function in `src/web/views/` renders it, as presenters do for Discord. Views import application, infrastructure, Drizzle and job modules as types only. Templates use `html` from `src/web/html.ts`, which escapes every interpolation:

- untrusted text (server, member and role names, notes) goes through `untrusted()`, links through `href()`, and times through `time()` (UTC);
- never write a `style=` attribute or a script: the CSP allows neither;
- the unescaped `raw()` is allowed only in constant files that `tests/unit/web-boundary.test.ts` allow-lists.

Throw catalog `Failure` values. The error page maps the category to a status and shows the approved message with its code and ref; anything else is a 500 that shows neither its text nor its stack.

### Dashboard data and presentation

Server configuration and Background work are read-only; [Role menu](#role-menu), [My roles](#my-roles), [Mod mail](#mod-mail) and [Moderation](#moderation) write. `/g/:guild/configuration` uses `Service.validate()` and the same `configurationChecks()` checklist as Discord. Validation is single-flight per application service and server, with successful results reused for 30 seconds from completion. Every lookup, including a memo hit, reauthorizes the officer; rejected checks are not retained. The page prints the check's actual UTC completion time.

`/g/:guild/status` is labelled **Background work** in navigation. Its process health keeps only readiness, Discord, database and the Lodestone cooldown state. It shows up to 10 recent refresh runs and 25 outstanding jobs from `syncStatus()`, with counts explicitly limited to the displayed sample, not server-wide or global totals. Native `<details>` disclose officer diagnostics without scripts; arbitrary job payloads and process-wide diagnostics are not rendered.

A server page is a console: from 64rem a sidebar holds the wordmark, the server switcher (a link back to the server list, and the only place the server's name appears), the page navigation and the account menu, beside a top bar; on narrower screens they form a sticky bar with the navigation as a strip under it. Sign-in, the server list, no access and errors are entry pages over a decorative starfield. Each server page has one featured card. On Configuration it is the health snapshot, which counts the checks and links to the full checklist, followed by six settings cards; a long checklist group folds into a disclosure only when every check in it passed. On Background work it is process health, followed by the sample counts and the work and run tables, each in its own focusable scroll region with native diagnostic disclosures; below 48rem each job and run stacks into a card instead, still marked up as the same table with explicit roles.

`src/web/mentions.ts` snapshots names from this server's gateway cache at render time, never stores them, and turns Discord mentions and timestamps into escaped, isolated text and UTC `<time>` elements. Uncached names fall back to IDs; obfuscated or permission-denied channels never expose cached names. Every page declares `gatewayKey` alongside its data services.

Both web surfaces are TaruBot's port of the Orrery design system export, dark only; the export itself is not in the repository. `site/src/styles/tokens.css` is the one token source, and `src/web/styles/tokens.ts` carries its exact text. `assets.ts` assembles the dashboard stylesheet from `src/web/styles/` (tokens, the ported base, effects, components and form controls, the console and entry frames, each view's rules, then reduced motion, reduced transparency, forced colors and print) and serves it with the favicon, the fonts and the third-party notices at hashed `/assets/` paths. The ambient loops (holographic edge and drift, starfield twinkle, orbit rings) keep looping with no pause control, since the owner accepted the WCAG 2.2.2 finding on 2026-10-08; `prefers-reduced-motion` stops every loop on both surfaces. The fonts are Sora for headings and the wordmark, Manrope for text and JetBrains Mono for labels, timestamps and code, the latin subsets from Fontsource, in `site/src/assets/fonts/`; after changing one, regenerate `src/web/fonts.ts` with `bun --no-env-file scripts/web-fonts.ts`. Icons are Lucide path data inlined as constants in `src/web/icons.ts`. `src/web/notices.ts` copies `site/public/third-party-licenses.txt`, which every dashboard footer links. `tests/unit/web-parity.test.ts` keeps the tokens, favicon, notices and fonts identical on both surfaces. The CSP admits styles, fonts and images from the dashboard's own origin only, and no script or inline style, so a page makes no third-party request.

### Forms

`post` runs only after, in this order: the same-origin and form-type checks and the session; the server checks; the session's form token; the shutdown check; a refusal from the actor memo; for a page that declares `recentSignIn`, the sign-in's age (a stale one gets a 303 to the page itself, not to `/login`; see [Moderation](#moderation)); the page's `postLimit`; and a fresh actor that the page's flags admit. None of the checks before the actor costs a Discord request. The memo check (`AccessResolver.peek`) only refuses: when the memo already holds an answer this page wouldn't admit, the POST gets that answer's 404 or 403 at once, so someone hammering a page they can't use, such as a member on Role menu, costs at most one full resolution a minute. Anything else goes on to the full resolution. `servePage` in `src/web/server.ts` has the exact order.

- **Form token.** Every POST form carries the session's form token in the hidden `form_token` field (`FORM_TOKEN_FIELD`). It's an HMAC-SHA-256 keyed with the session cookie's token (`formToken` in `src/web/sessions.ts`), so it needs no storage and no new secret, a database reader can't derive it, and a new sign-in rotates it. The server compares it in constant time (`formTokenMatches`) and answers 403 on a mismatch, then removes the field from the form `post` receives. It's defense in depth behind the same-origin check. The account menu's two sign-out forms carry it too: signed in, a sign-out without it ends no session.
- **Shutdown and budgets.** Once shutdown starts, a POST gets `stoppingRefusal()` from `src/web/limits.ts` (429, Retry-After 30). Over the page's `postLimit`, it gets a 429 with Retry-After. Budgets are fixed ten-minute windows counted in memory per page, server and Discord user, never by address. A POST refused by the token, shutdown, memo or budget check isn't counted; one refused later, by the actor check or the page, is.
- **Render with the form kit.** `src/web/views/forms.ts` holds pure helpers. `postForm` opens every form, with the token first and a same-origin action. Fields come from `textField`, `numberField`, `selectField`, `choiceGroup` and `hidden`; feedback from `errorSummary` and `notice`; actions from `submitButton` and `formActions`. Put a danger button only inside a `disclosure`, and use `context` for the visually hidden suffix that keeps repeated control names unique. Labels, hints and error messages take plain text or `SafeHtml`, such as `mentionText` output. `src/web/styles/forms.ts` gives inputs real borders under the base outline focus, keeps checkboxes and radios native, and makes the action row sticky on phones.
- **Answer with a `PostOutcome`.** Parse the form with zod, call one application operation, and return either of two outcomes. `{ redirect }` answers 303 through `safeReturnPath`, normally to `noticeLocation(path, token)` with a token from the page's fixed notice table; `notice()` ignores any other token, so a URL can't put text on the page. A page may add its own parameters, such as the Role menu's `category`, which it only compares with its own data to place the notice, never shows. `{ invalid, status }` re-renders the page's content with the submitted values kept, escaped, and an error summary: 422 for refused input (the default), 409 when valid input met a changed state. A 409 keeps only the values the user changed from what the form showed (the Role menu's `was:` fields), so resubmitting it can't put back someone else's change in a field the user never touched. A re-render that draws the refused form open over the page, its own blocks inert under it (the Role menu's editors), also sets `modal: true`, and the layout makes the shell inert too, so only that form takes focus. The layout then prefixes the title with "Error: ". Messages never echo submitted text. Throw catalog `Failure` values for refusals that end the request (403, 429, 503); the error page shows them, with a link back to the page, since reloading the answer to a POST would send the same form again.
- **One transaction per write.** The application operation authorizes the actor again, makes any Discord reads first and never inside the transaction, then locks, compares, writes and audits in one transaction. Just before it commits it checks for shutdown again and throws `stoppingRefusal()`'s failure, so a write that began just before the drain rolls back. Web handlers never write to Discord: Discord effects belong to the job worker. `SelfRoles.edit` is the example of an audited officer write, and `SelfRoles.choose` of a member's save that queues a job.
- **Idempotency by state.** A write whose result equals the current state succeeds without writing, whatever revision the form carried, so a double submit lands on the same 303. A create carries an ID its GET minted, so a repeat finds the existing record. Otherwise a stale revision is a 409 re-render. Forms name records by ID and moves name an absolute position, never an index or a direction.
- **Audit.** Officer changes are audited. Member self-service keeps Discord as the record of what someone chose and is delivered through durable jobs, with no audit row per save, as the `/main` and `/nickname` preferences (`Service.preferences`) already do.
- **Jobs.** A page that enqueues work follows these rules for its job kind: carry `guild_id`; validate the payload before `enqueue()`; use a per-action dedupe key; use the `reconcile.` prefix only when generation fencing is intended; add a `JOB_KIND` label. Pages then say "queued", never "done".

### Role menu

`/g/:guild/role-menu` lets officers edit the server's self-service role menu through `SelfRoles` (`selfRolesKey`, `src/application/self-roles.ts`). The menu is one versioned JSON document per server ([persistence](PERSISTENCE.md#self-service-role-menus)). `src/domain/self-roles.ts` holds its schema and caps, every edit as a pure function from one menu to the next, and `selfRoleChecker`, the one rule set for what may be self-assigned. The page renders through `src/web/views/role-menu.ts` and declares `selfRolesKey` and `gatewayKey`.

- **Who.** Any officer may make every change, adding roles and resetting an unreadable menu included. There's no Discord Manage Roles requirement and no check of the officer's own role position (owner decision of 2026-10-09). The rule set and TaruBot's own role position are the whole safety boundary, so loosening a rule needs the owner's agreement.
- **The rule set.** A self-service role:
  - is an ordinary role TaruBot can assign: it exists, isn't @everyone, managed or TaruBot's own, sits below TaruBot's highest role, and TaruBot has Manage Roles;
  - is never a bound or retired access role;
  - sits below the bound Officer and FC Leader roles and below every role under TaruBot holding Kick Members, Ban Members, Time Out Members, Manage Nicknames or Administrator, managed bot roles included (`above_staff`; the owner's "Refuse them", 2026-10-09). Discord lets those powers reach only members whose highest role is lower, so a menu role above one would put everyone who picks it out of that role's reach. TaruBot's own managed role is left out, since TaruBot is its only holder and its reach comes from its highest role; any other role TaruBot holds still counts, since people can hold it too. Tied raw positions follow Discord's order, as for TaruBot's own role. The message names only the powers the role it names holds. This rule doesn't block removal;
  - holds no server permission @everyone lacks, and never Administrator, Manage Server, Manage Roles or Manage Channels;
  - gains nothing in a readable channel that any of three audiences already sees: @everyone, @everyone with the Member role, and @everyone with the Guest role. The Member and Guest baselines matter: a Send Messages allow in a members-only announcements channel would otherwise let every member post there;
  - allows, in its own overwrite in any readable channel, only bits @everyone holds server-wide, View Channel aside, because its holders may see that channel through a role the check can't know about (otherwise a Manage Messages allow would make everyone who picks it a moderator there);
  - lifts, with that allow, no deny another role's overwrite sets in the channel, View Channel included, and no @everyone deny in a channel it doesn't open (`channel_deny`). Discord lets any role's allow beat every role's deny, so a Send Messages allow would otherwise undo a mute role, a View Channel allow a jail or quarantine role, or let people who see a read-only channel through an officer-assigned role post there. In a channel the role opens, two lifts are what opening means and stay allowed: @everyone's deny (an opt-in channel) and the View Channel bit of the Member and Guest roles' deny (an opt-in channel in a server private by default). Any other role's View Channel deny there, such as a jail role's, still refuses the role;
  - takes nothing away from the people who hold it (`restricts`): no deny in its own overwrite in a readable channel it doesn't open, and nothing lost by any of the three audiences in a channel it already sees. A self-service role's holders can remove it, so a mute, jail or quarantine role on the menu could be removed by the very people it restricts. A deny in a channel the role opens only shapes that channel, so it stays allowed. This rule blocks removal too, so even under Not offered or Stop offering nobody removes such a role themselves. So a role that passes every rule changes nothing in a readable channel it doesn't open: it grants nothing there, lifts no deny and takes nothing away;
  - may open a channel none of those audiences sees, carrying no more than that audience holds server-wide (View Channel aside, so opt-in channels work where @everyone lacks it server-wide), unless the channel looks officer-facing. Seeing a channel is judged only as opening it.

  Channels TaruBot can't read are outside every channel rule: their real overwrites, the role's own included, aren't in the snapshot. An add needs the officer's confirmation that the roles neither open them nor give any permission in them.

  The channel rules judge the role's overwrites with its server bits capped at @everyone's, because any excess is already reported once server-wide. Problem messages name roles and channels in Discord's mention grammar; render them with `mentionText`.
- **Officer-facing is a heuristic.** A channel counts as officer-facing when a setting names it for officers (the officer room, officer notifications, guest reviews, or onboarding's staff-only channels), or when none of the three audiences sees it and its View Channel allows include the Officer or FC Leader role or a role with a staff power. Two shapes are missed: a private channel that only Administrators see, with no allow at all, and a private channel opened to officers through per-member entries rather than a role, such as an officer room built from each officer's own entry or a ticket-style channel. So the page lists every channel each role opens, officers read **Opens:**, and an add needs the officer's confirmation while TaruBot can't read some channels.
- **Where it runs.** The page GET judges every role on the gateway cache, with no Discord request. Each add reads a fresh snapshot (two requests) before its transaction and judges the added roles again under the locks. The "Role menu" health check in `Service.validate()` uses the snapshot that method already reads.
- **The invariant.** A menu role is never one of the four bound access roles or a retired role, or reconciliation would add it to everyone or strip it from everyone who picked it. A menu add checks it under the guild row lock. `Service.configure()` and `/setup onboarding` refuse a menu role under their `FOR UPDATE` (`assertNotOnMenu`, `rolesOnMenu`), and `planSetup` lists it as a blocker. `/setup onboarding` also checks the roles it would reuse, decided read-only as the dry run decides them, before `ensureRole` creates or renames any role. A menu this build can't parse is scanned for role IDs, so the check fails closed.
- **An unreadable menu.** A stored document that doesn't parse, for example one a newer release wrote before a rollback, is never edited. Every edit but **Reset role menu** is a 409, and the reset is audited like any other edit. A reset of a menu that reads fine is a 409 too, since it would wipe every category at once; a repeat after a reset meets the empty menu and succeeds without a write. The scan that keeps an unreadable menu's roles from being bound reads every string in the document, object keys included.
- **Members' choices** are picked on [My roles](#my-roles) and applied by the `roles.self` job.

### My roles

`/g/:guild/my-roles` lets members, guests and officers pick their own roles from the published menu (`access` `selfroles.use`; `requires` `selfRolesKey` only; `postLimit` 10). It renders through `src/web/views/my-roles.ts` and needs no gateway service: `SelfRoles.view` returns the menu roles' cached names (`MyRoles.roleNames`) with everything else.

- **View.** `SelfRoles.view` reads only the database and the gateway caches: the menu, the cached snapshot judged with `selfRoleChecker`, the member's cached roles (`DiscordPort.cachedRoles`, which `GuildMemberUpdate` keeps current, so a job's echo shows at once), and the newest `roles.self` row, whose waiting payload it overlays. `choiceMenu` in the domain decides each row: changeable (addable and passing, or held and removable), held but unchangeable (a text line), or hidden. A pick-one category with several roles held preselects none. Ticks follow the waiting change, and a row it ticks differently from what is held is badged "Waiting to add" or "Waiting to remove"; notes never say "You have" of a role that isn't held. A published category whose held, unchangeable roles already fill its limit, with nothing changeable ticked, renders as text, since no input there could do anything. Removal-only categories show only to holders; drafts reach officers only, disabled and never submitted. With no category to show, `MyRoles.offers` tells a menu whose roles all fail a rule now ("There are no roles to pick here right now") from one with nothing published. Banners about a change that ended unapplied or incomplete carry its `completedAt` as a UTC `<time>`.
- **Save.** The form sends `shown` (each enabled category), `seen:<id>` (each value ticked at render, `""` for a preselected None) and `c-<id>` (the picks). `SelfRoles.choose` reauthorizes with `selfServiceAccess` and refuses a timed-out actor, paused effects, an unreadable server and a missing setup. `changedCategories` keeps only the categories whose picks differ from what was shown, so a stale tab, another bot or an officer's hand edit is never undone in a category the person didn't touch: a value the menu no longer allows there is a 409 re-render, too many picks or a role that now fails a rule a 422. The transaction locks `self-roles:<guild>:<user>`, merges into the waiting change by category (`mergeChoice`: a changed category replaces everything the waiting change asked there, roles the page hid included), applies the equal-state rule and enqueues ([persistence](PERSISTENCE.md#self-service-role-menus)). No audit row is written. Outcomes are `saved` (303 to `#status`), `unchanged` (303 with `notice=unchanged`), `conflict` (409) and `invalid` (422).
- **Apply.** The dispatcher completes a cleared `{}` payload as `nothing to apply` before the effects gate, parks paused work as `disabled`, then calls `RoleChoiceJob.apply` before any delivery bookkeeping, so the job never writes `delivery_attempts`. `RoleChoiceJob` is a separate class that only the dispatcher constructs and no service key provides: it writes any member's roles from the job it is given, so it stays out of `SelfRoles`, which My roles can reach. `apply` takes `reconcile.user`'s `user:<guild>:<user>` lock (busy waits without spending an attempt), reads the member, plans with `planSelfRoles` against the current menu (only `offered` roles still listed, never a bound or retired role, an over-limit category skipped whole), re-checks every role on a fresh snapshot, and writes through `DiscordPort.selfRoles`: one role per request, with an audit-log reason. Unknown Role (10011) is skipped; Missing Permissions (50013) re-reads TaruBot's member and is skipped while it still has Manage Roles, otherwise the job is blocked with a role-free diagnostic. Results are counts: `{status: "applied", added, removed, skipped}`.
- **Access loss (owner decision Q3 B).** When `Synchronization.user` leaves someone with none of Member, Guest, Officer and FC Leader, in a server that binds Member or Guest, `accessLossRoles` lists the held, listed, removable menu roles that open a channel, and the pass removes them with a separate `selfRoles` call after the access change, so they can never block it. Its result and the preview record only a count, `selfRoles`. `apply` likewise skips adding a channel-opening role to someone with none of those roles. Cosmetic roles and drafts are never touched.
- **Privacy.** Role IDs a member chose may appear only in the waiting payload, which migration 012's trigger clears when the job ends. They never reach job results, diagnostics, logs, audit rows, issue reports or officer views: `Service.syncStatus` leaves out the user of someone else's role choices, `Service.guestStatus` leaves `roles.self` rows out of every record, and problem messages that name roles stay on the person's own 422. `IssueReports` leaves `roles.self` rows out of a report's member section, the member's own `/issue` included, so a report shows one only in its queue tables, by kind; an automatic report of a failed one (`jobFailed`) names no member, so it has no member section. Tests scan for `<@&` and every menu role ID.

### Mod mail

Mod mail (2.43.0, issue #60) lets members and guests reach their server's officers privately. Discord's only part is opening a case: `/modmail` (`src/commands/utility/modmail.command.ts`) opens a form whose text arrives with the interaction, so no message intent is needed, and the `modmail` component handles its submission. The Mod mail page opens cases too, with the same `ModMail.open`. The conversation then happens on two pages, both `access` `modmail.inbox` and `modmail.open` and `requires` `modmailKey` only, so every member reaches no other service through them:

- `/g/:guild/modmail` (`modmail.page.ts`): officers get the inbox (`ModMail.inbox`: waiting on officers first, oldest waiting first, filtered by state through the `state` query value, at most 100 rows) beside the on/off card (`ModMail.settings` and `toggle`, the one audited mod mail write); everyone else gets their own cases (`ModMail.mine`) and **Open a case** (`op=open`: the topic, the message and a case ID minted with the page, so the same form sent twice lands on the case it made; refused text is 422 and a refusal the page didn't foresee or a minted ID naming someone else's case is 409, both drawn open over the page with what was typed, `PostOutcome.modal`). The form opens in a modal `<dialog>` anchored to its button, the Role menu's overlay (invoker commands, a popover fallback, one static anchor class pair, a bottom sheet on a phone), and `MyCases.openRefusal` disables the button with the reason when the member can't open one. Officers keep the inbox and `/modmail`; their view has no such form, and a forged one is refused as out of date. Its `navWhen` lists it to officers always and to members and guests while mod mail is on. Listing a case's decrypted topic records a `list` read. `postLimit` 20.
- `/g/:guild/modmail/:number` (`modmail-case.page.ts`): the thread with a reply form (`reply`: a minted message ID, so a double submit lands on the same message, and for officers the signing radios), Close (inside a disclosure) and, for officers, Reopen and the folded read log. A case that doesn't exist or isn't the viewer's is `pageNotFound()`, the same 404 as an unknown path, never a 403. `postLimit` 40.

Both declare `freshActor`, so every request, GET included, resolves the viewer afresh instead of from the minute-long memo: an officer removed or demoted loses them at once. Both render through `src/web/views/modmail.ts` and `src/web/styles/modmail.ts`. `ModMail` (`src/application/modmail.ts`) authorizes every call again with the domain's rules (`src/domain/modmail.ts`: `mayOpen`, `mayAccess`, `sideIn`, `shownAuthor`, the limits and the fixed sentences), records a read on every case view, decrypts in memory for the render only, and resolves display names when it renders through `DiscordPort.displayNames` (the gateway cache, then at most five member fetches; someone gone is null, "A former member" or "A former officer", and is remembered as gone for ten minutes so a reloaded page doesn't ask Discord again). The member's view model never holds who wrote a reply signed as the officers. A field the current key can't decrypt shows `UNREADABLE_TEXT` and reports once per view with a fixed message.

- **Opening.** `ModMail.open` is the one path for both forms, so the rules can't drift: Member or Guest now, no Administrator for TaruBot (A2), mod mail on, a valid key, the web, the limits and the text's lengths, checked for the fresh actor, the switch and limits inside its transaction under the member's lock, so a web form and `/modmail` at once can't both pass the open limit ([persistence](PERSISTENCE.md#mod-mail)). `/modmail`'s `beforeModal` (`ModMail.openGate`) refuses plainly first, with no Code or Ref, from the interaction's role IDs and TaruBot's own channel permissions plus two quick reads; the page's courtesy is `MyCases.openRefusal`. A member in a Discord time-out may open and answer cases, unlike a My roles save, since mod mail is how they reach officers: Discord takes Use Application Commands away during a time-out, so for them that's the page's form.
- **Notifications.** `ModMailNotices` sends the `modmail.ping` and `modmail.dm` jobs; like `RoleChoiceJob` only the dispatcher builds it and no service key provides it. Before the effects gate a job completes as skipped when its case is gone, a ping has no officer notifications channel, or the member has already viewed the case since the officers' latest reply or close; paused Discord changes then park the rest. A ping posts a case number, the event and a link, and the gateway adds the one mention it may carry, the Officer role (`allowedMentions.roles`, never the guild ID, so never @everyone), so presenters still never ping; a DM names the case number and the server. The mention notifies only when the role is mentionable or TaruBot has Mention Everyone in the officer notifications channel: an allow there that officers set by hand, on the TaruBot role's entry (owner decision of 2026-10-11; TaruBot never grants itself a permission). Onboarding's channel pass (`src/discord/guild-access.ts`) writes entry by entry, `PUT` or `DELETE /channels/{id}/permissions/{target}` for the entries that change only (`overwriteWrites` in `src/domain/channel-access.ts`: TaruBot's own entry first, then restrictive meets, then openings, so no state in between is more open than before or after), so that allow is never resent, and a 50013 on a write is a named refusal; the readback still checks the channel settled. `officerPing` in `src/domain/visibility.ts` judges it for the settings card and `/config validate` (a warning, never a prerequisite), and the same analysis reports Mention Everyone allowed to TaruBot in any other channel, or there while mod mail is off, as not needed (`VisibilityReport.mentions`; server-wide grants stay in `neverNeeded`). Closed DMs end the job as `dm_blocked`, never retried.
- **Encryption** lives in `src/infrastructure/modmail/cipher.ts` (padding, the identity-bound AAD, the key ID); main.ts reads `MODMAIL_KEY` once, deletes it from `process.env`, keeps it out of the configuration and hands the cipher to `ModMail` only.
- **Retention** is `ModMailRetention`, on its own timer under the writer lease, stopped by the drain.
- **Privacy in Discord**: `/modmail` and its form component declare `alwaysPrivate`, so their replies stay ephemeral even under DevBot's public-response override.

### Moderation

Moderation (2.45.0) is `/g/:guild/moderation` (`moderation.page.ts`, rendered by `src/web/views/moderation.ts`), the first page to declare `recentSignIn`. `access` is `moderation.view`, `requires` is `moderationKey` only, `postLimit` is 30, and it declares `freshActor`: the pause reasons and the suggestion-sender lookup are private, so someone who loses the permission loses the page on their next request. `Moderation` (`src/application/moderation.ts`) holds every rule, and the page only reads forms and shows what it answers ([persistence](PERSISTENCE.md#pauses), [permissions](#pauses)).

- **GET.** `Moderation.overview` gives the active pauses (at most 200, with `truncated`) and the newest 25 ended; `Moderation.names` adds display names from the gateway cache, which fall back to IDs. The finder is a GET (`?find=`), so a lookup needs no recent sign-in: an ID or a mention reads `Moderation.status`, and `#N` reads `Moderation.senderOfSuggestion` and then the sender's status. Controls follow `moderation.block`; with an older sign-in (`PageContext.recentSignIn`) the page shows "Sign in again to make changes" instead of them. Who set a pause, and who lifted one, is shown only for other people's pauses: a viewer's own rows are built with `view(row, officer)` and `officer` false (an officer can be paused too, by a server manager), and their own ended pauses are left out of the ended list in SQL (`ne(user_id, viewer)`), the same view `Moderation.status` gives for oneself, so the 25 are other people's.
- **The sign-in gate, precisely.** A POST to a page that declares `recentSignIn`, from a session whose sign-in is over `RECENT_SIGN_IN_MS` (15 minutes) old, is answered with a **same-origin 303 to the page itself** (step 6a in `servePage`), after the memo refusal and before the budget and the actor, and the form is not kept. The page's GET then shows "Sign in again to make changes" as a plain link to `/login` with the page as its return path; the callback rotates in a session with a fresh sign-in time. The POST is deliberately not redirected to `/login`: that chain would be a form-submission navigation through to discord.com, which the page's CSP `form-action 'self'` blocks in Chromium (verified), so the click would silently do nothing; a link is not governed by `form-action`. `/login` uses Discord's `prompt=none`, so for a browser still signed in to Discord the re-sign-in is silent. The gate stops a copied or replayed TaruBot session cookie, whose holder's browser has no Discord session as that person, from making changes once its owner's last sign-in is over 15 minutes old; a cookie copied inside that window works until it closes. It does not defend an unlocked browser that is still signed in to Discord, and it covers changes only: reading pauses and looking up suggestion senders are GETs ([threat model](THREAT_MODEL.md)).
- **POST.** `op=block` takes the member (an ID or mention), the features ticked, the length and the reason; `op=lift` takes a chip's member and feature, and a reason. A refusal about the input or the person (no reason, nothing ticked, yourself, a server manager, someone TaruBot has never seen) is a 422 with the form drawn open over the page, in fixed wording that never quotes typed text; a refusal about the actor ends the request; hidden fields the page never rendered are refused whole as out of date, a length outside `PAUSE_DURATIONS` among them, before `Moderation.block` is called. Success is a 303 back with a fixed notice token and the person as `find`.

### Public status page

`/status` (2.41.0) is the one page anyone may open without signing in (owner decisions of 2026-10-09; the [threat model](THREAT_MODEL.md) records why it keeps W1). It's a fixed route in `src/web/server.ts`, not a discovered page: those are server pages behind `access`. The route mounts no session middleware, so the cookie isn't read; takes no input (the query string is ignored); renders no form and sets no cookie. One global `RateLimiter` budget (`STATUS_LIMIT`, 600 a minute, keyed by nothing personal) refuses a flood with a 429 and Retry-After before anything else; its refusals log at debug, and the route logs one info line when a run of them begins. The answer is `public, max-age=30`, with the usual header set (`noindex` included) and CSP.

- **The snapshot.** `PublicStatus` (`src/application/public-status.ts`, `publicStatusKey`, which `startWeb` requires) keeps a `StatusSnapshot` in memory. `main.ts` starts it once TaruBot is ready, with or without the web, and the shutdown drain stops it. Every minute an unref'd timer reads readiness from `ApplicationLifecycle.status()`, the Lodestone's cooldown and reachability from its client, and whether Discord changes are paused from one query (`changesPausedAnywhere`: `ENABLE_EFFECTS` off, or an active, served server with `effects_enabled` false; a boolean, never which server). A failing query keeps its last answer. The route renders the layout once per snapshot and serves the cached text, so a visit makes no database query or Discord request.
- **The rule** (`overallStatus` in `src/domain/uptime.ts`): Down when not ready (or Discord or the database is down); Degraded when the Lodestone's latest request went unanswered; Operational otherwise. A Lodestone cooldown shows on its component only, and so do paused Discord changes: `ENABLE_EFFECTS` off (the default, which saves decisions and holds the changes) or a server awaiting activation is a deliberate setting, not a fault, so its tile reads "[WAIT] Paused by a setting" and the headline is untouched.
- **The history.** In each five-minute bucket, while the process holds the writer lease, the timer writes one sample, deletes those older than 90 days but the earliest, and recounts ([persistence](PERSISTENCE.md#status-samples)). `uptimeHistory` turns the counts into 90 UTC days: ready samples over expected ones, expected from the first sample ever (earlier days have no data; pruning keeps that sample, so an outage at the window's oldest edge still reads as down) to the later of the bucket last written and the latest bucket that has wholly passed. Every snapshot works the days out afresh from the counts in memory, so a bucket that passes without a sample counts as down at once, through a database outage and across midnight, with no query. Store trouble is reported once per streak at warn and retried on the next tick. `uptimePercent` floors hundredths in integers, so 57 of 100 reads 57.00%, not 56.99%.
- **The page.** `src/web/views/public-status.ts` renders an entry page: the overall card beside a 2×2 grid of components, then the history. The overall card's section is named "Right now" plus its word, and its uptime fact names the same span as the summary ("Uptime, 90 days" only once all 90 have data). The 90 bars are spans with one class per band (`uptimeBand`: 100%, at least 99%, at least 95%, below, no data) and no style attribute, inside a `role="img"` with a short name (the summary sentence above it gives the figures). Each band has a height as well as a color (full, about 80%, 55% and 30%; no data an empty outline), and so do the legend's swatches, so the bars read without telling colors apart; under forced colors they take the system's text color. A `<details>` table lists every day below 100%, newest first, with its time down and versions. Phones show the last 30 bars, and the components fall to one column where two 10rem tiles don't fit. Every layout's footer, and the sign-in card, link it.
- **The offline page.** When Caddy gets no complete answer from the bot (stopped, restarting, crashed, or the connection dropped, as for a request body over 64 KiB), bundled Caddy answers `ops/offline/index.html` instead (a 503, `no-store`, `Retry-After`, always the whole page: the conditional and range headers are dropped first), with its files under `/_offline/` and dotfiles hidden; see the [site's monitoring guide](../site/src/content/docs/deploy/monitoring.md#offline-page). Caddy follows symlinks, so the folder holds regular files only. `tests/unit/offline-page.test.ts` pins the Caddyfile, the page and the folder's file types, and `web-parity.test.ts` its copied tokens, fonts and notices. The managed deploy entry makes the folder readable to Caddy, as it does the Caddyfile (`tests/unit/deploy-script.test.ts`).

### Sign-in

`/auth/callback` checks `state` before any Discord request. `DiscordSignIn.finish` runs the token exchange and `/users/@me` inside an `ExchangeGate` (`src/web/limits.ts`): 30 exchanges a minute across all users, 4 at once, and after a Discord 429 every callback is refused locally until its Retry-After passes, so a flood can't earn the bot's egress address Discord's invalid-request ban. Its refusal is a 503 with Retry-After. Once Discord has returned the user ID, a per-user limit of 10 sign-ins in 10 minutes applies before admission (429, no session, the browser's existing session untouched). Admission lists only servers whose pages admit the user, resolving the actor light and fresh for each, and creates no session when none does. `PgSessions.create` keeps at most `SESSIONS_PER_USER` (10) live sessions per user, in one transaction under a per-user advisory lock. Every limit is counted in memory by Discord user ID or globally, never by address. `/` answers 303 straight to the page when exactly one server is listed with exactly one navigation page.

For a preview from another machine, `--host` selects the VM's LAN interface and `--cert` / `--key` supply its TLS certificate and key. mkdir -p .cache/web-preview
openssl req -x509 -newkey rsa:2048 -noenc \
  -keyout .cache/web-preview/key.pem -out .cache/web-preview/cert.pem \
