# Extending the bot

Commands, gateway events and interaction components are discovered from their own files. Keep routing in `src/bot/`, business operations in `src/application/`, Discord formatting in `src/discord/presenters/`, and I/O adapters in `src/infrastructure/`. `src/main.ts` constructs dependencies and starts the application.

Use the [contributor workflow](../CONTRIBUTING.md), [persistence guide](PERSISTENCE.md) and [threat model](THREAT_MODEL.md) for checks, transactions and security boundaries.

## Discovery and deployment

Default-export `defineCommand`, `defineEvent` or `defineComponent` from a `*.command.ts`, `*.event.ts` or `*.component.ts` file in the corresponding `src/` directory. Discovery is recursive and deterministic; production loads the compiled `.js` files. Duplicate identities, invalid exports and missing services fail startup. `bun run build` removes stale compiled routes.

Command registration and runtime use the same definitions. After a definition changes, use `bun run commands:register --guild ID` for development or `--global` for an authorized production cutover, then rebuild/restart execution code. `scripts/commands.ts` also provides command inventory and guild-scope cleanup; see [maintenance-tool profiles](CONFIGURATION.md#maintenance-tool-profiles).

## Maintenance tooling boundaries

Keep tool I/O at the edges and reusable logic in exported functions or `src/`. Discord/database tools use the deployment-identity guard in `src/config/deployment.ts` before I/O. Share existing permission, visibility and inspection helpers instead of duplicating SDK interpretation; `src/domain/permissions.ts` supports checks that deliberately ignore Administrator.

## Add a command

Use an existing command in the same feature group as the starting point. The module owns its Discord builder, `execute`, optional `autocomplete` and `requires` services. Keep related subcommands under their root command.

The router acknowledges interactions, checks guild/human scope, resolves the actor and viewer, and controls reply visibility and mentions. Commands parse options, call an application operation and return its presenter. Application services independently authorize the operation. For an officer-only root, declare `access: "officer"` and the builder's default `ManageGuild` permission; mixed-permission subcommands authorize each operation.

Autocomplete cannot defer and may reveal private records, so authorize each focused-option branch. Use `focusedOption()`, the shared `completeMember()` for member inputs, and `choice()` for bounded labels. Member completion values are user IDs, parsed by `userId()` in `src/discord/selectors.ts`; use `selfOnly` where appropriate.

### Present results

Return one `Presented` reply and throw catalog `Failure` values for errors. Put pure presenters in `src/discord/presenters/`, using typed application results and the viewer. Follow [REPLIES.md](REPLIES.md) for formatting, examples, attachments and presenter tests. Handlers do not set `flags` or `allowedMentions`.

### Open a modal

A command may provide a synchronous `modal(interaction)` instead of `execute`; `/apply` is the current example. Modal openers are user-access only. Opening a form must be the initial acknowledgement and does no database/network work. An optional fast `beforeModal` availability check is only a courtesy: errors or timeouts still open the form.

Handle submissions in a separate component namespace. Recheck actor/guild bindings, input limits and persisted context in the application operation. Forms can survive restarts; opening one does not create a record or authorize submission.

## Add an event

Use `defineEvent` with a unique handler `id` and a Discord `Events` value. Handler arguments follow `ClientEvents`; several handlers may subscribe to the same event. Filter guild scope and bots before feature work. Use `once` for a one-time listener; shutdown listeners may declare `duringShutdown`.

Delegate stateful decisions and critical deliveries to application services and the durable outbox. The binding layer handles errors and listener cleanup. Additional gateway intents must be configured in `DiscordGateway` and, when privileged, in the developer portal.

## Inject a new service

Reuse tokens from `src/application/keys.ts` where possible. A new capability defines one `ServiceKey` with a provider predicate, is registered through `services.provide()` in the composition root, and is declared in the module's `requires` list. Consumers retrieve it with `services.get()`. Import the same token in provider and consumer; startup validates required services.

## Add a component

Use `defineComponent` with a unique custom-ID `prefix`. Narrow the interaction type before reading fields. Build and parse IDs through `src/discord/custom-ids.ts`: they carry selectors, never authority. Every click resolves a fresh actor and the application operation reauthorizes it.

Replies are the default acknowledgement. Use `acknowledge: "update"` only for a component's own view; the router updates a source only when ephemeral or created for the presser. Ordinary failures leave that view intact and normally become private follow-ups; DevBot's public-response override is an exception. See the existing guest review, ledger pager and verification components for their durable context checks.

Messages outlive deployments. Add grammar/builder/parser tests together; retired actions keep parsing and answering “out of date” for at least one minor release.

## Test a presenter

Add cases to `tests/fixtures/replies/` and pin wording in the group's unit tests. [REPLIES.md](REPLIES.md#add-or-change-a-reply) lists the relevant checks. An intentionally added public command also needs the command inventory expectation updated.

## Web pages

The web pages (#43) run in the bot process: `src/main.ts` starts a second listener once the writer lease and Discord are ready, and the shutdown drain stops it. They stay off until `WEB_PUBLIC_ORIGIN` is set. `src/web/settings.ts` parses the web settings when the web starts, so a bad value turns the web off with a report naming the setting and never stops the bot. `src/web/http.ts` holds the header set and the POST checks; `src/web/server.ts` owns the fixed routes (`/`, sign-in, sign-out, `/health/ready` and the assets) and wires the request pipeline.

### Add a page

Default-export `definePage` from a `*.page.ts` file under `src/web/pages/`. The path is `/g/:guild/` followed by lowercase segments. `access` is required, with no default, so no page is public by omission. It's an any-of list of `PAGE_ACCESS` flags (`src/web/access.ts`): `officer` (officer authority, as commands use it), `manager` (`authorizeRoleManager`), `member` and `guest`. `member` and `guest` mean the actor holds the server's bound Member or Guest role now (`Actor.member`, `Actor.guest`, set by `Service.enrichActor`; never true while the role is unbound or TaruBot isn't set up there), and both also need `botAdministrator === false`: members and guests are refused while TaruBot holds Administrator in the server, and an uncached TaruBot member counts as holding it (owner decision A2). Officers aren't affected. `selfServiceAccess` in `src/domain/policy.ts` is the same rule for application operations. Neither flag reads `timedOut`: a member in a Discord time-out may view, and the operation refuses the write. `requires` lists service keys, checked when the web starts; a missing one keeps the web off. A page reaches only those: `context.services.get()` throws "Page used an undeclared service" for any other key, which shows as a reported 500, so a bug in one page can't reach a service it never declared. A page with a `post` handler must also declare `postLimit`, its budget of POSTs per user and server in each ten-minute window, and `definePage` refuses one without it (or a `postLimit` without `post`). `nav` lists the page in the server navigation for viewers it admits, and the optional `icon` names its decorative navigation icon from `src/web/icons.ts`.

The server refuses before the page runs: a malformed or unserved server, or someone who isn't a current member, gets 404, a signed-out visitor goes to sign-in, and a missing flag gets 403. `servePage` in `src/web/server.ts` has the exact order.

The actor is resolved as for a slash command, in one of two modes (`ActorResolution`, `gateway.actor()`). A GET reuses it for up to 60 seconds, and on a miss resolves it **light**: the server and its roles from the gateway cache, which the Guilds intent keeps current, and only the member fetched, one Discord request instead of three; a server that isn't cached and available falls back to full. Sign-in admission resolves light and fresh for each candidate server. Every POST resolves **full** and fresh, as commands do. Application operations authorize it again.

`get` loads a typed view model through `context.services`, and a pure function in `src/web/views/` renders it, as presenters do for Discord. Views import application, infrastructure, Drizzle and job modules as types only. Templates use `html` from `src/web/html.ts`, which escapes every interpolation:

- untrusted text (server, member and role names, notes) goes through `untrusted()`, links through `href()`, and times through `time()` (UTC);
- never write a `style=` attribute or a script: the CSP allows neither;
- the unescaped `raw()` is allowed only in constant files that `tests/unit/web-boundary.test.ts` allow-lists.

Throw catalog `Failure` values. The error page maps the category to a status and shows the approved message with its code and ref; anything else is a 500 that shows neither its text nor its stack.

### Dashboard data and presentation

Server configuration and Background work are read-only; [Role menu](#role-menu) and [My roles](#my-roles) write. `/g/:guild/configuration` uses `Service.validate()` and the same `configurationChecks()` checklist as Discord. Validation is single-flight per application service and server, with successful results reused for 30 seconds from completion. Every lookup, including a memo hit, reauthorizes the officer; rejected checks are not retained. The page prints the check's actual UTC completion time.

`/g/:guild/status` is labelled **Background work** in navigation. Its process health keeps only readiness, Discord, database and the Lodestone cooldown state. It shows up to 10 recent refresh runs and 25 outstanding jobs from `syncStatus()`, with counts explicitly limited to the displayed sample, not server-wide or global totals. Native `<details>` disclose officer diagnostics without scripts; arbitrary job payloads and process-wide diagnostics are not rendered.

A server page is a console: from 64rem a sidebar holds the wordmark, the server switcher (a link back to the server list, and the only place the server's name appears), the page navigation and the account menu, beside a top bar; on narrower screens they form a sticky bar with the navigation as a strip under it. Sign-in, the server list, no access and errors are entry pages over a decorative starfield. Each server page has one featured card. On Configuration it is the health snapshot, which counts the checks and links to the full checklist, followed by six settings cards; a long checklist group folds into a disclosure only when every check in it passed. On Background work it is process health, followed by the sample counts and the work and run tables, each in its own focusable scroll region with native diagnostic disclosures; below 48rem each job and run stacks into a card instead, still marked up as the same table with explicit roles.

`src/web/mentions.ts` snapshots names from this server's gateway cache at render time, never stores them, and turns Discord mentions and timestamps into escaped, isolated text and UTC `<time>` elements. Uncached names fall back to IDs; obfuscated or permission-denied channels never expose cached names. Every page declares `gatewayKey` alongside its data services.

Both web surfaces are TaruBot's port of the Orrery design system export, dark only; the export itself is not in the repository. `site/src/styles/tokens.css` is the one token source, and `src/web/styles/tokens.ts` carries its exact text. `assets.ts` assembles the dashboard stylesheet from `src/web/styles/` (tokens, the ported base, effects, components and form controls, the console and entry frames, each view's rules, then reduced motion, reduced transparency, forced colors and print) and serves it with the favicon, the fonts and the third-party notices at hashed `/assets/` paths. The ambient loops (holographic edge and drift, starfield twinkle, orbit rings) keep looping with no pause control, since the owner accepted the WCAG 2.2.2 finding on 2026-10-08; `prefers-reduced-motion` stops every loop on both surfaces. The fonts are Sora for headings and the wordmark, Manrope for text and JetBrains Mono for labels, timestamps and code, the latin subsets from Fontsource, in `site/src/assets/fonts/`; after changing one, regenerate `src/web/fonts.ts` with `bun --no-env-file scripts/web-fonts.ts`. Icons are Lucide path data inlined as constants in `src/web/icons.ts`. `src/web/notices.ts` copies `site/public/third-party-licenses.txt`, which every dashboard footer links. `tests/unit/web-parity.test.ts` keeps the tokens, favicon, notices and fonts identical on both surfaces. The CSP admits styles, fonts and images from the dashboard's own origin only, and no script or inline style, so a page makes no third-party request.

### Forms

`post` runs only after, in this order: the same-origin and form-type checks and the session; the server checks; the session's form token; the shutdown check; a refusal from the actor memo; the page's `postLimit`; and a fresh actor that the page's flags admit. None of the checks before the actor costs a Discord request. The memo check (`AccessResolver.peek`) only refuses: when the memo already holds an answer this page wouldn't admit, the POST gets that answer's 404 or 403 at once, so someone hammering a page they can't use, such as a member on Role menu, costs at most one full resolution a minute. Anything else goes on to the full resolution. `servePage` in `src/web/server.ts` has the exact order.

- **Form token.** Every POST form carries the session's form token in the hidden `form_token` field (`FORM_TOKEN_FIELD`). It's an HMAC-SHA-256 keyed with the session cookie's token (`formToken` in `src/web/sessions.ts`), so it needs no storage and no new secret, a database reader can't derive it, and a new sign-in rotates it. The server compares it in constant time (`formTokenMatches`) and answers 403 on a mismatch, then removes the field from the form `post` receives. It's defense in depth behind the same-origin check. The account menu's two sign-out forms carry it too: signed in, a sign-out without it ends no session.
- **Shutdown and budgets.** Once shutdown starts, a POST gets `stoppingRefusal()` from `src/web/limits.ts` (429, Retry-After 30). Over the page's `postLimit`, it gets a 429 with Retry-After. Budgets are fixed ten-minute windows counted in memory per page, server and Discord user, never by address. A POST refused by the token, shutdown, memo or budget check isn't counted; one refused later, by the actor check or the page, is.
- **Render with the form kit.** `src/web/views/forms.ts` holds pure helpers. `postForm` opens every form, with the token first and a same-origin action. Fields come from `textField`, `numberField`, `selectField`, `choiceGroup` and `hidden`; feedback from `errorSummary` and `notice`; actions from `submitButton` and `formActions`. Put a danger button only inside a `disclosure`, and use `context` for the visually hidden suffix that keeps repeated control names unique. Labels, hints and error messages take plain text or `SafeHtml`, such as `mentionText` output. `src/web/styles/forms.ts` gives inputs real borders under the base outline focus, keeps checkboxes and radios native, and makes the action row sticky on phones.
- **Answer with a `PostOutcome`.** Parse the form with zod, call one application operation, and return either of two outcomes. `{ redirect }` answers 303 through `safeReturnPath`, normally to `noticeLocation(path, token)` with a token from the page's fixed notice table; `notice()` ignores any other token, so a URL can't put text on the page. A page may add its own parameters, such as the Role menu's `category`, which it only compares with its own data to place the notice, never shows. `{ invalid, status }` re-renders the page's content with the submitted values kept, escaped, and an error summary: 422 for refused input (the default), 409 when valid input met a changed state. A 409 keeps only the values the user changed from what the form showed (the Role menu's `was:` fields), so resubmitting it can't put back someone else's change in a field the user never touched. The layout then prefixes the title with "Error: ". Messages never echo submitted text. Throw catalog `Failure` values for refusals that end the request (403, 429, 503); the error page shows them, with a link back to the page, since reloading the answer to a POST would send the same form again.
- **One transaction per write.** The application operation authorizes the actor again, makes any Discord reads first and never inside the transaction, then locks, compares, writes and audits in one transaction. Just before it commits it checks for shutdown again and throws `stoppingRefusal()`'s failure, so a write that began just before the drain rolls back. Web handlers never write to Discord: Discord effects belong to the job worker. `SelfRoles.edit` is the example of an audited officer write, and `SelfRoles.choose` of a member's save that queues a job.
- **Idempotency by state.** A write whose result equals the current state succeeds without writing, whatever revision the form carried, so a double submit lands on the same 303. A create carries an ID its GET minted, so a repeat finds the existing record. Otherwise a stale revision is a 409 re-render. Forms name records by ID and moves name an absolute position, never an index or a direction.
- **Audit.** Officer changes are audited. Member self-service keeps Discord as the record of what someone chose and is delivered through durable jobs, with no audit row per save, as the `/main` and `/nickname` preferences (`Service.preferences`) already do.
- **Jobs.** A page that enqueues work follows these rules for its job kind: carry `guild_id`; validate the payload before `enqueue()`; use a per-action dedupe key; use the `reconcile.` prefix only when generation fencing is intended; add a `JOB_KIND` label. Pages then say "queued", never "done".

### Role menu

`/g/:guild/role-menu` lets officers edit the server's self-service role menu through `SelfRoles` (`selfRolesKey`, `src/application/self-roles.ts`). The menu is one versioned JSON document per server ([persistence](PERSISTENCE.md#self-service-role-menus)). `src/domain/self-roles.ts` holds its schema and caps, every edit as a pure function from one menu to the next, and `selfRoleChecker`, the one rule set for what may be self-assigned. The page renders through `src/web/views/role-menu.ts` and declares `selfRolesKey` and `gatewayKey`.

- **Who.** Any officer may make every change, adding roles and resetting an unreadable menu included. There's no Discord Manage Roles requirement and no check of the officer's own role position (owner decision of 2026-10-09). The rule set and TaruBot's own role position are the whole safety boundary, so loosening a rule needs the owner's agreement.
- **The rule set.** A self-service role:
  - is an ordinary role TaruBot can assign: it exists, isn't @everyone, managed or TaruBot's own, sits below TaruBot's highest role, and TaruBot has Manage Roles;
  - is never a bound or retired access role;
  - sits below the bound Officer and FC Leader roles and below every role under TaruBot holding Kick Members, Ban Members, Time Out Members, Manage Nicknames or Administrator, managed bot roles included (`above_staff`; the owner's "Refuse them", 2026-10-09). Discord lets those powers reach only members whose highest role is lower, so a menu role above one would put everyone who picks it out of that role's reach. TaruBot's own managed role is left out, since TaruBot is its only holder and its reach comes from its highest role; any other role TaruBot holds still counts, since people can hold it too. Tied raw positions follow Discord's order, as for TaruBot's own role. The message names only the powers the role it names holds. This rule doesn't block removal;
  - holds no server permission @everyone lacks, and never Administrator, Manage Server, Manage Roles or Manage Channels;
  - gains nothing in a readable channel that any of three audiences already sees: @everyone, @everyone with the Member role, and @everyone with the Guest role. The Member and Guest baselines matter: a Send Messages allow in a members-only announcements channel would otherwise let every member post there;
  - allows, in its own overwrite in any readable channel, only bits @everyone holds server-wide, View Channel aside, because its holders may see that channel through a role the check can't know about (otherwise a Manage Messages allow would make everyone who picks it a moderator there);
  - lifts, with that allow, no deny another role's overwrite sets in the channel, View Channel included, and no @everyone deny in a channel it doesn't open (`channel_deny`). Discord lets any role's allow beat every role's deny, so a Send Messages allow would otherwise undo a mute role, a View Channel allow a jail or quarantine role, or let people who see a read-only channel through an officer-assigned role post there. In a channel the role opens, two lifts are what opening means and stay allowed: @everyone's deny (an opt-in channel) and the View Channel bit of the Member and Guest roles' deny (an opt-in channel in a server private by default). Any other role's View Channel deny there, such as a jail role's, still refuses the role;
  - takes nothing away from the people who hold it (`restricts`): no deny in its own overwrite in a readable channel it doesn't open, and nothing lost by any of the three audiences in a channel it already sees. A self-service role's holders can remove it, so a mute, jail or quarantine role on the menu could be removed by the very people it restricts. A deny in a channel the role opens only shapes that channel, so it stays allowed. This rule blocks removal too, so even under Not offered or Stop offering nobody removes such a role themselves. So a role that passes every rule changes nothing in a readable channel it doesn't open: it grants nothing there, lifts no deny and takes nothing away;
  - may open a channel none of those audiences sees, carrying no more than that audience holds server-wide (View Channel aside, so opt-in channels work where @everyone lacks it server-wide), unless the channel looks officer-facing. Seeing a channel is judged only as opening it.

  Channels TaruBot can't read are outside every channel rule: their real overwrites, the role's own included, aren't in the snapshot. An add needs the officer's confirmation that the roles neither open them nor give any permission in them.

  The channel rules judge the role's overwrites with its server bits capped at @everyone's, because any excess is already reported once server-wide. Problem messages name roles and channels in Discord's mention grammar; render them with `mentionText`.
- **Officer-facing is a heuristic.** A channel counts as officer-facing when a setting names it for officers (the officer room, officer notifications, guest reviews, or onboarding's staff-only channels), or when none of the three audiences sees it and its View Channel allows include the Officer or FC Leader role or a role with a staff power. Two shapes are missed: a private channel that only Administrators see, with no allow at all, and a private channel opened to officers through per-member entries rather than a role, such as an officer room built from each officer's own entry or a ticket-style channel. So the page lists every channel each role opens, officers read **Opens:**, and an add needs the officer's confirmation while TaruBot can't read some channels.
- **Where it runs.** The page GET judges every role on the gateway cache, with no Discord request. Each add reads a fresh snapshot (two requests) before its transaction and judges the added roles again under the locks. The "Role menu" health check in `Service.validate()` uses the snapshot that method already reads.
- **The invariant.** A menu role is never one of the four bound access roles or a retired role, or reconciliation would add it to everyone or strip it from everyone who picked it. A menu add checks it under the guild row lock. `Service.configure()` and `/setup onboarding` refuse a menu role under their `FOR UPDATE` (`assertNotOnMenu`, `rolesOnMenu`), and `planSetup` lists it as a blocker. `/setup onboarding` also checks the roles it would reuse, decided read-only as the dry run decides them, before `ensureRole` creates or renames any role. A menu this build can't parse is scanned for role IDs, so the check fails closed.
- **An unreadable menu.** A stored document that doesn't parse, for example one a newer release wrote before a rollback, is never edited. Every edit but **Reset role menu** is a 409, and the reset is audited like any other edit. A reset of a menu that reads fine is a 409 too, since it would wipe every category at once; a repeat after a reset meets the empty menu and succeeds without a write. The scan that keeps an unreadable menu's roles from being bound reads every string in the document, object keys included.
- **Members' choices** are picked on [My roles](#my-roles) and applied by the `roles.self` job.

### My roles

`/g/:guild/my-roles` lets members, guests and officers pick their own roles from the published menu (`access` `member`, `guest` and `officer`; `requires` `selfRolesKey` only; `postLimit` 10). It renders through `src/web/views/my-roles.ts` and needs no gateway service: `SelfRoles.view` returns the menu roles' cached names (`MyRoles.roleNames`) with everything else.

- **View.** `SelfRoles.view` reads only the database and the gateway caches: the menu, the cached snapshot judged with `selfRoleChecker`, the member's cached roles (`DiscordPort.cachedRoles`, which `GuildMemberUpdate` keeps current, so a job's echo shows at once), and the newest `roles.self` row, whose waiting payload it overlays. `choiceMenu` in the domain decides each row: changeable (addable and passing, or held and removable), held but unchangeable (a text line), or hidden. A pick-one category with several roles held preselects none. Ticks follow the waiting change, and a row it ticks differently from what is held is badged "Waiting to add" or "Waiting to remove"; notes never say "You have" of a role that isn't held. A published category whose held, unchangeable roles already fill its limit, with nothing changeable ticked, renders as text, since no input there could do anything. Removal-only categories show only to holders; drafts reach officers only, disabled and never submitted. With no category to show, `MyRoles.offers` tells a menu whose roles all fail a rule now ("There are no roles to pick here right now") from one with nothing published. Banners about a change that ended unapplied or incomplete carry its `completedAt` as a UTC `<time>`.
- **Save.** The form sends `shown` (each enabled category), `seen:<id>` (each value ticked at render, `""` for a preselected None) and `c-<id>` (the picks). `SelfRoles.choose` reauthorizes with `selfServiceAccess` and refuses a timed-out actor, paused effects, an unreadable server and a missing setup. `changedCategories` keeps only the categories whose picks differ from what was shown, so a stale tab, another bot or an officer's hand edit is never undone in a category the person didn't touch: a value the menu no longer allows there is a 409 re-render, too many picks or a role that now fails a rule a 422. The transaction locks `self-roles:<guild>:<user>`, merges into the waiting change by category (`mergeChoice`: a changed category replaces everything the waiting change asked there, roles the page hid included), applies the equal-state rule and enqueues ([persistence](PERSISTENCE.md#self-service-role-menus)). No audit row is written. Outcomes are `saved` (303 to `#status`), `unchanged` (303 with `notice=unchanged`), `conflict` (409) and `invalid` (422).
- **Apply.** The dispatcher completes a cleared `{}` payload as `nothing to apply` before the effects gate, parks paused work as `disabled`, then calls `RoleChoiceJob.apply` before any delivery bookkeeping, so the job never writes `delivery_attempts`. `RoleChoiceJob` is a separate class that only the dispatcher constructs and no service key provides: it writes any member's roles from the job it is given, so it stays out of `SelfRoles`, which My roles can reach. `apply` takes `reconcile.user`'s `user:<guild>:<user>` lock (busy waits without spending an attempt), reads the member, plans with `planSelfRoles` against the current menu (only `offered` roles still listed, never a bound or retired role, an over-limit category skipped whole), re-checks every role on a fresh snapshot, and writes through `DiscordPort.selfRoles`: one role per request, with an audit-log reason. Unknown Role (10011) is skipped; Missing Permissions (50013) re-reads TaruBot's member and is skipped while it still has Manage Roles, otherwise the job is blocked with a role-free diagnostic. Results are counts: `{status: "applied", added, removed, skipped}`.
- **Access loss (owner decision Q3 B).** When `Synchronization.user` leaves someone with none of Member, Guest, Officer and FC Leader, in a server that binds Member or Guest, `accessLossRoles` lists the held, listed, removable menu roles that open a channel, and the pass removes them with a separate `selfRoles` call after the access change, so they can never block it. Its result and the preview record only a count, `selfRoles`. `apply` likewise skips adding a channel-opening role to someone with none of those roles. Cosmetic roles and drafts are never touched.
- **Privacy.** Role IDs a member chose may appear only in the waiting payload, which migration 012's trigger clears when the job ends. They never reach job results, diagnostics, logs, audit rows, issue reports or officer views: `Service.syncStatus` leaves out the user of someone else's role choices, `Service.guestStatus` leaves `roles.self` rows out of every record, and problem messages that name roles stay on the person's own 422. `IssueReports` leaves `roles.self` rows out of a report's member section, the member's own `/issue` included, so a report shows one only in its queue tables, by kind; an automatic report of a failed one (`jobFailed`) names no member, so it has no member section. Tests scan for `<@&` and every menu role ID.

### Sign-in

`/auth/callback` checks `state` before any Discord request. `DiscordSignIn.finish` runs the token exchange and `/users/@me` inside an `ExchangeGate` (`src/web/limits.ts`): 30 exchanges a minute across all users, 4 at once, and after a Discord 429 every callback is refused locally until its Retry-After passes, so a flood can't earn the bot's egress address Discord's invalid-request ban. Its refusal is a 503 with Retry-After. Once Discord has returned the user ID, a per-user limit of 10 sign-ins in 10 minutes applies before admission (429, no session, the browser's existing session untouched). Admission lists only servers whose pages admit the user, resolving the actor light and fresh for each, and creates no session when none does. `PgSessions.create` keeps at most `SESSIONS_PER_USER` (10) live sessions per user, in one transaction under a per-user advisory lock. Every limit is counted in memory by Discord user ID or globally, never by address. `/` answers 303 straight to the page when exactly one server is listed with exactly one navigation page.

### Run and test pages

`bun --no-env-file tests/fixtures/web-dev.ts` runs the real web server on `[::1]` with a fake Discord sign-in, in-memory sessions and invented data. Never start it through a root `bun run` alias, which loads `.env`. Review states are opt-in and combine: `--state-checks=warn|fail`, `--state-activation`, `--state-deploy-disabled`, `--state-empty`, `--state-cooling`, `--state-hostile-names`, `--state-menu-problems`, `--state-menu-unreadable` and `--state-roles=queued|blocked|failed|skipped|expired` (the harness header describes each); without them the data is the healthy default the tests rely on. Its fake authorize page offers invented accounts (`HARNESS_ACCOUNTS`): an officer, a member of both servers, a guest, a member in a time-out, a lobby newcomer, someone in neither server and a bot. Test routes with `createWebApp` and `app.request()` (`tests/unit/web-server.test.ts`), and views with invented data and linkedom (`tests/unit/web-pages.test.ts`).

For a preview from another machine, `--host` selects the VM's LAN interface and `--cert` / `--key` supply its TLS certificate and key. Both the dashboard and fake sign-in bind and advertise that address over HTTPS; production's origin policy still rejects plain HTTP on routable addresses. Replace the documentation address below with the VM's LAN address before generating the certificate:

```sh
mkdir -p .cache/web-preview
openssl req -x509 -newkey rsa:2048 -noenc \
  -keyout .cache/web-preview/key.pem -out .cache/web-preview/cert.pem \
  -days 2 -subj /CN=192.0.2.10 -addext subjectAltName=IP:192.0.2.10
bun --no-env-file tests/fixtures/web-dev.ts --host 192.0.2.10 \
  --cert .cache/web-preview/cert.pem --key .cache/web-preview/key.pem
```

Open the printed HTTPS address. A self-signed certificate may need a browser exception on both the dashboard and fake sign-in ports. The default command remains IPv6-loopback HTTP, and production passes none of these listener overrides.
