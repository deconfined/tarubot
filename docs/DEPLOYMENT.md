# Release delivery and owner operations

TaruBot is delivered by moving registry tags (owner decision, 2026-10-28). An approved Deploy points the `production` tags of `ghcr.io/deconfined/tarubot-release`, a package only an approved Deploy can write, at one release's signed images; the production runtime's updater follows those tags, and starting the new image is the whole upgrade. GitHub never connects to the runtime, and the operator needs access to the containers only: no SSH, no host scripts, no host files, no cron and no host tools. The owner accepted the price: GitHub can't watch the result or roll back by itself, so a bad release is rolled back by dispatching Deploy with the earlier version. The image carries its own tools, and one-off containers of the same image run them.

This runbook describes what the repository implements. It is **not evidence that any step happened live**. Provisioning, credentials, GitHub settings, the cutover and every live operation are owner steps under [AGENTS](../AGENTS.md); agents run none of them. Self-hosters use the site's [Compose installation](../site/src/content/docs/deploy/install.md) and [operations guide](../site/src/content/docs/deploy/operations.md) instead. See also [configuration](CONFIGURATION.md) and the [threat model](THREAT_MODEL.md).

## How a release reaches production

1. **Review.** Protected `main`, current CI and security checks and the owner's code-owner approval; merge commits only. An explicit version increase declares a release ([CONTRIBUTING](../CONTRIBUTING.md)); maintenance merges keep the version and publish nothing.
2. **Publish.** `publish.yml`'s release gate validates the version and proves the merged commit carries a pull-request head tree whose CI passed, the in-image suite on native AMD64 and ARM64 included; for any other tree it runs `ci.yml` in full. It then publishes two images, each tagged only while its tag is absent, so a published version is never overwritten and a re-run resumes only with this commit's own images:
   - `ghcr.io/deconfined/tarubot:X.Y.Z` (also `sha-<commit>`): the bot and every tool, built on each platform's native runner, both platforms scanned by `scan.yml`;
   - `ghcr.io/deconfined/tarubot:web-X.Y.Z`: the stock Caddy image, pinned by digest, plus TaruBot's Caddyfile and offline page (the Dockerfile's `web` stage).
3. **Attest.** Both index digests get GitHub build provenance from `publish.yml` on `main`. Fixable high or critical findings, scanner or registry errors and expired exceptions stop it. The default exception policy is empty; an exception needs the exact reviewed finding, a reason or issue and an expiry within 30 days. `latest` and `web-latest` move only after attestation, and only while `main` still names this commit.
4. **Approve.** When the repository variable `DEPLOY_ENABLED` is exactly `true`, publication calls `deploy.yml` with `target: production` and the version. Its one job, shown as **Production release / Deploy production**, waits for the owner's approval of the `production` environment, the routine go-ahead ([AGENTS](../AGENTS.md)). A skipped Deploy proves nothing about the runtime.
5. **Verify.** First of all, Deploy checks that its environment holds `RELEASE_REGISTRY_TOKEN`, the only credential that moves a channel tag ([owner settings](#owner-settings-in-github)). Then, with the run's own token, which only reads packages, it checks the target's switch and the version's shape; that this attempt was held for the approval (the owner's rule of 2026-10-08: an approval given to an earlier attempt is never reused); that `X.Y.Z` and `web-X.Y.Z` both exist in `ghcr.io/deconfined/tarubot`; that the bot image's source commit (its `org.opencontainers.image.revision` label) is on `main` and its `package.json` says `X.Y.Z`; and that both digests carry that commit's [provenance](#signed-build-provenance). Every refusal ends with "No tag was moved."
6. **Read the channel.** With the environment's token, Deploy reads which release the channel names now, from the version label of the bot image that `ghcr.io/deconfined/tarubot-release:production` names. Before the first Deploy that package doesn't exist, and GHCR answers for a missing package as for a private one, so Deploy first asks GitHub's packages API whether it exists; until it does, both channel tags count as absent. That answer also lists the token's scopes (GitHub's `X-OAuth-Scopes`), and Deploy refuses a token holding any but `write:packages` and `read:packages` ([owner settings](#owner-settings-in-github)). **A publication never rolls back:** publication's call, which GitHub runs as a push, refuses when the channel already names a newer version ("A publication never moves production back from …"), or one it can't read. Only a dispatched Deploy goes back to an earlier version: that is the rollback.
7. **Move the tags.** `web-production`, then `production`, are set in the release package to exactly those digests and read back. Each is copied index for index from `ghcr.io/deconfined/tarubot`, so the release package names the very digests verified above. Web first, so a failure between the two leaves the bot, and so the database, on the previous release. The run's summary lists both digests before and after, the commit and the version the channel named before.
8. **Follow.** On the runtime, Watchtower notices the moved tags within its 300-second poll, pulls them, stops the old container and starts the new one with the same configuration ([what runs](#what-runs-on-a-docker-host)). GitHub sees none of this: `/version`, the heartbeat and the container say which release runs.

**Why a package of its own.** Every workflow in this repository, on any branch, can ask for a token that writes `ghcr.io/deconfined/tarubot`. A channel tag there would let such a workflow deploy production without the approval or the provenance checks (a review finding; the owner's decision of 2026-10-28). So the runtimes follow only `ghcr.io/deconfined/tarubot-release`, which is written with `RELEASE_REGISTRY_TOKEN` alone, a secret of the `production` and `staging` environments, which GitHub hands only to their approved job on `main`. Deploy's own token has `packages: read`, in `deploy.yml` and in publication's call of it. `ghcr.io/deconfined/tarubot` keeps `X.Y.Z`, `web-X.Y.Z`, `sha-<commit>`, `latest` and `web-latest`, and no channel tag is written there.

**Starting the image is the whole upgrade.** Before it takes the writer lease, the bot runs the deployment guard and applies its own pending migrations. Immediately before the first one, holding the writer lease's lock so no bot can write in between, it takes an encrypted pre-migration backup; a failed backup applies nothing. Production and staging refuse to migrate without backups configured. If this migration step fails, the bot waits 10 minutes before it exits, so a restart can't repeat it, full backup included, every minute ([when a release doesn't come up](#when-a-release-doesnt-come-up)). Once ready, the bot registers its commands in its profile's scope (global for production, DevBot's guild for staging) with one bulk request. A refusal or a Discord error there is filed as an issue report (`command registration`), and the bot keeps running with the set Discord already holds, so 2.45.0's outage, a registration failure after the migration with the bot stopped, can't recur. PR CI's command-registration test still checks Discord's rules before merge. The info lines `Modules loaded` and `Database writer lease acquired` keep their exact text.

Re-running a failed Deploy really retries, and asks for the approval again. A Deploy of the version the channel already names changes nothing and says so. Deploy accepts stable `X.Y.Z` only, at most four digits per component, compared part by part as numbers (2.10.0 is newer than 2.9.0); prereleases are never published or deployed. A dispatched Deploy may go back to an earlier version, which is the rollback; a publication never does ([when a release doesn't come up](#when-a-release-doesnt-come-up)).

## Signed build provenance

For owner verification of an exact image, the bot's or the web image, substitute its index digest and full source commit (Deploy's summary lists both):

```sh
gh attestation verify oci://ghcr.io/deconfined/tarubot@sha256:<digest> \
  --repo deconfined/tarubot \
  --cert-identity https://github.com/deconfined/tarubot/.github/workflows/publish.yml@refs/heads/main \
  --source-ref refs/heads/main --source-digest <commit> \
  --predicate-type https://slsa.dev/provenance/v1 --deny-self-hosted-runners
```

`docker buildx imagetools inspect ghcr.io/deconfined/tarubot-release:production` shows the digest a channel tag names now: the same digest as the release's tag in `ghcr.io/deconfined/tarubot`, so the command above checks it as it is. Keep the exact `--cert-identity`; a broader signer-workflow pattern is insufficient. Image labels are read in addition to, never instead of, provenance. Deploy runs this check for both digests before it moves a tag. Actions use SHA-pinned tools and checkouts; only attestation gets the OIDC permissions it needs.

## What runs on a Docker host

Any Docker host with Compose v2 serves, and so does a platform that runs the same containers. Compose can run on the owner's own machine against the host's Docker (a Docker context): nothing of TaruBot's lives on the host's filesystem but Docker's own images, volumes and logs. Production and staging each have their **own Docker host**: two projects on one rootful daemon aren't isolated from each other, and both manifests use the project name `tarubot`.

| Service | Container | Image | Role |
| --- | --- | --- | --- |
| `tarubot` | `tarubot` | `${TARUBOT_IMAGE_REPOSITORY}:${TARUBOT_IMAGE_TAG}` | The bot. One-off tool runs of this service are named `tarubot-tarubot-run-<id>` |
| `watchtower` | `tarubot-watchtower-1` | `ghcr.io/nicholas-fedor/watchtower`, pinned by digest | Follows the tags of the two named containers |
| `caddy` (profile `web`) | `tarubot-web` | `${TARUBOT_IMAGE_REPOSITORY}:web-${TARUBOT_IMAGE_TAG}` | The optional HTTPS proxy ([optional dashboard](#optional-dashboard)) |

- **Settings** are the Compose project's environment: a private copy of `production.env.example` (or `staging.env.example`), mode 600, kept wherever you run Compose and passed with `--env-file`. `TARUBOT_IMAGE_REPOSITORY=ghcr.io/deconfined/tarubot-release` and `TARUBOT_IMAGE_TAG=production` are required: `ghcr.io/deconfined/tarubot` is writable by any workflow of the repository, so a runtime follows a tag there only during a [deploy by hand](#rotation-and-host-loss). Containers keep the settings they were created with, and Watchtower copies them onto the new container, so after changing a setting run `up -d` again. The bot also receives the project's own `TARUBOT_IMAGE_REPOSITORY`, `TARUBOT_IMAGE_TAG` and `COMPOSE_PROFILES`, which it ignores, so that each backup's settings copy starts the project again as it was ([recover the settings](#recover-the-settings)); set the web profile there as `COMPOSE_PROFILES=web`, because a `--profile` on the command line never reaches the copy. A variable exported in your shell overrides the file, so run Compose from a shell without TaruBot's settings exported. Never copy production's settings to staging.
- **Manifests** are read where Compose runs: `docker-compose.production.yml` beside the `docker-compose.web.yml` it includes, from the release you run. Watchtower keeps a container's configuration, so a release that changes a manifest or adds a setting says so in its changelog entry, and that change takes effect only once you update your copy and run `up -d`.
- **The database** is the owner's managed PostgreSQL: the direct TLS endpoint with its verified CA, never a transaction-mode pool (the writer lease needs a session connection), with the names the [tool profile](CONFIGURATION.md#maintenance-tool-profiles) requires. A new host's address must be able to reach the Lodestone.
- **Hardening.** The bot's root filesystem is read-only, and its only writable path is a 1 MiB `/tmp` tmpfs, which holds the database CA's private file while `pg_dump` or `pg_restore` runs. No capabilities, no new privileges, bounded local logs. Its health port is never published; only the proxy's 80 and 443 are, with the `web` profile. A new bot has 300 seconds to become healthy, for a migration plus its backup.
- **Watchtower**, Nicholas Fedor's maintained fork (the original is archived), runs with `--scope tarubot --interval 300 --stop-timeout 40s --include-restarting --cleanup` and the container names `tarubot` and `tarubot-web`. When a tag has moved, it pulls it, stops the old container (the bot within its own 30-second stop grace period), starts the new one with the old one's configuration and removes the old image; the swap takes seconds. It touches only containers that have one of those names **and** carry its scope label, `com.centurylinklabs.watchtower.scope: tarubot`, which the bot, the proxy and Watchtower itself have. One-off tool runs are left alone: `docker compose run` copies the service's labels, the scope included, but names them `tarubot-tarubot-run-<id>`, so a restore or backup run is never stopped and started again on a tag move. The scope also keeps it apart from other updaters: it never stops another Watchtower on the host, and this fork's other instances, scoped differently or not at all, leave it and TaruBot's containers alone. An updater someone else runs on the same Docker host is their own tool, though: the original Watchtower without a scope still updates TaruBot's containers, and stops TaruBot's updater as a duplicate when it starts. Running containers get changed labels only from `up -d`. A missing name (no `web` profile) is skipped, and a stopped container is left alone. `--include-restarting` also replaces a bot that crash-loops, so deploying the earlier version rolls back even a release that never stays up. Watchtower needs the Docker socket, which is **root on that Docker host**; only this pinned image gets it. It pulls anonymously, so the release package must stay public.
- **The proxy** doesn't depend on the bot: it keeps serving the offline page while the bot is swapped, and follows `web-production` in the same package the same way.

Every command below uses this shell function; replace the placeholder, and for staging use staging's own copy and `docker-compose.staging.yml`:

```sh
tb() { docker compose --env-file <private settings copy> -f docker-compose.production.yml "$@"; }
```

## First start and the one-time cutover

### A new runtime

1. Prepare the managed database, a backup bucket with [the lifecycle](#backups-and-restore) applied, an age key pair (the public key in `BACKUP_AGE_RECIPIENTS`; the private key with the owner, plus one offline copy) and the settings copy. The `production` tags must exist in the public release package, which the first Deploy creates ([owner settings](#owner-settings-in-github)).
2. `tb up -d --pull always`. On an empty database the bot applies every migration without a pre-migration backup (there is nothing to back up yet, and it logs that at info), takes the writer lease, registers its commands and becomes ready. Production refuses to migrate at all without backup settings.
3. Check `tb ps` (the bot healthy, Watchtower running, `tarubot-web` healthy with the web profile), `/version` in Discord, and the log lines `Database writer lease acquired` and `Commands registered`. Take the first backup with `tb run --rm -T tarubot bun dist/scripts/backup.js`; `tb run --rm -T tarubot bun dist/scripts/restore.js list` then shows it.

### From the host-installed entry (2.45.x)

Publishing 2.46.0 and approving its Deploy only creates `production` and `web-production` in the release package, which nothing follows yet: the running 2.45.x is untouched. The release package needs two owner steps around that first Deploy:

1. **Before approving it, create the release token:** a classic personal access token of the `deconfined` account with only `write:packages` (which brings `read:packages`) and an expiry you track. Open [a new classic token](https://github.com/settings/tokens/new?scopes=write:packages&description=TaruBot%20release%20channel) and **untick `repo`**, which GitHub ticks beside `write:packages`: Deploy refuses a token holding any other scope ("The RELEASE_REGISTRY_TOKEN secret of the production environment may hold write:packages and read:packages only: …"), since `repo` would let the secret read and write every repository the account can. Add it as the environment secret `RELEASE_REGISTRY_TOKEN` of both `production` and `staging`, never as a repository or organization secret. Without it, Deploy refuses before anything else ("Deploy needs the RELEASE_REGISTRY_TOKEN secret of the production environment: …").
2. **After it, configure the package** it created, `ghcr.io/deconfined/tarubot-release`, which GHCR makes private: make it **public**, since Watchtower pulls anonymously. In its settings, under Manage Actions access, make sure `deconfined/tarubot` has no write access (remove it, or set Read), and turn off inheriting access from the source repository if GitHub offers that: the copied images' `org.opencontainers.image.source` label links the package to this repository.

Then, once, away from the old daily backup's time:

3. **Prepare the settings copy** from the host's `.env`. Add `TARUBOT_IMAGE_REPOSITORY=ghcr.io/deconfined/tarubot-release`, `TARUBOT_IMAGE_TAG=production` and `BACKUP_AGE_RECIPIENTS` (the key in [age-recipients.txt](../ops/age-recipients.txt)); remove `TARUBOT_IMAGE_DIGEST` and `TARUBOT_RESTART_POLICY`. Keep the storage settings, with two checks the old script didn't need: `BACKUP_STORAGE_REGION` is now required (the old script fell back to a default region when it was empty), and `BACKUP_STORAGE_ENDPOINT` must be the bucket's own host, `<bucket>.<region host>` (virtual-hosted style; a path is now a key prefix).
4. **Stop the old project**, bot and proxy: `docker stop --time 40 $(docker ps -q --filter label=com.docker.compose.project=tarubot)`.
5. **Start the new one** with the 2.46.0 manifests: `tb up -d --pull always`. Compose replaces the stopped containers (same project, so the proxy keeps its volumes and certificates); the bot starts from `ghcr.io/deconfined/tarubot-release:production`, with Watchtower beside it. 2.46.0 adds no migration, so nothing migrates.
6. **Check** as for a new runtime, the first `Backup stored` (or one `backup.js` run) and `restore.js list` included.
7. **Clean up** once it runs: remove the host-installed `tarubot-deploy` and `tarubot-backup` entries, their cron entry and the deploy key's `authorized_keys` forced command, then the unused `DEPLOY_SSH_KEY`, `DEPLOY_HOST` and `DEPLOY_KNOWN_HOSTS` values in GitHub. The old daily backup keeps working until it's removed. The other host state can go too, but keep the 2.45.x release worktree until a release after 2.46.0 has run: it is 2.46.0's only way back.

Deploy can't move a channel to 2.45.x or earlier, which have no `web-X.Y.Z` image ("Release X.Y.Z is not published as both …"), so going back from 2.46.0 to 2.45.x is always stopping the new project (`tb down`, which keeps the proxy's volumes) and starting 2.45.x from its recorded worktree with the [previous runbook's command](https://github.com/deconfined/tarubot/blob/672a755a1b06874e6dd87f9b4ed02cd9568469dc/docs/DEPLOYMENT.md#everyday-observation-and-outcomes). Staging moves the same way, with `staging`.

## Everyday operations

- **What runs:** `/version` in Discord, the heartbeat, `tb ps`, and `docker inspect tarubot --format '{{index .Config.Labels "org.opencontainers.image.version"}}'`.
- **Logs:** `tb logs tarubot` and `tb logs watchtower`. The bot logs `Migrations applied` (the files; `restorePoint`, a moment after the previous bot's last write and before the migration, for point-in-time recovery; and `backup`, the pre-migration dump's key), `Backup stored`, `Commands registered`, `Modules loaded` and `Database writer lease acquired`. A `LOG_LEVEL` above `info` hides them without anything being wrong.
- **Readiness:** the container's health is `/health/ready` (database, writer lease and Discord); in Discord, `/sync status` and `/config validate`. Effects may stay paused on staging. Lodestone and visibility diagnostics are informational; an incomplete upstream roster is never an empty roster.
- **Deploy a release:** publication asks for it. Any published version can also be dispatched: **Actions → Deploy → Run workflow**, branch `main`, the target and the version, then approve. Only a dispatch can move a channel back to an earlier version. Agents dispatch only when the owner asks in that session.
- **Change a setting:** edit the copy, then `tb up -d`. Never `restart` to reload settings: a restarted container keeps its old environment.
- **Run a tool** as a one-off container of the bot's service, always naming the tool, because a `run` without a command starts a second bot: for example `tb run --rm -T tarubot bun dist/scripts/commands.js list`. The tools (`migrate.js`, `register.js`, `commands.js`, `backup.js`, `restore.js`, `check-restore.js` and the rest of the site's [tools page](../site/src/content/docs/deploy/tools.md)) obey the [tool profiles](CONFIGURATION.md#maintenance-tool-profiles). `register.js --global` is needed only to repair production's command set between releases.

## When a release doesn't come up

A successful Deploy means only that the tags moved. Look at `/version` and `tb ps` about five minutes later.

When the bot's migration step fails at startup with migrations pending (backups aren't configured on production or staging, the pre-migration backup fails, or a migration fails), the bot stops cleanly, holding no writer lease, transaction or connection. It logs one error line, `Startup migration failed; waiting before exiting, so a restart doesn't repeat it (and its pre-migration backup) at once`, with the failure's `code` and, for a known failure, its message as `diagnostic` (a failed migration names its file and SQLSTATE: `Migration <file> failed (SQLSTATE <code>); nothing was applied.`), or another error's own `errorCode` (such as `ECONNRESET`), then waits 10 minutes before it exits, and Docker starts it again. So a failing release retries about every 10 minutes and stores at most about six pre-migration backups an hour, not one per restart. During the wait the container runs, unhealthy (its health port is closed). A stop ends the wait at once: Watchtower's swap to a rolled-back tag, `tb stop tarubot`, or `tb up -d` after fixing a setting. A failure before anything is pending takes no backup and exits at once: the deployment guard refuses, an applied migration file was changed, another writer holds the lease, or the database can't be reached, so the bot is back within a minute of the database. So does a failure after the migration, such as the Discord login. Docker restarts the bot within a minute, so that start repeats until it's fixed or rolled back.

**Rolling back** is dispatching Deploy with the earlier version (a publication never moves a channel back); Watchtower replaces the failing container, crash-looping or not. That works whenever the failing release changed nothing in the database: it failed before migrating, its backup or migration failed (nothing applied), or it has no migration. Deploy moves a channel only to 2.46.0 or later; 2.46.0 itself goes back to 2.45.x [the cutover's way](#from-the-host-installed-entry-245x). A release that **did** migrate can't be rolled back that way, because the previous release refuses the newer schema by itself. Then fix forward with a new release, or restore the pre-migration backup (`Migrations applied` names it) into an empty database and point the bot at it ([backups and restore](#backups-and-restore)).

The bot's signs below for a pending migration (backups not configured, a failed pre-migration backup, a failed migration) are each followed by that pause line; the others exit at once.

| Sign (in `tb logs tarubot` unless noted) | Meaning | Do |
| --- | --- | --- |
| Deploy's log: `Deploy needs the RELEASE_REGISTRY_TOKEN secret of …`, `GitHub refused` / `GHCR refused` `… RELEASE_REGISTRY_TOKEN …`, or `The RELEASE_REGISTRY_TOKEN secret of … may hold write:packages and read:packages only` | That environment's release token is missing, expired, revoked or holds another scope (or GitHub or GHCR didn't answer); no tag moved | The owner [replaces the token](#rotation-and-host-loss) in that environment, then re-runs |
| Deploy's log: `A publication never moves production back from <current> to <version>; …` | An older release's publication after a newer one went out; no tag moved | Nothing; to go back on purpose, dispatch Deploy with that version |
| The tags moved, but `/version` shows the old release after 5 minutes | Watchtower isn't running, can't pull, or follows another tag | `tb logs watchtower`; check `TARUBOT_IMAGE_REPOSITORY` and `TARUBOT_IMAGE_TAG`, the container names and scope labels (`tb up -d` sets them) and that the release package is public |
| The bot exits at startup naming a setting | A setting the bot validates is wrong; the database is untouched | Fix the setting and `tb up -d`, or roll back |
| `Backups aren't configured (BACKUP_STORAGE_ENDPOINT is empty), and the production profile never migrates without a pre-migration backup, …` | A migration is pending and backups are off: nothing applied | Set the backup settings and `tb up -d` |
| The pause line's `diagnostic` is `Backup failed at: <stage>…` (the backup check also gets `/fail`; no issue report is filed) | The pre-migration backup failed (at `settings`, the message names the settings at fault): nothing applied | Fix the storage settings, credentials or recipients, or roll back |
| `Migration <file> failed (SQLSTATE <code>); nothing was applied.` | The migration failed and rolled back, `57014` past the 15-second statement limit, `23xxx` on rows it didn't expect | Roll back; either is a release defect |
| `Modified applied migration: <file>` | The image's copy of an applied migration differs from what the database applied: nothing applied | Roll back; applied migrations are immutable |
| `A TaruBot writer (database process N) holds the writer lease, so … migration(s) were not applied` | Another bot holds the lease: a second runtime, or a `run` without a tool command | Find and stop it (`docker ps -a`); never run two |
| Readiness stays unready with `writerLease: false` | A previous writer still holds the lease | As above; the lease frees when its process exits |
| `Schema version/checksum mismatch. Use matching versioned migrations and application image.` | An older image met a database migrated past it | Deploy the release whose migrations the database has, or a newer one, never an older one |
| An issue report for `command registration` | Discord refused the command set; the bot runs with the previous one | Fix it in the next release; `commands.js list` shows what Discord holds |

## Backups and restore

The bot takes its own backups (2.46.0): daily at `BACKUP_TIME_UTC` (default `03:00`, UTC) while it holds the writer lease, and one immediately before it applies migrations. `tb run --rm -T tarubot bun dist/scripts/backup.js` takes one now, prints its keys and sizes as JSON and exits non-zero on failure; it doesn't take the writer lease, since `pg_dump` reads one consistent snapshot. The settings are in [configuration](CONFIGURATION.md#backup-settings).

The `rehearsal` profile never backs up. Its `*_rehearsal` database is disposable, and a one-off container of production's service carries production's backup settings, so its backup would become the newest object in production's bucket, the one `restore.js` takes as `latest`. So neither the bot nor `migrate.js` takes a pre-migration backup under that profile (they log `No pre-migration backup: a rehearsal database is disposable`), and `backup.js` refuses it.

Each backup streams `pg_dump` (the PostgreSQL 18 client, custom format, `--no-owner --no-privileges`) through age encryption straight into a multipart upload; no plaintext touches a disk or a log. A failed dump, an encrypted dump of 4096 bytes or less, or a stored size that differs from the bytes sent fails the backup. The layout is the one the lifecycle rules and the owner's age identity already work with:

- `daily/tarubot-<YYYYMMDDTHHMMSSZ>.dump.age`: the encrypted dump;
- `monthly/tarubot-<stamp>.dump.age`: the same ciphertext, on the 1st of the month (UTC);
- `env/tarubot-env-<stamp>.age`: an encrypted copy of the bot's settings.

The settings copy holds every variable the container received (`*_FILE` secrets resolved, runtime variables such as `PATH` and `HOME` left out), `MODMAIL_KEY` included, as a Compose-compatible env file. It rebuilds a lost runtime and recovers a lost mod mail key, and so **whoever holds the backups' age identity can read every mod mail case in them**: the owner's deliberate trade-off (2026-10-11).

Every file is encrypted to `BACKUP_AGE_RECIPIENTS`. Production's public key is published in [age-recipients.txt](../ops/age-recipients.txt); the private key stays with the owner, with an offline second copy. Backups are ordinary age files, which the `age` command line opens too. [bucket-lifecycle.xml](../ops/bucket-lifecycle.xml) keeps `daily/` and `env/` for 30 days and `monthly/` for 365, and aborts incomplete multipart uploads (a backup cut off part-way) after a day; the owner applies it to each bucket. Production and staging each have their own bucket, credentials and recipients; never point both at one bucket. The key pair needs read and write on its bucket (the monthly copy is the daily object read back, and `restore.js` lists and reads), so it can delete too: keep independent copies, since a bucket in the same provider account isn't independent disaster recovery. These files don't prove the live configuration; the owner checks the lifecycle and the first backups.

With `HEALTHCHECKS_BACKUP_URL` set, a backup pings `<url>/start` with `backup starting`, then `<url>` with `<daily key>: <n> bytes; <env key>: <m> bytes`, or `<url>/fail` with `backup failed at: <stage>`, the stage being `settings`, `dump`, `settings-copy` or `upload`. Pings are best effort and never fail a backup. A failed daily backup also files an issue report. A stop abandons a running backup (`pg_dump` killed, upload aborted) and leaves no object. It sends no `/fail`, since nothing broke: its `/start` stays open until the next backup succeeds, and healthchecks.io marks the check down by itself if none does within the check's grace time.

### Restore a database

Restore is `restore.js`, a one-off container of the same image, which needs the backup storage settings and, for a database, an empty target. The age identity (`AGE-SECRET-KEY-1…` lines; `#` comments are fine) goes on standard input only, never in an argument or a setting.

1. **Choose the source.** `tb run --rm -T tarubot bun dist/scripts/restore.js list` lists the `daily/`, `monthly/` and `env/` objects with their sizes, newest first. To undo a migration, the dump `Migrations applied` names is the last state the previous release wrote. Managed point-in-time recovery to its `restorePoint` is the other way back, where configured and proven: a timestamp alone doesn't prove usable PITR, and a fork needs fresh address, CA and access checks.
2. **Prepare an empty target** on PostgreSQL 17 or newer (TaruBot runs 18): the image's `pg_restore` 18 sets `transaction_timeout`, which older servers reject, so `restore.js` refuses an older target before it reads anything. Production restores into `tarubot_restore` on the primary's cluster, or `tarubot` on another cluster; the tool's guard refuses anything else, and staging has no restore target. Never restore over the live database: `restore.js` refuses a target whose `public` schema has tables. Keep unrelated clients out (revoke `PUBLIC` `CONNECT` and `TEMPORARY` as appropriate) and keep the provider's monitoring access.
3. **Restore.** Put `RESTORE_DATABASE_URL` (and `RESTORE_DATABASE_CA_CERT`, when its CA differs from the primary's) in a second private file for this run only, then:

   ```sh
   docker compose --env-file <private settings copy> --env-file <private restore settings> \
     -f docker-compose.production.yml run --rm -T tarubot \
     bun dist/scripts/restore.js database <daily/… key, monthly/… key or latest> < <age identity file>
   ```

   `pg_restore --no-owner --no-privileges --exit-on-error --single-transaction` loads it, so a failure leaves the target empty. It prints `Restored <key> into <host>/<database>; schema head <file>.` and what it closed.

Before any bot starts on a restored database, two things must happen, and `restore.js` does both in one transaction: it signs everyone out of the dashboard with `DELETE FROM web_sessions`, since the backup would otherwise revive sessions ended since it was taken ([persistence](PERSISTENCE.md#web-sessions)), and it closes the members' role changes the backup caught waiting, so the restored copy never replays older choices over newer ones; the database then clears the role IDs they held ([persistence](PERSISTENCE.md#self-service-role-menus)). Members save again if they still want them. After a restore made any other way, such as a point-in-time fork, run both yourself before any bot starts: `DELETE FROM web_sessions`, then

```sql
UPDATE jobs SET status='succeeded', completed_at=now(), lease_until=NULL, last_error=NULL,
       result='{"skipped":"restored"}'
 WHERE kind='roles.self' AND status IN ('queued','running','blocked','disabled');
```

4. **Fence the old writer:** `tb stop tarubot`. Watchtower leaves a stopped container alone. One application runs in one place, so no bot may run against the old database once one runs against the restored one.
5. **Point the bot at it.** Set `DATABASE_URL` in the settings copy to the restored database (`tarubot_restore` is a database name the production profile accepts). If you restored because a release failed, first deploy one that works on the restored schema, usually the previous one. Then `tb up -d --pull always`. An image newer than the dump migrates it, after its own pre-migration backup.
6. **Check what a restore can't bring back.** Mod mail reads only with the same `MODMAIL_KEY` (`restore.js settings` recovers it), and cases that expired since the backup come back until the next retention pass deletes them ([persistence](PERSISTENCE.md#mod-mail)). The restored pauses can differ from the current ones, so officers check the Moderation page ([persistence](PERSISTENCE.md#pauses)). The status page's samples need nothing ([persistence](PERSISTENCE.md#status-samples)). Discord effects already sent can't be undone, and update-post baselines may need the owner's correction to avoid repeat announcements. Verify readiness, the command inventory and the data, and keep the source database until the restore is accepted.

`check-restore.js` still compares two databases row for row, for a drill against a source nothing has written to since the dump. Its exact comparison fails on `jobs` or `web_sessions` once the closing statements changed them: after `restore.js`, its output says whether they changed anything; after a manual restore, run the check before the closing statements. Record a drill's release, commit, outcome and anything skipped in an issue, not here.

### Recover the settings

`tb run --rm -T tarubot bun dist/scripts/restore.js settings <env/… key or latest> < <age identity file> > <new settings copy>` writes a decrypted settings copy, ready for `--env-file`. It holds the project's own settings too (`TARUBOT_IMAGE_REPOSITORY`, `TARUBOT_IMAGE_TAG` and `COMPOSE_PROFILES`), so `docker compose --env-file <new settings copy> -f docker-compose.production.yml up -d` starts the project again as it was, the web profile included. It holds every secret: create it with `umask 077`, keep it at mode 600 and never in a checkout. Always run it with `--rm`: Docker keeps a container's output in its log until the container is removed. When the runtime and its settings copy are both gone, the image alone runs it, with only the four `BACKUP_STORAGE_*` settings in a private file (one `NAME=value` per line, no quotes):

```sh
umask 077
docker run --rm -i --env-file <private storage settings> ghcr.io/deconfined/tarubot-release:production \
  bun dist/scripts/restore.js settings latest < <age identity file> > <new settings copy>
```

## Optional dashboard

The [site installation guide](../site/src/content/docs/deploy/install.md#optional-https-dashboard) owns the DNS, OAuth, port and public verification recipe. In the settings copy, `COMPOSE_PROFILES=web` selects the bundled proxy (set it there rather than with `--profile web`, so the backups' settings copy carries it), `WEB_PUBLIC_ORIGIN` is shared by the bot and the proxy, `WEB_PORT` (default `8080`) stays private, and `DISCORD_CLIENT_SECRET` belongs to the existing application. The proxy is the release's own web image, so its Caddyfile and offline page come with the release and nothing is mounted. It publishes ports 80 and 443. An external HTTPS proxy, with the profile off, routes privately to the bot's web port instead.

- **Enable or change** the origin, secret or port: prepare DNS, the firewall and the exact `/auth/callback` redirect in Discord, edit the copy and `tb up -d`, which recreates the bot and the proxy with the new settings.
- **Disable** the bundled proxy: clear the profile, then `tb --profile web stop caddy` and `tb --profile web rm -f caddy`. Keep the `caddy_data` and `caddy_config` volumes; never `down -v`. To turn the dashboard off as well, clear its origin and secret and `tb up -d`.
- The proxy's health checks its own admin endpoint and the bot's private web readiness. It doesn't prove public DNS, certificate issuance, HTTPS redirects or OAuth: check the public origin with trusted TLS and an authorized Discord sign-in, following the site's recipe.

Every member and guest of a served server can sign in, for My roles and Mod mail. Before production members use it, the owner confirms (owner decision Q1, 2026-10-09; agents run none of these steps):

- the web is enabled in production: the origin, the bundled or external HTTPS proxy, the exact `/auth/callback` redirect in Discord, and AAAA as well as A records;
- TaruBot no longer holds Administrator in the server: `/config validate` says it's no longer needed after `/setup overrides`, and the owner removes it. The code refuses members and guests until then;
- on staging, an account that never authorized the application signs in with `prompt=none`. If Discord refuses it, a consent fallback is built and passes the same check first;
- Discord changes are live, TaruBot's role sits as the [officer guide](../site/src/content/docs/admin/roles.md#where-tarubots-role-sits) says, the "Role menu" health check is clean, and the restore steps above carry their sign-out and role-choice steps.

## Rotation and host loss

If GitHub is unavailable, the runtime keeps running the release it has. A deploy by hand still needs the owner's explicit go-ahead: verify the release's [provenance](#signed-build-provenance), set `TARUBOT_IMAGE_REPOSITORY=ghcr.io/deconfined/tarubot` and `TARUBOT_IMAGE_TAG` to its exact version (version tags live only there, and the proxy follows `web-X.Y.Z`), `tb up -d --pull always`. Switch back as soon as Deploy works again, in this order: first dispatch Deploy with the version running by hand and check its summary, so the channel names it; only then set both back (`ghcr.io/deconfined/tarubot-release` and `production`) and `tb up -d`. Switching back first would start whatever the channel named before. Don't stay on the version tag: publication never moves an `X.Y.Z` tag, but any workflow of the repository could.

- **The release token:** before `RELEASE_REGISTRY_TOKEN` expires, the owner creates a new classic token with only `write:packages`, `repo` unticked ([as at the cutover](#from-the-host-installed-entry-245x)), replaces the secret in both environments, then revokes the old token. An expired or revoked token makes Deploy refuse ("GitHub refused the production environment's RELEASE_REGISTRY_TOKEN, …"), and nothing moves.
- **Runtime credentials:** update the copy, `tb up -d`, verify, then revoke the old credential. Change a database password in one window.
- **Backup credentials:** the same; check the next backup.
- **The age key:** add the new public key to `BACKUP_AGE_RECIPIENTS` (for production also to [age-recipients.txt](../ops/age-recipients.txt), through a reviewed change), `tb up -d`, check that the new identity opens the next backup, then remove the old key from both and `tb up -d` again. Earlier backups stay encrypted to the old key, so keep its identity until they have expired (a year for monthly copies) or re-encrypt them.
- **Mod mail key:** `MODMAIL_KEY` has no rotation in 2.43.0. A different key makes every existing case unreadable (the pages say so and file one issue report), so never replace it while cases matter, and recreate the container with the same value after any settings change. Keep it in the settings copy and one more copy outside the runtime; losing every copy loses every case. Each backup's encrypted settings copy carries it next to the dump, to the same age recipients, so that copy is how a lost key is recovered, and **whoever holds the backups' age identity can read every mod mail case in them**. That's the owner's deliberate trade-off (2026-10-11): a lost host restores fully, cases included. Guard the age identity accordingly. Production and staging each have their own.
- **Suggestion App:** production only; verify settings and recreation before revoking its old key. An empty client ID disables suggestions without blocking startup.
- **Discord token:** one application runs in one place. Stop the old runtime before a token moves or a replacement starts.
- **Host loss:** the managed database outlives a lost Docker host, and nothing else of TaruBot's was on it. Make sure the old host can't start the bot again (remove its containers if you still can, or revoke its database access), then start the same project on a new host from the settings copy, or one [recovered from a backup](#recover-the-settings). Losing a host doesn't authorize replacing the database.

## Owner settings in GitHub

The owner maintains these; agents change none of them ([AGENTS](../AGENTS.md)).

- **`main`:** the owner's code-owner review, required current checks, merge commits, signed commits and dismissal of stale approvals.
- **Environments `production` and `staging`:** the sole required reviewer `User: deconfined`, `prevent_self_review=false` so the owner can approve their own release, `can_admins_bypass=false`, and a custom deployment branch policy holding only `main`. GitHub enforces them. Deploy refuses unless its job was held for that approval in the same attempt, so an environment without a required reviewer can't deploy. Each environment holds one secret, `RELEASE_REGISTRY_TOKEN`, and no variables; after the cutover, remove `DEPLOY_SSH_KEY`, `DEPLOY_HOST` and `DEPLOY_KNOWN_HOSTS`.
- **`RELEASE_REGISTRY_TOKEN`:** a classic personal access token of the `deconfined` account with only `write:packages` (which brings `read:packages`; Deploy refuses any other scope, and GitHub ticks `repo` beside it unless you untick it), with an expiry the owner tracks and renews ([rotation](#rotation-and-host-loss)). It is the only credential that moves a channel tag, so it is an environment secret of `production` and `staging` alone, never a repository or organization secret, which would reach every workflow on any branch. Publication's call of Deploy binds only its name; the approved environment job resolves the environment's own value. A classic token's `write:packages` covers every package of the account, `ghcr.io/deconfined/tarubot` included ([accepted limits](THREAT_MODEL.md#accepted-limits)).
- **Repository variables** `DEPLOY_ENABLED` (production) and `STAGING_DEPLOY_ENABLED` (staging): only the value `true` lets Deploy run. A run takes their values when it starts, so turning one off doesn't stop a run already waiting or approved; reject that deployment instead. Keep a target off until its runtime is ready.
- **The packages.** `ghcr.io/deconfined/tarubot` holds the releases: public, with this repository's workflows allowed to write to it (publication tags it with the workflow's own token). `ghcr.io/deconfined/tarubot-release` holds the channel tags `production`, `web-production`, `staging` and `web-staging`: the first Deploy creates it, private, and the owner makes it public, since Watchtower pulls anonymously, and makes sure, under its Manage Actions access, that this repository has no write access, inherited from the source repository or not ([the cutover](#first-start-and-the-one-time-cutover)).
- **Code scanning:** the deleted SSHFP lab held the repository's only Python files. If a ruleset requires a Python analysis, update it.

## Staging

Staging rehearses the same path on its own Docker host, with DevBot's application and declared test guild (from `src/config/deployment.ts`), the managed `tarubot_staging` database and user, its own bucket and age recipients, and settings from `staging.env.example`, never production's. Keep `ENABLE_EFFECTS=false` until an effects test is approved, and leave production's suggestion App credentials out. DevBot runs in one place only: fence any other copy before starting the staging runtime or moving its token ([DevBot](DEV_GUILD.md)).

- **Deploy:** the owner dispatches **Actions → Deploy → Run workflow**, branch `main`, `target: staging` and a published version, then approves the `staging` environment; `STAGING_DEPLOY_ENABLED` must be `true`. Publication never dispatches staging. Staging's Watchtower follows the `staging` tags of the release package (`TARUBOT_IMAGE_REPOSITORY=ghcr.io/deconfined/tarubot-release`, `TARUBOT_IMAGE_TAG=staging`).
- The bot registers commands only in DevBot's guild, so staging never touches production's global set. Like production, it refuses to migrate without its own backup settings.
- Staging has no restore target: `restore.js database` and `check-restore.js` refuse there, and resetting staging is an owner step. Perform any isolated staging restore drill with the provider's own tools, never by relabelling the bot as unmanaged.
- Test plans come with the image ([startup test-session plans](DEV_GUILD.md#startup-test-session-plans)).
- Staging success doesn't authorize a production Deploy or prove production's settings, backups or readiness; a waiting production approval stays unapproved until production is ready.
