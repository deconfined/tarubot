# Configuration code reference

Strict JSON files use this companion documentation rather than nonstandard JSON comments. TOML, environment examples, Docker/Compose, SQL, and TypeScript carry inline comments alongside their implementation.

## `package.json`

- `type: module` establishes the first-party ESM boundary.
- `packageManager` and `engines.bun` pin the development/production runtime.
- `build` runs `scripts/build.ts`, which removes stale generated modules and compiles TypeScript. Since 2.21.0 nothing else is built: the parser worker runs from the compiled output.
- `typecheck` includes source, tooling, tests, and declaration contracts; `lint` enforces first-party ESM and the explicit-any rule.
- `format` and `format:check` use the shared Biome rules.
- `start` executes the compiled composition root.
- `test:unit`, `test:contract`, and `test:integration` separate pure/module behavior, external boundaries, and real PostgreSQL persistence. `test:docker` supplies a disposable complete environment.
- `commands:register` discovers command definitions and explicitly overwrites the selected development/production inventory. It confirms the token's application first and refuses `--global` while `TEST_GUILD_ID` is set.
- `commands:list` and `commands:clear-guild` run `scripts/commands.ts` over Discord REST only. `list` reads back the global scope and every guild scope and exits 2 unless the declared scope matches exactly and every other scope is empty. `clear-guild GUILD_ID --application APP_ID` prints a dry run with a fingerprint and clears that one guild scope only with `--confirm FINGERPRINT`; nothing clears the global scope.
- `selectors:check` compares `bun.lock`'s `lodestone-css-selectors` commit with upstream HEAD. `selectors:update` advances it, records the commit in `src/infrastructure/lodestone/upstream-revisions.json`, and checks the build and contracts. The running bot follows HEAD live regardless; these refresh only the set bundled with a release.
- `ci:version` validates the SemVer increment and changelog entry before publication. Since 2.30.0 only `main` publishes (`publish.yml` has no tag trigger); the script's check that a `v*` tag matches `package.json` is kept for a manual run on a tag and no longer runs in CI. `test:fixture` generates invented migration input for public CI under `.cache/ci/legacy.sql`; `LEGACY_FIXTURE_PATH` selects it for integration or Docker tests.
- Migration/import/snapshot/acquisition/preview/activation/retry scripts execute compiled one-shot tooling. Their file headers explain their maintenance boundaries. For production and rehearsal, run the compiled files directly with `bun --env-file` rather than these `bun run` aliases (see [Maintenance-tool profiles](#maintenance-tool-profiles)).
- Runtime dependencies support active bot operations, including pinned `drizzle-orm` with the existing `pg` driver, and since 2.21.0 the parser's `linkedom` and the `lodestone-css-selectors` data the bundled set imports. TypeScript tooling and Biome are development dependencies.

`bun.lock` is generated by Bun and pins transitive packages and source revisions. Dependency changes are made through Bun and verified with frozen-lockfile installation.

The parser is first-party (`src/infrastructure/lodestone/parser.ts`, since 2.20.0; there is no Nodestone, and since 2.21.0 no sidecar). Selectors keep a floating `#HEAD` manifest reference that `bun.lock` pins for the bundled set, whose commit `src/infrastructure/lodestone/upstream-revisions.json` records; a unit test checks the two agree. The running bot follows HEAD live (2.19.0).

## `tsconfig.json`

`resolveJsonModule` includes the package manifest in compiled output. `/version` uses that build-local copy, so its reported SemVer identifies the deployed application. The source manifest and [CHANGELOG.md](../CHANGELOG.md) define the version policy and milestone numbering.

| Option | Reason |
| --- | --- |
| `target: ESNext` | Emit modern JavaScript supported by pinned Bun |
| `module`, `moduleResolution: NodeNext` | Native ESM semantics with explicit runtime-relative `.js` imports |
| `strict` | Require explicit null/error handling and safe inference |
| `noUncheckedIndexedAccess` | Array/map lookups can be absent |
| `exactOptionalPropertyTypes` | Omitted properties differ from explicitly undefined values |
| `noImplicitOverride` | Make subclass contract changes visible |
| `noFallthroughCasesInSwitch` | Prevent accidental dispatch fallthrough |
| `verbatimModuleSyntax` | Preserve ESM and require explicit type-only imports |
| `forceConsistentCasingInFileNames` | Keep imports portable across host/container filesystems |
| `skipLibCheck` | Leave separately packaged dependency declaration internals outside first-party checking |
| `types: [bun]` | Type Bun APIs and test facilities |
| `rootDir`, `outDir` | Preserve module directory layout under `dist/` |
| `sourceMap` | Keep production diagnostics traceable to TypeScript source |
| `include` | Check all first-party source, operational scripts, and tests |

`tsconfig.build.json` inherits those guarantees and emits application and tooling code, with the JSON files it imports. Tests are independently type-checked and executed through Bun. Declaration-only files describe narrow dependency boundaries.

## `biome.json`

- File selection excludes dependencies, generated output, working caches, imported data, and the requirements contract.
- Formatting uses two-space indentation, double quotes, semicolons, and a 100-column target.
- `noCommonJs` and `noExplicitAny` enforce the first-party module/type contracts.
- Automated import/code assists are disabled so the formatter does not silently restructure source.

## Runtime configuration

`.env.example` comments identify credentials, scope, activation, timing, health, and resource budgets. Validation lives in `src/config/env.ts` and the Lodestone adapter (`src/infrastructure/lodestone/client.ts`). Every setting is described on the documentation site's [configuration page](../site/src/content/docs/deploy/configuration.md), including the Lodestone settings. `RESTORE_DATABASE_CA_CERT` optionally gives `check-restore`'s `RESTORE_DATABASE_URL` its own CA (a PITR fork is a new cluster); empty reuses `DATABASE_CA_CERT`. `MIGRATE_WRITER_WAIT_SECONDS` (default 90, 0–600) bounds how long `migrate.js` waits for a stopping bot to release the writer lease before it refuses a pending migration ([the single writer](../site/src/content/docs/deploy/operations.md#single-database-writer)).

`production.env.example` is the tracked template for the production maintenance-tool environment. It lists every `.env.example` key with production values, a direct-port (27520, Linode) managed-cluster URL placeholder, a quoted multi-line CA placeholder, and an empty token, so no development value can fill a gap. Copy it outside any checkout (for example `~/tarubot-cutover/production.env`, mode 600); never name the copy `.env` or `.env.production`. Git and Docker ignore `*.env` files; the templates stay tracked.

**Staging settings (2.32.0, [#50](https://github.com/deconfined/tarubot/issues/50)).** `staging.env.example` is the template for `~/tarubot/.env` on the staging host, where DevBot's application will run as a rootless Quadlet unit ([HOSTING.md](HOSTING.md#staging-host-50)). Fill a copy with staging-only values, never from a production copy, keep it outside any checkout (mode 600), and send it over SSH stdin as the template's header shows. It holds:
- `TARUBOT_IMAGE_TAG`, exactly one plain line, which deploys rewrite;
- `DATABASE_URL` for staging's own database and role, both `tarubot_staging`, on the managed cluster's direct port 27520, with the cluster's CA in `DATABASE_CA_CERT`;
- `DISCORD_TOKEN`, left as its placeholder until the DevBot move, when the owner resets DevBot's token and puts the new one only here;
- `TEST_PLAN_CHANNEL_ID`, and staging's own reports token, heartbeat URL, and backup bucket, key and check, each never production's.

The staging target, `ops/quadlet/staging/target.env`, fixes DevBot's application ID, `TARUBOT_ENVIRONMENT=staging`, the test guild and public test replies whatever `.env` says, and forces `GITHUB_APP_CLIENT_ID` empty, so `/suggest` stays off on staging. The playbook also refuses any `GITHUB_APP_*` value in staging's `.env`. The template leaves out the optional tunables (`LOG_LEVEL`, the intervals, `LODESTONE_*`, `GITHUB_REPORTS_REPO`), so the bot's defaults apply. Add one only with a value: `ops/quadlet/check-env.sh` refuses a set but empty setting that Compose would have replaced with its default. systemd and Compose must read every line the same way, so `check-env.sh --syntax` refuses a `$` or a backslash in a value, inline comments and `export` lines; percent-encode such characters in the URL.

**Issue reports (2.18.0).** `GITHUB_REPORTS_TOKEN` is a fine-grained GitHub token limited to the reports repository's issues (read and write). `GITHUB_REPORTS_REPO` names that repository (`owner/name`, default `deconfined/tarubot-reports`). Only the running bot uses them: set them in DevBot's `.env` and in the production host's `.env`. With the token empty, `/issue` and automatic reports are saved in the database and sent once a token is set and the bot restarts. `production.env.example` lists the token empty, because maintenance tools never send reports; `GITHUB_REPORTS_REPO` keeps its default there, since a repository name isn't a secret. See [the site's monitoring page](../site/src/content/docs/deploy/monitoring.md#issue-reports). Since 2.28.0 `GITHUB_REPORTS_REPO` must not name TaruBot's public repository (`deconfined/tarubot`, in any case): startup refuses it, so private diagnostics can never go public. On DevBot the same token and repository also take `/suggest` previews.

**Public suggestions (2.28.0).** `GITHUB_APP_CLIENT_ID` and `GITHUB_APP_PRIVATE_KEY` identify the TaruBot GitHub App (App ID 5076273) that opens `/suggest` issues in the public repository `deconfined/tarubot`. The client ID isn't secret; the private key is the PEM GitHub downloads (PKCS#1), written in `.env` as a double-quoted multi-line value like `DATABASE_CA_CERT`. They are production settings: `docker-compose.production.yml` passes them from the host's `.env`, and `docker-compose.yml` (DevBot) never does. DevBot ignores them even when present and previews suggestions into the reports repository with `GITHUB_REPORTS_TOKEN`. With either one empty (or, on DevBot, without the reports token), `/suggest` tells members it is switched off. The key isn't parsed at startup, so a bad key fails only `/suggest`, with a private issue report. `production.env.example` lists both empty, because maintenance tools never post. See the site's [monitoring page](../site/src/content/docs/deploy/monitoring.md#public-suggestions) and, for the app itself (key storage, rotation, the probe and the off switch), [HOSTING.md](HOSTING.md#public-suggestions-the-github-app).

## Container settings

The Compose files hold the containers' security settings (2.30.3, [#51](https://github.com/deconfined/tarubot/issues/51)):

- **The bot.** `docker-compose.yml` runs `tarubot` with `read_only: true`, `cap_drop: [ALL]` and `security_opt: ["no-new-privileges:true"]`, and no tmpfs, because the bot writes no files. The DevBot, source-build and tools overlays inherit these settings unchanged. The source build's `test-plans` mount is read-only.
- **Production.** `docker-compose.production.yml` stands alone, so it repeats the three settings for `tarubot`. It gives the `backup` job the same three, plus a 1 MiB `/tmp` tmpfs (mode 0700) for the CA file `pg_dump` reads.
- **The bundled database.** The `postgres` service keeps Docker's defaults: its entrypoint prepares the data directory as root.

`tests/unit/container-hardening.test.ts` pins these settings. It checks that the two bot definitions agree, and it refuses any overlay that sets them again. [VERIFICATION.md](VERIFICATION.md) has the container tests behind them, and [HOSTING.md](HOSTING.md#container-hardening) covers what they mean for operators.

## Host playbook and Quadlet unit

Since 2.32.0 (#50 part 1) the repository carries the configuration for the Podman hosts ([HOSTING.md](HOSTING.md#staging-host-50)):

- **`ops/ansible/ansible.cfg`.** `inject_facts_as_vars = False`, so a task run as `tarubot` can't return facts that override a setting a later root task reads. `collections_path` and `roles_path` point at `/dev/null`, and `collections_scan_sys_path = False`, so only `ansible.builtin` loads, whatever is installed on the machine that runs it. `interpreter_python` is `/usr/bin/python3`, because ansible-core 2.16 doesn't know EL10 and would guess. `host_key_checking` stays on, and a typo in the inventory fails the run (`unparsed_is_failed`). Pipelining sits under `[connection]`, so the ssh and local connections both send modules over stdin; only the ssh plugin reads `[ssh_connection]`. That is defence in depth, not the boundary: a module run as `tarubot` still unpacks itself into a directory `tarubot` owns. The boundary is `site.yml`'s rule that no root task follows the `tarubot` play, which `tests/unit/playbook.test.ts` pins with the rest of these settings. Ansible reads the file only from a working directory that isn't world-writable, or through `ANSIBLE_CONFIG`, and on a host only ever from a checkout `tarubot` can't write. ansible-core 2.16 refuses to start under `LC_ALL=C`, so run it under a UTF-8 locale such as `C.UTF-8`.
- **`ops/ansible/requirements.txt`** pins ansible-core 2.16.16, the version AlmaLinux 10.2's AppStream ships, by hash, for Python 3.12 as on the hosts. `requirements-lint.txt` adds ansible-lint 26.6.0 for CI, and `.ansible-lint` selects the `production` profile, offline.
- **Host settings** are extra vars only (`-e @host.yml`; `host.example.yml`): `tarubot_role` (`staging` or `production`), `tarubot_hostname`, `tarubot_deploy_key_public`, `tarubot_operator_keys` and `tarubot_root_keys`. The playbook refuses a run where one is missing or malformed. `inventory.example.yml` says only how to reach a host. The real files live outside the repository.
- **`ops/quadlet/`** holds the release's unit (`units/tarubot.container`), the settings every host's container gets (`units/tarubot.env`), each target's settings and drop-in (`production/`, `staging/`), and `check-env.sh`. Its [README](../ops/quadlet/README.md) describes how settings reach the bot. `tests/unit/quadlet.test.ts` checks that the two lists plus the secret names give exactly the bot's settings in `docker-compose.production.yml`, and that the unit keeps #51's hardening. Git and Docker would ignore the three setting lists as `*.env` files, so `.gitignore` and `.dockerignore` list them as exceptions; they hold names and fixed public values only.

## Maintenance-tool profiles

`src/config/deployment.ts` is a deployment-identity guard. Every maintenance tool that touches Discord or PostgreSQL calls it once, after parsing arguments and before any I/O: `migrate`, `register`, `commands`, `snapshot`, `import` (publishing only; dry runs use no credentials), `acquire`, `preview`, `activate`, `retry`, `check-restore`, `discord-inspect`, and `discord-smoke` (DevBot only). The bot runtime itself is unchanged; it checks only that its token belongs to `DISCORD_APPLICATION_ID`. Refusals are `configuration` failures that name settings, hosts, and database names, never a URL, password, or token.

**Profile selection.** `TARUBOT_ENVIRONMENT=production`, `rehearsal` or (since 2.32.0) `staging` selects that profile. `devbot`, or DevBot's application ID `943291473477128243` with the variable empty, selects DevBot. Staging uses DevBot's application too, so only its marker selects it, and the marker is read first. The production application ID `965294750741692416` without an explicit marker is refused. Anything else is `unmanaged` (CI and other developers).

| Profile | Application and scope | Databases |
| --- | --- | --- |
| `production` | `965294750741692416`; `TEST_GUILD_ID` and `TEST_PLAN_CHANNEL_ID` empty and `PUBLIC_TEST_RESPONSES` not true; guild `1036062273631952955` only; the only profile that may register the global command set, and it registers nowhere else (`register.js --guild` is refused) | Managed host only, with a CA, the direct port 27520 (never the 27521 pool), and user exactly `tarubot`. Since 2.32.0 `DATABASE_URL` must name `tarubot`, or `tarubot_restore` after [Restoring a dump](HOSTING.md#daily-dumps) repoints the bot at a same-cluster restore; before, anything but `tarubot_dev`, `*_test` and `*_rehearsal` passed. A restore target is `tarubot_restore` on the primary's host or `tarubot` on another host (a PITR fork). |
| `rehearsal` | As production, but read-only on Discord (registration and command cleanup are refused) | `DATABASE_URL` ends in `_rehearsal`, and a restore target in `_restore_test`. A managed host needs the CA, port 27520, and a user other than `akmadmin`. |
| `staging` | Since 2.32.0 (#50): DevBot's `943291473477128243` with `TEST_GUILD_ID=1040379370159743139`, as under `devbot`; that guild only; commands registered only there; no global registration. Public test replies and a test-plan channel are allowed. | Managed host only, with a CA, port 27520 and a user other than `akmadmin`; `DATABASE_URL` names exactly `tarubot_staging` and connects as the `tarubot_staging` user. There is no restore target (`RESTORE_DATABASE_URL`, so no `check-restore`) and no `--restore-rehearsal`: staging resets its database in place, and its role can't create databases. |
| `devbot` | `943291473477128243` with `TEST_GUILD_ID=1040379370159743139`; that guild only; no global registration | Local host (loopback, the Compose `postgres` service, or Docker's host alias) with an empty CA; `DATABASE_URL` names exactly `tarubot_dev`, and a restore target ends in `_restore_test`. Only `migrate.js --restore-rehearsal` may name a `*_restore_test` copy as `DATABASE_URL`, to rehearse a migration there first ([DEV_GUILD.md](DEV_GUILD.md#backup-and-restore-rehearsal-on-devbot)). Production, rehearsal and staging refuse that flag. |
| `unmanaged` | May not touch either managed deployment's guilds or use its token | No deployment-specific rules |

Staging and production share the managed cluster, so the database name is what tells them apart: the production and rehearsal profiles refuse every database and user whose name starts with `tarubot_staging`, for `DATABASE_URL` and a restore target alike. `tests/unit/deployment.test.ts` covers the staging profile, production's database names and the refusal of staging's, and checks `staging.env.example` against the host's rules.

Every database URL must carry its host, port, user, and database itself; `host`, `hostaddr`, `port`, `user`, `dbname`, and `database` query parameters are refused, and a restore target must differ from `DATABASE_URL`. After authenticating, tools that use Discord confirm that the token belongs to the profile's application before reading any guild or command. `commands.js clear-guild` never touches the profile's own registration scope (DevBot's guild, under `devbot` and `staging`), and under production it clears only guilds the application belongs to.

**Owner action for DevBot.** The DevBot profile requires the local `.env` to point local tools at `…/tarubot_dev`. A `.env` whose `DATABASE_URL` names `…/tarubot` is refused until the owner changes it; the Compose overlay already gives the running bot `tarubot_dev`.

**Launch rule and verified Bun 1.4.2 behavior.** Production, rehearsal and (since 2.32.0) staging runs are refused when an auto-loaded env file (`.env`, `.env.local`, `.env.production[.local]`, `.env.development[.local]`, or `.env.test[.local]`) exists in the working directory and the process was started without `--env-file`. The reasons, each verified with Bun 1.4.2:

- `bun --env-file=FILE` loads only that file; the working directory's `.env` family is not loaded.
- A `bun run` script child reloads the working directory's `.env` for every key the parent did not set, even when the parent used `--env-file`, so development values fill any gap.
- With `NODE_ENV=production` and no `--env-file`, Bun also loads `.env.production`.
- Variables already in the environment, such as shell exports, override the file.

The production invocation is therefore `env -i HOME="$HOME" PATH="$PATH" bun --env-file=PATH dist/scripts/TOOL.js`, from a clean clone of the deployed release, never `bun run` ([MIGRATION.md](MIGRATION.md) E0). Containers have none of these files; the production host's container sets `TARUBOT_ENVIRONMENT=production`, and the staging target sets `staging` for the bot's container, where staging's tools will run too (from 2.33.0).

## Database schema

`migrations/001_initial.sql` documents each domain/table and the important database-enforced invariants. Once applied outside disposable development/rehearsal databases, migration contents—including comments—must remain immutable because startup and migration tooling validate checksums. Add subsequent changes as new numbered migrations and update the expected schema version.

`src/infrastructure/postgres/schema.ts` maps the applied schema for Drizzle queries and inferred record types. SQL migrations remain the deployment authority; there is no automatic schema synchronization or Drizzle Kit push step. The current 2.32.0 source adds no migration and requires `010_status_notices.sql` (from 2.29.0): `guild_users.status_state`, `status_since` and `status_posting`, the per-member state behind the officer status posts (all NULL until a member is first observed). `009_changelog_channel.sql` (from 2.25.0; 2.27.0 and 2.28.0 added no migration) adds `guilds.changelog_channel_id`, where update posts go (NULL is off), and `guilds.changelog_version`, the newest version the guild was told about. `008_issue_reports.sql` (from 2.18.0) adds the `issue_reports` table, which saves each report before delivery. The earlier `007_profile_checks.sql` (from 2.17.0) adds `characters.profile_retry_at`, which paces scheduled profile refreshes, and `characters.profile_missing_at`, the first 404 of the two-404 unlink rule. `006_guest_application_switch.sql` (from 2.15.0) adds the per-guild guest-application switch `guilds.guest_applications_enabled` (off by default; backfilled on for guilds that already had a review channel, except imported guilds still awaiting first activation) and the `guest_grants.ended_at`, `ended_by` and `ended_reason` columns that `/guest reset` sets to end a grant while keeping it as history. The earlier `005_launch_access_policy.sql` (from 2.13.0) added `grandfathered` guest-grant provenance, the once-only first-activation grandfathering marker, and the per-guild role-layout switch (on by default, backfilled off for imported guilds). Channel onboarding still defaults off until `/setup`. See [PERSISTENCE.md](PERSISTENCE.md) for query, connection, and exact-value conventions.
