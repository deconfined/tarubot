# Release-integrated infrastructure pipeline

## Status and scope

This is the implementation specification for the next pipeline, not a claim that it is deployed. [DEPLOYMENT](DEPLOYMENT.md) describes the shipped path. Keep the milestone table below current as code lands. A contributor should need this specification, the code and its tests, not a resumed conversation.

The agreed direction is **safe auto-apply**, using the existing Linode PostgreSQL cluster, AlmaLinux 10 with SELinux enforcing, Ansible and rootless Podman/Quadlet. The documentation site stays in place. Production deployment still requires the owner's GitHub environment approval. Credentials stay in GitHub Actions secrets, never in the checkout, user data or an agent session.

**Initial provider: Linode**, for compute, the existing PostgreSQL cluster and private Object Storage. Object storage conditional writes are not required. Use workflow-serialized writes and verified persistence, not a distributed-lock claim; retain native passphrase-based state/plan encryption and GitHub environment secrets. No external lock service, Secret Manager or KMS is a prerequisite. OVH remains an optional later owner-selected migration, requiring separate review and recovery/cutover acceptance; do not add a second provider or replace the current database for this implementation.

The owner selected **durable automatic trust on first use (TOFU)** for initial SSH enrollment. This accepts possible interception of the first observation. DNSSEC/SSHFP protects subsequent connections; it cannot authenticate that first observation retroactively. Hosts generate their own SSH keys; normal enrollment needs no manual pinning.

Authorization remains unchanged: this document authorizes no live operation, environment change, workflow dispatch, shared-bot restart or Discord write. Do not repurpose approval-gated `infra` to bypass its reviewer. Production's byte-pinned Compose files and `deploy`/`notify` jobs remain unchanged until a separately reviewed cutover; prepare that separately from staging/safety work.

## Target release flow

```text
PR checks + security + code-owner review
  → merged-main validation
  → build AMD64/ARM64 → scan both images → publish → sign exact index digest
  → verify release identity → infrastructure plan → classify
      no changes: continue
      safe changes: apply exact saved plan → verify infrastructure
      review required / invalid: stop automatic promotion
  → verify SSH trust → Configure staging → deploy exact digest
  → staging acceptance for this digest and schema
  → owner's production environment approval
  → reverify release/state/trust → deploy production → verify + notify
```

- Bind version, source/configuration commits, image index digest, publication run, plan digest and policy revision. A mutable tag is not evidence. Preserve exact provenance identity/ref/commit verification and migration immutability.
- PR/fork/suggestion/build/scan code receives no deployment/provider credentials. Pin actions, tools and providers. Separate build registry write from signing OIDC/attestation write permissions.
- Scan each platform's built digest with a pinned scanner for fixable high/critical vulnerabilities. Exceptions are reviewed, bounded, reasoned and expire. Scan errors or expired exceptions block signing/promotion. Candidate blobs may be published before scanning, but no signed/promoted deployable release bypasses it.
- Plan infrastructure for merged releases, including infrastructure-only changes. Documentation-only changes may skip host deployment, not required identity/security verification. Production-only recovery is an explicit reviewed dispatch, distinct from automatic promotion.
- Missing hosts/credentials, skipped jobs, `configured`, `preflight-ok`, `superseded` and green publication never satisfy staging acceptance. Failed/absent staging blocks automatic production promotion.
- Partial apply, stale plan, lost result or uncertain host outcome blocks downstream deployment; do not assume the previous state survived unchanged.

## Safe-plan policy

Classify the **full private `tofu show -json` output**, not the summary or change counts. Return fixed public-safe decision/reason codes and counts only. Missing, malformed, unsupported or contradictory evidence fails closed; never echo arbitrary addresses, provider text, fields or identifiers.

Initial automatic allowlist:

| Change | Decision |
| --- | --- |
| Complete valid plan, recognized no-ops only, no imports | `no-changes` |
| Existing VM display label only; identity, networking, image, power, size and credentials unchanged | `safe` |
| Existing unproxied A/AAAA TTL only, within 300–3600 seconds; zone/name/type/address unchanged | `safe` |
| Existing access list adds only module-managed unchanged hosts' known IPv4 `/32` or IPv6 `/128`, preserving every previous entry | `safe` |
| Import-only adoption, initial VM/DNS/firewall creation, firewall edits, resize/reboot/network/image changes, enrollment/replacement | `review-required` |
| Cluster mutation, access removal/widening, credentials/keys/hash change, delete/replace, unknown critical values or unrecognized resource/field | Never automatic; `review-required` or `invalid` |

Implementation rules:

- Match provider source, type/name, canonical root-module address and configured public role/key. Reject deposed resources, unexpected modules, duplicates, unsupported actions and unknown resource kinds even on no-op. Validate format/version, completion/error flags, checks and resource/output changes; missing lists are not evidence of no changes.
- Compare every before/after field, not selected fields. Allow only named configurable differences, accounting explicitly for computed fields using the pinned schema. Unknown/sensitive configurable differences cannot become safe by omission. Output-only changes also need recognition.
- Unknown new-host addresses are not safe additions. Review host provisioning, then replan once addresses are known. The existing summary's count reconstruction remains presentation only.
- Preserve previous access entries byte-for-byte. Broad CIDRs, unrelated addresses and arbitrary `db_allow_extra` additions need review even without removals. Drift correction outside the allowlist is never automatic.
- Compare private planned/current inputs, including creation-only/ignored keys/hash. Bind both environments' backend identity and inputs to the saved plan. Policy changes require code-owner review.
- Automatic runs have no destroy/access-removal/replace/target/override switch. Sensitive operations require a fresh owner-reviewed dispatch/plan, never a silent fallback from failed automatic policy.

### Plan transfer, credentials and concurrency

Retain enforced native state/plan encryption and one-day encrypted-plan artifacts. Upload no plaintext state/JSON plans, credentials, inventories, trust records or provider logs. Private temporary files use `umask 077` and cleanup on every exit. Before Apply, recheck bytes, release, private inputs, backend binding, freshness and classification; apply the same file, never replan with write credentials.

| Gate | Credentials and authority |
| --- | --- |
| `infra-plan` | Existing main-only read-only planning credentials, no reviewer |
| `infra` | Existing main-only owner-approved writes for imports/builds/sensitive changes |
| Proposed `infra-auto` | Separate main-only write credential environment, owner-provisioned with no reviewer; policy is its execution gate |
| `staging`, `production`, `notify` | Retain target isolation and production approval; enrollment/host secrets load only for their target |

The owner creates/readbacks the safe lane and accepts reviewed workflow code gating its write credentials. Do not remove `infra`'s reviewer. Enrollment tokens need only intended-zone DNS edit and private trust-store access.

Use the shared `infra` concurrency group across every dispatch/release infrastructure writer, including applied-input baseline updates; retain `cancel-in-progress: false` and `queue: max`. Serialize Configure/deploy/enrollment and each target's trust/SSHFP writes in its shared target group. Avoid nested reusable workflows holding the same group while waiting on each other. Recheck obsolete releases before credential gates and after waiting for approval. Superseded/skipped work never counts as acceptance.

This is repository-local single-writer coordination, not a storage lock or distributed lease. Keep native S3 locking disabled; a read-then-PUT lock object or expected-revision check is not compare-and-swap. Saved-plan staleness does not make concurrent provider writes safe. All writers must use these groups and scoped credentials. Before a hand run, the owner fences automation and verifies that no running or queued job can overlap; agents never change workflow/environment controls to create that window. A future backend lock is optional and needs separate review and disposable-lab compatibility tests, not a provider move now.

### Durable control records and interrupted writes

Keep applied-input baselines, operation journals and SSH trust in private encrypted versioned Linode Object Storage, with restricted writers, owner-controlled recovery and tested write/readback visibility. Plan reads records without writing. Each mutable current-generation pointer has one designated serialized writer; per-target enrollment cannot update the shared infrastructure baseline.

1. Write each record under a unique operation/generation key and never intentionally overwrite historical records. This is an append-only convention, not storage-enforced immutability. Bind the record to its role/backend, instance or state identity, previous generation, workflow commit/run and relevant plan/input/policy digests. Preserve state lineage/serial evidence with an applied-input baseline.
2. Under the writer's concurrency group, validate the expected previous generation and absence of an incomplete operation. Initial baseline/enrollment establishment is an explicit owner-reviewed operation; missing records do not mean an empty safe baseline or permission to relearn trust.
3. Before provider, trust or DNS mutation, persist an operation intent and its pending-operation reference, and verify both by exact readback. An intent permits only that operation's bound inputs, not arbitrary recovery writes.
4. After successful Apply and infrastructure verification, persist/read back the completed applied-input baseline, advance/read back its current-generation pointer and then mark/read back the operation as complete. Enrollment similarly persists and verifies trust before authentication and records verified SSHFP publication before completion. Downstream promotion waits for complete evidence.
5. Failed or ambiguous writes, stale/conflicting generations, partial Apply and interrupted pointer/completion updates block subsequent mutation and promotion. Never clear an intent in unconditional cleanup, infer that an absent success record means no remote change, or blindly rerun Apply. Owner-authorized reconciliation establishes actual state/trust/DNS outcomes and repairs the journal before work resumes.

Readback verifies persistence, not mutual exclusion. Version history supports recovery, not atomic updates or protection against an unrestricted storage writer. The supported safety boundary is one authorized writer, including during recovery; loss of that boundary stops automation. Restore tests must cover mismatched state/baseline/trust generations rather than accepting whichever object is newest.

## Durable SSH TOFU and DNSSEC SSHFP

### Enrollment

1. Privately obtain provider instance identity/addresses from successfully applied state. Require target A/AAAA resolution to agree, and wait boundedly for DNS/SSH. A hostname is not an instance identity.
2. Under the target writer's concurrency group, resolve the expected trust generation by target role and provider instance identity. Runner caches, fresh `known_hosts` and public artifacts are not trust stores. Use the encrypted, versioned control records and operation journal above; require matching reference/record bindings.
3. Only an explicitly approved, not-yet-enrolled generation may make a first observation. Consistently observe exactly one valid Ed25519 key on reachable expected addresses. Persist/read back the trust record and its generation reference **before** authentication/configuration, with instance/address binding, enrollment generation/time and SHA-256 SSHFP. Missing prior trust, conflicting evidence or failed persistence blocks deployment. Consistency checks do not eliminate the accepted first-use interception risk.
4. With a record, require an exact match. Never use `accept-new`, relearn, fall back to an empty file or overlook a missing record for a previously enrolled instance. Mismatch, lost trust or ambiguous identity stops delivery and alerts the owner.
5. Rebuild/rotation needs a separately approved enrollment generation after fencing the old host. Changed instance/hostname alone cannot authorize forgetting trust. Seeding existing manual pins is owner-authorized migration, not silent pin removal.

### Publication and connection

Publish **`SSHFP 4 2`** (Ed25519/SHA-256) from the persisted key, within the same serialized enrollment operation. The enrollment job is the sole SSHFP writer. Update only the expected record/name/type and retain a private trust-revision journal; never remove unrelated records or publish private keys. Initial enrollment/rotation is outside general safe auto-apply.

Cloudflare DNSSEC enablement alone is insufficient. Verify the parent DS/DNSKEY chain using a pinned local validating resolver, not an untrusted remote AD bit. Test bogus/insecure/missing/stale answers; wait boundedly for authoritative publication and validated resolution.

Connections require strict Ed25519 checking against the durable record, a private explicit `known_hosts`, `UpdateHostKeys=no`, batch mode and no global/agent fallback, **plus** matching DNSSEC-validated SSHFP. Validate DNSSEC independently and set `VerifyHostKeyDNS=no`: OpenSSH's `yes` setting can implicitly trust a secure matching SSHFP and bypass the durable key comparison ([OpenSSH manual](https://man.openbsd.org/ssh_config.5#VerifyHostKeyDNS)). Never warn-and-continue on absent/bogus/mismatched DNSSEC. SSHFP cannot authorize replacing durable trust. If inventory uses `HostKeyAlias=target`, validate the real DNS name explicitly rather than querying that alias. Connect only a validated literal address and recheck proof expiry immediately before SSH. Mask names/addresses/keys/fingerprints first; keep diagnostics private or fixed-code only.

Trust recovery is an owner-authorized restore from protected version history or newly authenticated observation, with competing automation fenced. An old record must not accept unintended rotation. Provider identity lookup, serialized encrypted persistence/readback/recovery and the local validating resolver need implementation and rehearsal; conditional storage APIs are not prerequisites.

## Deployment, staging acceptance and recovery

Preserve builtin-only Ansible, enforcing SELinux, one updater, rootless units with no exposed bot port, verified database TLS and runtime Podman secrets. Keep reviewed configuration and release bot commits explicit. Identity/schema/secret/candidate-unit checks precede mutation; one application has exactly one writer.

Quadlet recovery contracts:

- `ops/ansible/bot.yml` now stops the old writer and captures its stop-time boundary before installing/reloading the candidate unit. An existing writer without a captured timestamp is refused. Persist private `~/.config/tarubot/recovery-boundary.json` with previous/candidate image/schema context before candidate migration/start; failure results retain the captured boundary. The previous image's migration head is context, **not** a verified live database schema, and a timestamp is not proof of provider PITR recoverability. Live failure/recovery rehearsal remains pending.
- `.github/workflows/host.yml` no longer suggests blind image rollback on unhealthy results. Require explicit unchanged-schema evidence; otherwise inspect/fence the writer and fix forward or use owner-controlled restore. Missing evidence is not same-schema evidence.
- Unreachable hosts/lost results are `outcome-unknown`, not “nothing changed.” Never blindly rerun, restore, start an old worker or remove state. Inspect/fence the writer and live image/schema first.

Staging acceptance binds **this digest/commit/schema**: readiness/database/Discord/lease, a no-restart stability interval, command registration/readback, backup timer and successful encrypted backup. Use a separate database/role and distinct application. Preflight/synthetic checks cannot replace a healthy live bot. Initial setup and backup/schema/recovery changes need a decrypt/restore drill on scratch PostgreSQL, never a live database. Discord-writing acceptance remains owner-authorized.

Failure stops promotion and retains redacted phase/schema/restore evidence. Image rollback needs unchanged schema and a fresh authorized dispatch; no automatic database rollback. Committed migrations require compatible fix-forward or owner-approved restore/fencing. Production cutover fences/stops Compose before Quadlet, retains the existing cluster/data, verifies one writer and preserves recovery. Do not extend `ops/deploy.sh`'s unused legacy Quadlet modes.

### Durable trust foundation implemented locally

`scripts/ssh-trust.ts` separates encrypted trust by purpose, target and backend, with a dedicated per-target passphrase. It validates canonical Ed25519 SSH blobs and SHA-256 SSHFP, exact applied-host descriptors, expiring owner-approved generations and predecessor links. Enrollment reserves an immutable attempt and persists/readbacks intent, consumption and pending references before the first observation. Two observations must agree across every reachable expected literal address; an interrupted attempt cannot observe again. Missing current trust never authorizes automatic reenrollment.

Only exact owned SSHFP publication may proceed: read predecessor/conflicts, persist publication intent, write, read back and validate fresh local DNSSEC evidence before completion. Connections reopen all durable links, independently confirm the enrollment workflow's final successful conclusion and validate fresh DNSSEC again. The local resolver pin binds the Unbound version, helper, root anchors and full runtime manifest; a remote AD bit cannot satisfy it. Operational adapter integration and the owner-protected enrollment workflow remain pending.

Serialized read/write storage cannot guarantee that a failed acknowledgement after the final pointer write remains visible as pending. Intermediate failures retain fences; final ambiguity also needs independent successful workflow evidence, which an interrupted run cannot supply. Owner-fenced version-history reconciliation remains necessary. These tests do not establish approval, private storage compatibility or live enrollment, and the activation fence remains in place.

`scripts/trust-ssh.ts` supplies bounded two-round Ed25519 observation and one strict SSH invocation per fresh connection proof. It accounts for both descriptor addresses, refuses inconsistent reachability/keys and never authenticates while observing. A family is unavailable only on an exact initial-connect network-error diagnostic; empty keyscan results, protocol errors and uncertain timeouts stop enrollment. Authentication uses the exact durable key in a fresh private `known_hosts`, a validated literal address, explicit identity and isolated configuration/environment; no pooled connection, proxy, agent or retry is available. It checks proof expiry immediately before spawning. Safe baseline changes may reuse the same physical host identity, while changed addresses, instance or DNS identity cannot. Requests and evidence are copied across asynchronous boundaries.

`scripts/trust-ssh-stream.ts` reuses that private proof/pin lifecycle for bounded streaming input, stdout and stderr with backpressure. Each exchange calls its captured journal connection capability afresh; neither a frame nor a caller-supplied key can replace it. Shared preparation races the trust callback against a bounded deadline and accounts for physical elapsed time, then rechecks private paths/pin and original expiry immediately before spawning. The stream capability exposes known remote exit codes `0..254` internally; code `255`, signals, deadlines and failed streams are uncertain transport outcomes with one fixed error and no retry. Failed instances and used channels cannot be reused. Root login and existing passwordless sudo are the supported escalation contract. A first-party Ansible connection plugin, pinned launcher, private framing and operational journal/validator binding remain required; this API does not update the existing host workflow or authorize a host run.

`scripts/host-bridge-frames.ts` supplies private framing for one future command or file-transfer exchange. A fixed header binds the exact operation nonce, directional sequence, kind and bounded length; metadata has exact schemas and rejects duplicate decoded keys. Command tokens and canonical absolute transfer paths cannot select SSH options or identity. Frames distinguish input/file/stdout/stderr, with 64 KiB chunks, 8 MiB aggregate data and 9 MiB wire bytes per direction, at most 4,096 frames and eight pending writes bounded to 512 KiB including headers. Sends preserve order and backpressure; wall/physical deadlines include parsing/copying and never renew. A known remote result requires complete original request delivery and clean response EOF. A valid uncertain terminal immediately fences ordinary I/O without waiting for EOF or close acknowledgement; only a previously reserved uncertain terminal may flush under the original deadline. Channels are captured once and single-use, and late continuations cannot become another exchange. This is transport mechanics only: the future bridge must independently consume the authenticated target, obtain fresh guarded journal/local DNSSEC authority for each SSH invocation and own private per-exchange sinks. Frames, status and echoed private fields grant no authorization.

The first-party `tarubot_guarded` connection plugin and `scripts/host-bridge-adapter.ts` are exercised only by local fixtures at this stage. A parent-owned coordinator allocates one-use private channels and preserves uncertainty across controller workers and plugin reset/close. Exact passwordless sudo success gates pipelined input; framed exec/put/fetch supply no native SSH, SCP or SFTP fallback. The fixture launcher pins the controller's public core source and plugin bundle, generates one invented target, keeps exact localhost report plays local through its highest-precedence connection setting, and captures bounded controller output privately. Invented handlers live under `tests/fixtures/host-controller/`; no default operational handler or host-authorization factory exists. Core-source verification alone does not measure the whole Python runtime/dependency closure. Existing manual playbooks/configuration remain separate, and authenticated descriptor/journal/validator binding, durable reboot phases and operational integration are still required before activation.

`ops/dnssec/build.ts` builds only supplied public source into a new private directory; it installs nothing. It verifies the pinned source digest and detached signature against the pinned release key, and verifies IANA's root-anchor CMS against its pinned ICANN CA and designated signer. The runtime contains static libunbound plus measured copies of its shared dependencies and loader. `scripts/dnssec-validator.ts` rehashes/copies this complete closure on every invocation, clears inherited resolver/crypto/loader settings and runs validator plus iterator locally. SSHFP, A and AAAA must all be secure, non-bogus, complete, direct answers; addresses must exactly match the applied descriptor. The minimum TTL is reduced by lookup elapsed time. Review and pin the build receipt and runtime manifest independently; a matching name/version alone grants no trust.

Build on Linux AMD64 with Bun, GCC/make, OpenSSL and Expat headers, GnuPG and the normal archive tools. Supply the public archive and its detached signature from the pinned URL in `ops/dnssec/pins.json`:

```sh
bun --no-env-file ops/dnssec/build.ts PUBLIC_ARCHIVE PUBLIC_SIGNATURE PRIVATE_RUNTIME_DIRECTORY
```

The separate `buildLabDnssec` helper and `ops/dnssec/fixture.ts` are disposable rehearsal tools. Their differently measured binary has a compile-time localhost stub and uses an ephemeral synthetic root. Its flat synthetic zone disables query-name minimisation; the production iterator keeps its normal defaults. They cannot substitute for the production helper/root pins or authenticate a real host. The fixture exercises actual local DNSSEC validation with signed answers, altered signatures, unsigned AD-marked responses, missing SSHFP and different signed addresses.

`scripts/trust-run.ts` uses bounded GET-only GitHub evidence for exact first-attempt, owner-dispatched, main-branch enrollment/recovery runs. It checks the pinned workflow, target job, completed critical step, independently configured private owner account ID, final success and actual owner approval of a main-only protected environment, then rereads the gate/run. Its proposed gates are `trust-staging`, `trust-production`, `recover-infra`, `recover-staging` and `recover-production`; these are owner-created scopes, not changes to existing automatic staging or deployment gates. The API does not expose dispatch inputs/private outcome hashes or approval timestamps. Durable generation/intent bindings and independent outcome verification therefore remain separate mandatory integration boundaries. These workflows/environments have not been created or operated by this implementation.

`scripts/trust-live-run.ts` checks that the exact approved target job and its critical step are still running before mutation. It reopens the run, gate, main-only policies, current protected head, selected job and owner's approval, with a short expiry bounded by the oldest final-round observation. The same critical step must later succeed for the completed-run reader. Live metadata alone does not bind dispatch inputs or private grants and provides no atomic fence; operational integration must independently authenticate those bindings and retain the serialized writer boundary before every mutation.

`scripts/trust-provider.ts` supplies direct bounded HTTPS adapters with explicit credentials. It rechecks the owned predecessor and calls a mandatory authorization guard after awaited reads, immediately before POST/PATCH. Responses and final reads must agree; failure grants no retry authority. These guards still need binding to the durable enrollment journal and actual protected workflow.

`scripts/control-storage.ts` accepts an explicit infrastructure or per-target trust scope and allows only that scope's control/recovery paths. The infrastructure factory uses this adapter without changing its historical raw-backend encryption identity or namespace. Native S3 exposes no per-request deadline or redirect/response-metadata controls in the pinned API; operational adapters must run it inside a bounded isolated runtime.

Provider transports, codecs, journals and validator configuration retain secrets and authority in runtime-private fields; ordinary object inspection cannot reveal derived keys or substitute internal guards. Trusted dependency capabilities remain trusted. Disposable native rehearsal covers all three storage namespaces, bucket-qualified routing, ambient-token refusal before HTTP, encrypted journal reopen and a failed acknowledgement after persistence that still blocks downstream work. Scratch TLS backup/decrypt/restore and the separate localhost DNSSEC validator drill also passed; these results do not establish real-provider or live staging acceptance.

`scripts/target-descriptor.ts` derives the private target projection from full applied state/show evidence, two stable state readbacks and complete linked journal records. `scripts/target-handoff.ts` encrypts that projection with a dedicated per-target descriptor passphrase and purpose/backend binding, under an immutable release/run/payload path. `scripts/target-producer-run.ts` supplies bounded GET-only evidence for the exact successful infrastructure sealing job, its critical step and both referenced reusable workflow revisions. It accepts an otherwise valid publication run that is still waiting for its consumer. Configured repository IDs must match both fetched repositories; the check-run ID comes from the exact job's `check_run_url`, independently of its Actions job ID. These identities are checked again after private receipt authentication. Exact future nested job names are declarations for integration, not claims about jobs already present.

`scripts/target-sealing-oidc.ts` authenticates private sealing receipts with GitHub RS256 signatures from its fixed HTTPS issuer/JWKS endpoint. The signed audience binds every receipt field, expected job and stable verified writer identity. Consumer request time and eventual successful step status are excluded from that audience because neither exists while the producer mints its token; the producer reader independently requires the completed successful job and step. Authentication expires at the earliest signed JWT expiry, descriptor expiry or short proof deadline, including elapsed physical time during private reads. ### Completed-history recovery foundation

`scripts/control-recovery.ts` restores only exact encrypted bytes from owner-selected versions at the same scoped object paths. It verifies ciphertext/plaintext digests, the whole completed linked history, exact expected latest-object hashes, a fresh independent remote outcome and the owner's automation/hand-writer fence before writes. Infrastructure restoration requires matching state and a complete no-change plan; trust restoration also requires its independently successful enrollment run and fresh local DNSSEC/owned-record evidence. Dependency records precede the current pointer. Repair intent, pending reference, restored readbacks and completion are encrypted and verified; no Apply, key observation, DNS retry or synthetic completion is available.

Before any normal journal begin or connection resumes after repair, adapters must call `guardConsumer` with the repair generation independently retained by the owner and confirm that exact repair run's final success. Missing/pending metadata or an uncertain final acknowledgement blocks consumers even when a restored ordinary pointer looks complete. Do not enable this foundation until every reader uses the guard and the versioned storage/owner-boundary adapters are rehearsed. An interrupted repair or a partial remote outcome without valid completed history remains blocked for a separate reviewed reconciliation; no automatic retry or rollback is implemented.

`scripts/control-consumer.ts` adds an independently retained owner anchor that explicitly distinguishes a never-repaired scope, an expected completed repair and a fenced repair in progress. Absence of ordinary metadata never chooses the mode. The completed mode requires the whole-history recovery guard and independent final-run confirmation. Normal record wrappers bind the exact captured backend and reject repair paths before any I/O; opaque operation tickets retain one owner revision, repair generation, metadata hashes and initial expiry across bounded I/O and final verification. A changed owner boundary or late acknowledgement leaves persisted writes uncertain and grants no retry authority. Timeout cannot cancel a remote write already in flight. These checks do not provide mutual exclusion; fresh protected owner-anchor and completion adapters, workflow fencing and integration into every consumer remain mandatory before activation.

`scripts/control-owner-boundary.ts` supplies fresh GET-only owner configuration from the proposed `control-infra`, `control-staging` and `control-production` scopes. Explicit private owner/repository/environment IDs pin each whole read; `CONTROL_OWNER_ANCHOR` must declare the exact backend, namespace, revision and repair mode. A completed declaration additionally pins the full private intent digest and recovery commit/run. Its read-only `ControlRecovery.guardConsumer` checks the encrypted linked repair metadata and independently approved final run, then reopens the whole owner value. Missing configuration, changed values under one revision, observed revision rollback or expiry fails. Freshness includes the first request's transport time and physical elapsed time; an abandoned response cannot renew authority. No key, raw store or restore capability is exposed.

The owner must independently restrict configuration administration and provision a separate read-only credential. GitHub environment reviewers gate job execution; they do not establish who can edit a variable. Ordinary workflow/storage writers must lack configuration write permission, and the owner must fence automation and hand writers before restoration. These are provisioning prerequisites, never inferred from a reviewer list or an object-store copy. The current completed-repair adapter performs 68 GitHub GETs per guarded ordinary object read; repeated whole-history checks inside a journal operation need a separately reviewed bounded integration before activation. Do not relax freshness or cache authority to hide that request-volume limitation.

`scripts/control-journals.ts` is the mandatory operational factory for infrastructure and per-target trust journals: explicit scoped storage, independent current owner boundary, ordinary-record consumer guard, then the existing encrypted journal. Infrastructure also captures the real original-baseline execution reader from the same explicit private owner/repository/read credential; callers cannot replace it with an approval callback. It returns only a frozen journal and exposes no raw storage, codec, approval callback or recovery capability. Scope, historical encryption identity, private owner/repository/environment IDs and dedicated credentials are captured before I/O. The default infrastructure CLI now uses this factory; disabled reads return before construction and never look up owner configuration. Future host/enrollment adapters must also use this factory for every trust reader/writer/connection.

The seven infrastructure workflow journal entry points receive `CONTROL_OWNER_ID`, `CONTROL_REPOSITORY_ID`, `CONTROL_OWNER_ENVIRONMENT_ID` and `CONTROL_OWNER_READ_TOKEN` through masked secrets at step scope only. For `infra-plan`, `infra` and proposed `infra-auto`, the environment ID always pins independently owner-administered `control-infra`, never the execution gate. The separate repository-scoped reader needs Environments:read, Actions:read, Contents:read and metadata access, with no configuration write, dispatch or approval authority. Owner-only provisioning of these inputs and `CONTROL_OWNER_ANCHOR` remains required; the workflow declares references only and creates/changes no environment or secret.

`scripts/versioned-control-storage.ts` adds exact historical reads to the same scoped latest-record transport. The owner supplies a reviewed SHA-256 pin for the runner's root-owned `/usr/bin/curl`; the helper also requires curl at least 8.4 for streaming size enforcement. Only an exact bounded `NoSuchVersion` document can mean absence; contradictory object/version fields fail. There is no latest fallback, version discovery, deletion or retry. This reader does not supply owner approval or integrate normal consumer guards.
